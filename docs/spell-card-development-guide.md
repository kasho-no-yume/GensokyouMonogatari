# BOSS 符卡开发指南

> 本文是编写 BOSS 符卡（`danmaku/track/BossCards.java`）的工程手册。
>
> **语义规范来源**是 `openspec/specs/danmaku-track-composition` 与 `danmaku-motion`；
> 本文不重复定义语义，只讲**怎么写**、**按什么顺序查**、**哪些坑已经踩过**。
>
> 第 3 节的全部陷阱来自 `openspec/changes/rework-big-fairy-cards`（大妖精符卡重做，
> 2026-09-30）——那是本 mod **第一次正式开发符卡需求**，三条符卡全部返工过。
> 换句话说：这里每一条都是真金白银换来的，不要重新踩一遍。

## 1. 心智模型：四组必须绑死的概念

写符卡前先确认这四组关系。后面所有的坑都源于把它们当成独立的东西。

### 1.1 形状 × 行为 × 弹种 —— 三条正交的轴

一拍 = **几何**（发哪些弹、在什么方位）× **行为**（怎么动、怎么显、怎么死）× **弹种**（球弹/激光）。

- 形状只在 `Shape` 枚举里，**MUST NOT** 新造一个「悬停的环」这种把行为编进名字的形状
- 行为在 `Behaviour`，`Motion` 的 8 个 `Kind` 之间互斥
- 弹种在 `Projectile`（`SPHERE` / `LASER`），判据是**是否改变命中语义**（射线判伤 → 弹种；只改位置 → 行为）

### 1.2 几何不接触世界，位置解析在翻译层

`Geometry` 是无世界即可离线 lint 的纯数学。它**不接收 `Level`**。

「往下找地面」「往下找第一个空气」这类需要扫描地形的定位，走拍上的
`Track.Beat.SpawnAnchor`，由 `DanmakuEmitter` 求值（那里有 `boss.level()`）。

> 顺带：激光是静止射线，`speed = 0` 是它的**正确取值**，lint 已豁免。
> 别为了让 lint 过而给激光编一个假速度。

### 1.3 节拍判据跑在「循环内步号」上

```
step = cycleTicks > 0 ? tick % cycleTicks : tick
```

**`cycleTicks` 同时承担两个含义，它们是绑死的：**

1. **什么时候切走** —— 血量跨阈值时挂起切卡，等循环走完
2. **时间线靠什么重放** —— 显式枚举的拍每 `cycleTicks` tick 重来一遍

含义 2 是三次返工的直接原因，见 §3.1。**「持续型」= 必须给 `cycleTicks`**，
而「不声明循环」恰恰是保证它停掉的设置（`cycleTicks = 0` 时判据退化成绝对 tick，拍只响一次）。

### 1.4 「已发生」不能从别的状态推断

爆散 / 重瞄这类「到年龄换一次方向」的运动，需要记住「已经换过了」。这个标记
**MUST 是独立的一位**，MUST NOT 用「某个东西没了」去推。

> 因为「某东西没了」通常有歧义：「它被解除了」和「它从来没存在过」是两件事。
> 见 §3.2 —— 这个坑让花既不停也不散开。

## 2. 加一张卡的基本操作

### 2.1 步骤

1. 在 `openspec/specs/` 里找到该 BOSS 的符卡要求，确认这张卡在 spec 里有对应条款
2. 在 `BossCards` 里加一个私有方法返回 `SpellCard`，按血量从高到低排列
3. 形状：先查 `Shape` 有没有能用的；没有才新增（新增流程见 §2.3）
4. 行为：从 `Behaviour.Motion` 的 8 个 `Kind` 里挑；需要「到年龄换向」用
   `burst()` / `reclaim()`，两者都要求配一条编队帧
5. 逐发差异（某几发伤害/尺寸不同）→ `Beat.centreDamage` / `centreSize`（不是 `Shape.Params`）
6. 需要地面定位 → `Beat.SpawnAnchor`；需要生效前延迟（全向随机的可读性兑现）→ `Beat.harmlessTicks`
7. 跑 `BossCardLintTest.allBossCardTablesPassLint`
8. 数值：生命/弹伤/秒数走 config，不写进符卡表

### 2.2 代码骨架

```java
private static SpellCard myCard() {
    Track.Builder main = of("轨名", PALETTE.at(0))   // 颜色按【卡内轨序】分配，见 §3.6
            .identity(色相档, 速度档, 尺寸档)          // 视觉独占标识
            .repeatEvery(0)                          // 显式时间线
            .phaseStep(7.5D)                         // double，不是 int
            .formation(Behaviour.Formation.reference());  // 只要参考点
    for (int i = 0; i < N; i++) {
        main.at(i * STEP, Shape.XXX, Shape.Params.defaults()
                        .count(..).spread(..).speed(..).size(..),
                Behaviour.NONE.withMotion(/* ... */),
                TargetMode.SELF_AXIS,
                /* Projectile */, /* lifetime */, /* harmless */,
                /* SpawnAnchor */, /* centreDamage */, /* centreSize */);
    }
    return new SpellCard(card("<boss_id>", <序号>), 0.66D,
            List.of(main.build()), /* cycleTicks */);
}
```

符卡名走 `card(bossId, index)` 解析 lang 键 `spellcard.gensokyou.<boss_id>.<序号>`，
**不要从中文名推导键名**（中文名会改，键名跟着改等于作废已有语言条目）。

### 2.3 新增一个形状要动的地方

1. `Shape` 加枚举项 + 需要的 `Params` 字段
2. `Shape#guaranteesGap` / `isRandom` / `isOmniRandom` / `needsFacing` / `needsWorldAnchor` 归类
3. `Geometry#buildInternal` 加分支 —— **只准用局部基向量（forward/right/up）**
4. `DanmakuEmitter` 若需要新的行为开关
5. `TrackLint` 补该形状的 R1/R2/R3 判据

## 3. 陷阱清单

按**症状**索引 —— 遇到现象直接查。每条给出：症状 / 根因 / 现在由什么挡住。

### 3.1 符卡只放一次，然后就静默了

**症状**：进卡时正常放了几秒，之后彻底没弹幕。但 BOSS 血条还在掉、阶段还会切。

**根因**：`repeatEvery(0)`（显式枚举拍）+ `cycleTicks = 0`（未声明循环）。
节拍判据退化成「绝对 tick 等于拍号」，于是每个拍各响一次后永不重放。

**特别容易写成反**：「持续型」被写成「不声明循环」——**那正是保证它停掉的设置**。
大妖精阶段 1（环）与阶段 3（雨）都因此返工过一次，两次都是同一句话写反。

**现在由什么挡住**：`TrackLint#lintTimelineReplays` 静态拒绝
「多拍显式时间线 + 未声明循环长度」。

> 一次性过场**用单拍表达**（`repeatEvery(0)` + 1 拍 = 响一次就停），不需要结构豁免。
> 刻意没留豁免：「多拍但不想重放」与「忘了声明循环」在结构上无法区分，
> 而前者几乎没有使用场景，后者反复发生。

### 3.2 花/环该停住时不停，该散开时不散开

**症状**：本该「飞 1 秒 → 停 2 秒 → 散开」的弹，一路直飞永不停止，也不散开。

**根因**（两处叠加）：

1. `FormationFrame#active()` 判的是「**平面内有没有动作**」（自转/呼吸/公转），
   于是一个三项全零、只想提供参考点的帧被判为**不活动**，在 `bindToFrame` 里被静默丢弃
2. 「已结算」用 `!hasFormationFrame()` 推断 —— 而帧的缺失有歧义：
   「爆散后被解除」≠「从来没绑上」。缺失被当成已结算，于是速率曲线与换向**双双跳过**

**现在由什么挡住**：
- 新增 `Behaviour.Formation.reference()` 显式表达「只要参考点，不要平面内编排」
- `bindToFrame` 不再重复判 `active()`（声明侧已决定）
- `DATA_BURST_FIRED` 独立同步位，不再用「帧没了」推「已发生」
- 测试 `referenceOnlyFrameDegeneratesToAConstantPlusTravel` 钉住帧的常量性 + 曲线的静止段

> **教训**：这与 §3.1 是同一个形态 —— **用一个状态位去推断一个它不能唯一确定的事实**。
> 第一、二次返工我加了 lint 规则，第三次换了结构。lint 管声明层，
> 而 §3.2 的失败发生在绑定层，lint 看不见。

### 3.3 玩家死亡后 BOSS 放出「打不到人的僵尸弹」

**症状**：玩家死亡瞬间，某种按人复制的弹幕突然出现在 BOSS 脚下，停 60 秒后消失。

**根因**：`copies = perTarget ? Math.max(1, size) : 1`。
`Math.max(1, 0)` 把「零目标」静默当成「一个人」，于是锚点落回 BOSS 自己的脚，
瞄准方向变成竖直向下；而「重瞄各自的目标」解析不出实体 id，弹永远不发射。

**现在由什么挡住**：`TrackRunner#emitTrack` 在瞄准型轨道且目标集为空时**整轨不发**。
语义依据是 `TargetMode` 自己的定义：「`AIMED` = 有一发是给你的」，
没有给的人就不该有这一发。

顺带一条测试防线：`shippedCardsOnlyUseAimedOnTheRing` 断言**只有阶段 1 的环是瞄准型**。
否则哪天给别张卡加一条瞄准型轨道，玩家一死那整张卡就一起哑掉。

### 3.4 声明的弹径从未生效

**症状**：`Params.size()` 写了 0.95，实际弹出来比默认球（0.4）还小。

**根因**：`DanmakuEmitter#create` 把**弹速**传进了 `SphereDanmaku` 构造器的 `size` 形参。
于是所有 BOSS 弹幕的实际直径 = 弹速，`Shape.Params.size` 从未被读取。
「全大慢弹」这个定位从未成立过。

**现在由什么挡住**：`Geometry.Shot#size()` 是唯一的直径来源（几何声明 × 本发倍数），
并有回归测试。

> 这个 bug 存在了很久，一直没人发现 —— 因为小妖精的 0.4 恰好接近它的弹速 0.4，
> 看不出差别。**改一个"显然应该是那个意思"的传参时要格外小心，它可能一直是错的。**

### 3.5 相位取整，环多扫了一格

**症状**：`phaseStep(360/48)` 期望每拍 7.5°，实际每拍 8°，一圈扫了 384°。

**根因**：`Track.Builder#phaseStep(int)` 收 int。`7.5` 被截成 `7`（或 `8`）。

**现在由什么挡住**：`phaseStep` 收 `double`，`Track#phaseStepDeg` 也是 `double`。

### 3.6 声明色曾经是死字段（已修，勿回退）

**症状**：「我明明声明了淡蓝，激光出来是白灰」/「三张卡同色」。

**根因（已修）**：运行时颜色取 `palette.at(卡内轨序)`，而 `Track.color()` 全仓库无人读取。
单轨符卡（多张卡的常态）于是全部拿到 `at(0)` —— 作者写在 `of(name, PALETTE.at(k))`
里的那个色号从未被读取。淡蓝声明在轨 2，运行时拿到的是 `at(1)`（极淡粉白），
再叠上激光的加法发光就洗成白灰。

**现在由什么挡住**：
- `TrackRunner#emitTrack` 用 `track.color()`，且**签名里不再接收 `SignaturePalette`**
  —— 没有色盘参数，「按轨序取色」这条路径就无法被重新引入
- `TrackLint` 断言每条轨的声明色属于该 BOSS 的签名色盘
- 测试 `declaredTrackColorsAreLiveAndPaletteBound` 用反射钉住签名（不含色盘）
  并断言具体色相

**顺带一条实机经验**：激光这类自发光形状**必须给足饱和度**。
过淡的色（如 #DCE9FF）即使声明正确也会被加法发光洗成白灰。
判断标准是「蓝分量明显高于红分量」，测试里就是这么断言的。

### 3.7 索敌半径有两个数，没人对齐过

**症状**：48~64 格区间内，BOSS 会朝你放按人复制的弹幕，却**不再追你**。

**根因**：原版 `NearestAttackableTargetGoal` 的 `FOLLOW_RANGE` 是 48（构造属性时传入），
而弹幕锁定半径是 64（硬编码在 `refreshTargets` 里）。三个数（三只传 48、一只传 64、
锁定硬编码 64）互不相干。

**现在由什么挡住**：`AbstractTouhouBoss.LOCK_RADIUS` 是**单一来源**，
`bossAttributes` **不再接受 followRange 参数** —— 删掉第二个入口比写断言强。

> 顺带澄清一个常被误解的点：代码里**没有**「必须一开始在场」这道门。
> 目标集每 20 tick 全量重扫，走回来就在下一秒被重新锁定。唯一的「在场」判据是半径。

### 3.8 定时换向解析不出目标时，弹悬 60 秒

**症状**：一批弹停在半空，既不飞也不消失，直到寿命结束。

**根因**：只挂了速率曲线、没挂换向 —— 弹走到「停住等待」那段再无下文。

**现在由什么挡住**：`DanmakuEmitter#applyMotion` 在换向目标解析不出实体时
**整条运动都不挂**，退回普通匀速弹直飞出去。宁可打偏（一瞬间），不可悬住（一分钟且完全静默）。

### 3.9 全向随机必须声明无害窗口

**症状**：lint 报「违反 R1 前向威胁」，而你的花确实是全向抛射。

**背景**：R1 的原文是「生成点位于玩家视野锥内，**或该发有预警**」。锥包络只是兑现方式之一。
「弹在开火前够久不生效」同样是兑现 —— 公平性来自预警，不来自方向。

**现在由什么挡住**：`Shape#isOmniRandom()` 的形状（当前只有 `FLOWER`）
MUST 声明 `harmlessTicks > 0`，且**不得超过寿命的一半**（否则声明形同虚设）。

注意 `SCATTER_FALL` 不在此列：它的方向恒为竖直向下且来自 60 格之上，方向极其可读，
随机性在「落在哪」而非「朝哪来」。

### 3.10 读档后弹幕冻结（未修，有意保留）

**症状**：退出游戏再进，一批弹停住不动，约 60 秒后才消失。

**根因**：`deltaMovement` **从不入盘**。该模型对速率曲线/编队帧/爆散自洽
（位置是 `(t, p₀)` 的纯函数，读档能自愈），但「纯弹道飞行」这一段的速度只存在于
`deltaMovement` 里。四只 BOSS 的普通弹、小妖精、玩家武器弹幕**全都是这样**，
只是普通弹 2 秒就飞出场外没人注意。

**为什么不修**：见 `openspec/changes/danmaku-event-sync/spellcard-blockers.md`。
结论是等 `danmaku-timeline-sync` 落地后按它声明的兼容路径处理。

**写符卡时的实际影响**：任何带「静止等待」段的编排（`harmlessTicks` 语义的那些）
都会在读档后被撞上。实测时记得退出重进一次。

### 3.11 持续型卡的循环长度 ≠ 内容跨度，于是每轮末尾静默一段时间

**症状**：弹幕「放一阵 → 停一阵 → 再放一阵」，循环边界处有明显的空档。
和 §3.1 的症状是镜像的（那个是「只放一次」，这个是「放完一节就哑」）。

**根因**：`cycleTicks` 比内容跨度长。显式时间线只在其占用的那几拍上响，
剩下的时间落在循环尾部，每一轮都空一段。实测踩到的实例：雨季喷泉
（10 拍 × 20 tick = 200 tick 内容）曾复用**花之海洋**的循环常量，
两个值当时恰好都是 200 所以看不出来；花卡的循环一被调长，雨卡就跟着变长，
于是每轮最后 40 tick 完全静默。

**为什么 lint 抓不到**：留余量**不总是错的**。阶段 1 的环是「6 秒放环 + 6 秒游走」，
循环 240 而内容只有 48 tick，余量是**刻意的叙事分段**。
所以「循环 > 跨度」无法从结构上判定对错。

**怎么办**：
- **每张卡用自己独立的循环常量**，不要跨卡复用（复用的危险在于「两个值恰好相等」会掩盖耦合）
- 测试里**逐卡钉死循环长度的确切值**——这才是真正抓住上面那个 bug 的东西
- 写测试断言时把「为什么是这个数」写进断言消息
  （如「阶段2 = 12s，末朵第 60 tick 抛出、第 160 tick 爆散，余量 80 tick」）
- 自问一句：**这一轮的尾部空档是设计，还是漏算？**

## 4. 密度：两道闸，都要过

| 闸 | 判据 | 谁的职责 |
|---|---|---|
| **R3 层限** | 每名玩家 6 格内的稳态并发数 ≤ `STEADY_STATE_BUDGET`（120） | 可读性契约 |
| **实体上限** | 全场存活弹幕实体数 ≤ `danmakuEntityCap`（800） | 性能护栏 |

**两者是不同的量**：736 颗花全在 BOSS 身边 5 格内（对 R3 未必超），
但它们同时占着 800 上限的 92%（对实体上限很紧）。

`steadyStateEstimate` 按编排形态分流：
- **无限重复轨**（`repeatEvery > 0`）：按周期摊薄
- **显式时间线**（`repeatEvery == 0`）：区间扫线取**最大重叠数**，权重是**颗数**
  而不是「颗数 × 停留」——后者会把并发数放大数十倍

**豁免是合法但有界的例外**：`SpellCard#densityWaiver`，封顶预算的 8 倍，
且测试要求它**贴着实际值**、全表**至多一处**。当前唯一豁免是花之海洋，
理由（估值假设玩家站在爆散中心，而距离带下界 10 格使其物理上不可能）写在字段 javadoc 里。

**密度算不出来的时候先算一遍**：单次发数 × 场上停留秒数 × 每秒发射次数。
这个乘法比 lint 更早告诉你会不会撞线。

## 5. 调试

| 想知道 | 用什么 |
|---|---|
| BOSS 现在锁了谁 | `/gs_boss danmaku` 的 `emitted` 与实体命中数 |
| 弹幕管线有没有异常 | `/gs_boss danmaku` —— 重点看 `rejected`（判到了却没掉血） |
| 实体数有没有撞上限 | 同上的 `live=` / `cap=` |
| 某个形状长什么样 | `/danmaku spiral`、`/danmaku flower`、`/danmaku web`、`/danmaku laser-ring` |
| 阶段为什么没切 | 看该卡有没有 `cycleTicks`；没有就是即时切换（§3.1） |
| 弹为什么打不到人 | 分三层：判定没命中 / 伤害被吞 / 打了但量级不对（见 `danmaku-combat` spec） |

**三个最容易被误判的现象**：
- 「看着撞到了却不掉血」→ 必须看 `/gs_boss danmaku` 那一行，`entityHits=0` 与 `damageSum=0` 是两回事
- 「弹比想象的大/小」→ 先确认 `size` 真的生效（§3.4）
- 「只在开头出现」→ 先查循环长度（§3.1），再看是不是每玩家一份（§3.3）
