# 人间之里环境居民

居民是客户端模型，不是实体。不会响应攻击、交易或实体选择器，不产生服务器 AI、居民同步或存档。具名角色仍使用 NPC 系统。

## 预览

在创造模式站到平坦、干燥、已加载的地面上，面向一片空地执行：

```text
/gs_residents preview 24
/gs_residents preview 96
/gs_residents status
/gs_residents clear
```

预览排在执行时玩家前方，最多 96 名，一半驻足、一半沿短路线往返，按每 tick 最多 12 次尝试渐进补入。预览期间暂时替代正式活动点，清除后恢复正式场景。只在本客户端可见，不修改方块；清除、切维度、退出世界或资源重载都会移除预览。生存模式不能创建预览。

## 建筑接入

资源包在 `assets/<namespace>/village_residents/<scene>.json` 放活动点：

```json
{
  "dimension": "gensokyou:gensokyo",
  "origin": [-200, 72, 100],
  "residents": [
    {"id": "bookstall_reader", "points": [[-6, 0, 2]], "facing": 90},
    {"id": "lane_walker", "points": [[0, 0, 0], [8, 0, 0], [8, 0, 6]]}
  ]
}
```

原点和点偏移单位均为方块，Y 为预期脚底高度，允许向下两格、向上半格的局部地面适配，避免把低顶或临时障碍的顶部当成新落点。一个点代表驻足，多点代表沿折线往返，每个节点短暂停留。`facing` 使用 Minecraft 偏航角。槽位 ID 需要唯一且稳定，修改 ID 会改变外观。

正式活动只在指定维度的已加载区域生效，脚下必须是 `landmark_packed_earth`（自带颜色的夯实村土）、`landmark_brick`、`landmark_wood`、`landmark_tile`、对应半砖或楼梯；不因为自然草地碰巧在同一坐标就出现居民。不要把路线穿过建筑或水面。每条最多 16 点，相邻点 0.05–64 格，每个资源场景最多 128 人，资源总槽位最多 512；附近候选（含动态人流）也最多 512，同时最多活动/绘制 **96 人**，距离上限仍为 **96 格**。96 是共享上限，并非保证任何地点都显示满员。

正式 `human_village.json` 保留 116 个核心槽位（50 名驻足、66 名行人），分布于龙神广场、商街与市集、铃奈庵、鲵吞亭水巷、稗田宅门前及高札场/香霖堂西道。核心只依赖跨种子固定的公共留白，留白可以是土面，不要求整条石板路。需要重新生成核心配置时运行 `python tools/export_human_village_residents.py`。

核心 JSON 原点仍为 `[-200,73,100]`，这是 v1 基准。收到 v2 布局时，`VillageResidentAnchors.coreSlot()` 将该场景的所有活动点降低一格，对齐地面块 `Y=71`、脚底 `Y=72`；替换这个资源时也须使用 v1 基准，不能先自行降低一格。其他资源场景不受此偏移影响。布局变更会清除旧 walker。

人流不再按“一户一人、三格往返”生成，也不再排除核心 240 格。`VillageResidentAnchors` 仅索引建筑描述；只在玩家附近查询房屋门前、共享街巷、广场、地标外围及编排路线附近的兴趣点，远处不创建居民活动状态。v1 也可在已有合规铺装上补充行人，不改变它的布局或高度。

`ResidentStreetCrowd` 从 72 格内兴趣点逐步建立路线，最多缓存附近 384 条候选；每 40 个未暂停的本地 tick 或玩家水平移动 8 格后刷新兴趣点。动态候选约八成尝试行走，目标为 8～16 格往返，受阻可缩短为至少 4 格，少量路线可在空地转弯，约两成为驻足；实际行走比例取决于可用街巷。每半格检查落脚和扫掠碰撞，压缩共线节点，仍不超过 16 点。行人行速在原外观速度上乘 1.25，节点暂停最多 12 tick；原有核心编排不改速度或停留节奏。

路线生成每 tick 最多探查 48 个地面点，只读取已加载客户端区块；使用发送到客户端的 `MOTION_BLOCKING` 高度图，结合 landmark 支持面、身高净空、建筑占地与公共地标高度限制，排除屋内和屋顶。此预算是检查调用数，不是帧耗保证。

`ResidentPopulation` 保留仍在 96 格内的有效行人，逐 tick 更新其动作；离开范围后不再模拟。无效/未加载落点不占用人数名额，失败点短暂退避后重试，从后备候选补足；每 tick 最多尝试补入 12 名。动态新居民不在玩家 8 格内或距已有居民不足 1.2 格的位置出现，已有居民可正常走近玩家。仍使用同一个模型、贴图和绘制批次；没有新实体、存档或居民同步。

**正式居民只在视野外补入**：使用最近一次实际渲染视锥，检查居民经过随机路线相位和落脚适配后的完整身体，并外扩一格缓冲；与视野相交的点暂缓 60 个本地 tick 再试，继续查找后备点。核心编排和动态行人都适用。策略采用保守的视锥判断，视野内即使隔着墙也先等待，不把透明方块误认为可靠遮挡。

首个实际渲染帧还会复核一次，防止“tick 判定在身后、渲染前玩家已转头”的情况下直接现身；确认有一帧处于视野外后，居民即可正常走入视野，之后不重复隐藏。没有新鲜相机画面时先等待，初次进入世界、重连/重载后也遵循这一规则。主动执行 `/gs_residents preview` 是看外观的例外，可出现在面前。等待视野外入场时实际人数可能暂时少于上限。

服务器按已加载区块渐进放置村庄。v1 存档保留旧建筑/道路/进度，不自动改成 v2；已有区块不会因重进世界再次覆盖。**完整检查新版聚落与 Worldgen 土面请使用新测试世界**，不要删除或强制覆盖用户已有村庄。

**本次增加人流不要求重建村庄或新建世界**：已有 v1/v2 村庄在更新客户端并重新进入后即可使用附近人流逻辑。上述新世界要求只针对之前的地形/房屋布局改造。

管理员可使用 `/gs_village visit dragon|hieda|suzunaan|geidontei|kourindou|east_gate` 抵达核心地标，使用 `/gs_village stats` 查看建筑、归一化内/中/外区民居数、装饰铺装格数、平面入口可达率、放置进度及粗采样群系边缘余量。平面入口检查不验证高差与真实身形碰撞。`/gs_village showcase` 继续使用独立样件维度供逐栋查看模板，它不代表 v2 的街区排布。修改居民资源后执行 F3+T 即可重新加载场景。

自动化回归由 `HumanVillageResidentsAlignmentTest` 检查核心模板/路线，`VillageResidentAnchorsTest` 检查旋转、核心兴趣点与屋顶排除，`ResidentStreetCrowdTest` 检查局部路线/预算/回收，`ResidentPopulationTest` 检查无效点回填、96 人上限与状态复用。以上是回归源码覆盖，**本轮按本机策略未运行编译/测试或游戏**；实际人数、行走观感和性能仍待实测。原生完整村庄探针仅在明确要求时经项目 wrapper 启动。

## 实机验收

- 预览不同居民，检查三种衣形、四种头部样式、配件与配色，离开再返回时外观稳定。
- 居民正常被不透明墙遮住，日夜和灯光影响亮度；不得全亮或透墙。
- 在行走路径前放方块，居民停住；移除后从原位置继续。检查台阶/半砖、坑洞、水和低顶，不穿墙、不跳过阻挡。
- 暂停单人游戏时动画停止；F3+T、退出重进、切维度后无旧场景或预览残留。
- 联机执行预览，另一客户端不出现该预览，服务端没有新增居民实体。
- 使用 `status` 记录本地活动/绘制数量，沿 96 格边界和低视距巡查；性能数值需在实际硬件采样，不以实体数为零代替帧耗验收。
- 新世界从边缘穿过住宅组团进入核心，检查土面驻足、局部石板、缓坡与门槛，确认外围也有居民，且回到核心时不超过共享预算。
- 在已有村庄核心、普通街巷和外围各停留数秒，再缓慢移动/快速转身，检查新增行人、短暂停顿、复用与回收；用 `status` 区分活动人数和视锥内实际绘制人数。
- 盯住街道/广场等待补人，检查没有人物当面或从屏幕边缘突然出现；转身后再看回来，已有行人应继续动作。测试快速转头、第三人称、FOV 调整、重连/F3+T，以及预览仍可在面前显示。

## 开发工具

本次使用 OpenSpec 2.2.0；当前容器中安装在用户工具目录，仓库提供 `bash tools/openspec_task.sh` 入口：

```bash
bash tools/openspec_task.sh status --change add-client-village-residents
bash tools/openspec_task.sh validate add-client-village-residents --strict
```
