## Context

`danmaku-render-state` 已归档并落地实体级的模拟状态、权威样本、渲染偏移、快照恢复和有限校准。本变更建立在它之上，不重新实现 `lerpTo` 隔离、渲染访问层或恢复状态机。

当前仍有两个独立问题：

1. 客户端确定性运动仍主要使用本地实体 tick。快照能建立“服务器采样时刻 ↔ 客户端本地历史”的关系，但不等于知道服务器当前时间；网络延迟、客户端暂停和两端推进速率差异仍可能表现为相位偏差。
2. 编队参数被复制到每枚实体，原版位置包仍按实体更新率发送，低频校准也按实体发送。客户端不使用普通位置包驱动模拟，并不意味着这些包没有带宽成本。

`docs/danmaku-sync-architecture-and-open-problems.md` 是调查记录，不是运行时规范。文档中关于旧实现的“4~8 tick 年龄差”、投影滞后和符号翻转，可能混合了采样时刻、纠偏反馈和位置投影误差；它们只能作为需要复现实验的线索，不能直接成为时间轴算法或成功判据。实现前必须用带服务器时间的样本、未被硬纠正污染的模拟历史和 dedicated server 场景重新测量。

## Goals / Non-Goals

**Goals:**

- 为确定性弹幕定义服务器时间、轨道时间和阶段边界的单一语义。
- 让客户端可以从轨道输入和服务器时间直接重建确定性表现位置，不依赖逐 tick 网络位置或本地年龄巧合。
- 用轨道、版本、生命周期和实例索引表达共享运动参数，减少重复参数与重追踪竞态。
- 明确旧位置模式、实体快照模式和轨道模式的写权限与兼容边界。
- 保留服务端命中、伤害、分裂预算、销毁和区块判定的权威性。
- 为后续 `danmaku-event-sync` 提供稳定的 scope、时间、版本和生命周期接口。

**Non-Goals:**

- 不重复实现已归档的 `danmaku-render-state`。
- 不在本变更中实现事件缓存、缺号重放、灵符目标事件、分裂事件或激光关键帧。
- 不要求一次性迁移所有实体；非确定性弹幕可以继续走实体级快照/关键帧兼容模式。
- 不把客户端轨道计算用于命中、伤害、无敌帧、分裂配额或服务端生命周期。
- 不以“画面不抖”单独证明时间轴正确，也不使用无限相位外推掩盖失步。

## Evidence Boundary

- 已确认：普通位置包不应再写入模拟位置；这一点由归档的 render-state 代码和测试负责。
- 待确认：当前快照锚定是否在不同网络延迟、客户端暂停、dedicated server 和双客户端错时追踪下产生可接受的同刻相位。
- 待确认：关闭或降低位置/校准包后的实际带宽、CPU 和画面质量收益。
- 不采用未经复现实验的结论，例如把 `lagTicks = error · direction` 直接当作年龄差，或把单机内嵌服务端的表现推广到分机环境。

## Decisions

### 1. 服务器时间与轨道时间分层

每条轨道保存：

```text
scopeId          稳定轨道身份
scopeVersion     轨道重建/重载版本
startServerTime  轨道时间起点
startAge         起点年龄或等价相位
endServerTime    可选的生命周期终点
trackParams      可重建运动所需的不可变参数
```

轨道时间由服务器时间和起点定义。客户端维护受限的服务器时间估计，并保留最近锚点的来源、年龄、接收时间和误差界限。时间估计只用于表现重建，不修改服务端时间，也不把客户端本地 tick 当成权威时间。

时间源必须是单调的服务器游戏时间或明确的模组 epoch。不得混用不同维度、不同世界或不同客户端 session 的相对 tick。服务器暂停、降速或 tick gap 的语义必须在实现前明确；不能默认“现实经过一秒”必然等于 20 个轨道 tick。

### 2. 轨道先做纯函数，后做网络迁移

先把现有确定性路径抽象为无世界求值接口：直线、速率曲线、曲射、编队帧、悬停/溜め、相位显隐和固定阶段。接口输入必须显式包含轨道时间、实例索引和完整参数，不读取实体、目标、方块或客户端当前坐标。

服务端命中仍使用实体真实位置和扫掠结果。客户端轨道求值只提供模拟/渲染表现和诊断，不能成为玩法输入。

### 3. 轨道快照和实体实例

轨道快照包含完整可重建参数、版本、生命周期、外观/阶段参数和实例索引范围。单枚实体只携带 `scopeId`、`scopeVersion`、实例索引和实体专属数据。轨道参数不能引用客户端无法获得的服务端对象。

第一阶段允许实体继续存在，以复用现有生成、移除、渲染和服务端碰撞管线；轨道模式只取得位置表现和确定性运动的写权限。旧模式和轨道模式必须由同步模式明确区分，不能同时改同一模拟位置。

### 4. 与 render-state 的接入边界

普通原版位置包仍只能进入 legacy 诊断/权威样本路径，不能恢复为轨道模拟驱动。轨道快照和时间锚点通过现有完整恢复入口或其明确的轨道扩展原子应用：身份、版本、时间、轨道输入和实例状态必须来自同一个更新边界。

渲染偏移仍由 render-state 管理。轨道求出的模拟位置是基准，可信样本之间的有限视觉追赶不能改写轨道时间、轨道参数、实体年龄或服务端判定。

### 5. 版本、生命周期和重追踪

`scopeId + scopeVersion` 标识一次可重建的轨道生命周期。相同版本的重复快照必须幂等；更旧版本不得回滚；新版本必须清理旧轨道的历史和缓存后原子建立新基准。实体 id 不能作为跨追踪周期的唯一身份，必须配合 UUID 或等价实例身份。

实体先于轨道包注册、轨道包先于实体注册和实体重复追踪都必须有明确处理：按身份有限暂存，注册后应用；超过窗口请求/等待新快照；不得由未知包创建幽灵弹。

### 6. 渐进迁移和带宽门槛

迁移顺序固定为：测量基线 → 纯函数轨道 → 时间锚点 → 轨道快照/实例 → 单一实体类型灰度 → 关闭确定性位置驱动 → 扩大覆盖。

只有当实测确认轨道模式在带宽、CPU、重追踪和画面质量上满足门槛，才关闭对应实体类型的普通位置驱动。兼容模式必须可诊断、可回退，但回退时只能切换同步模式，不能让新旧协议同时写状态。

## Risks / Trade-offs

- 时间估计受网络延迟、客户端暂停和服务端 tick 状态影响。使用低频锚点、单调检查和最大漂移界限；超界进入兼容/不确定状态。
- 浮点和超越函数可能跨端产生差异。遵守现有数值纪律；不能逐位重建的运动进入关键帧模式，由 event 变更处理。
- 轨道快照减少参数重复但增加生命周期和版本管理。用 scope 版本、快照重置点和有限缓存约束复杂度。
- 原版实体分发器可能仍对实体坐标做世界平移/插值。复用已归档的渲染访问边界，并对每种 renderer 和激光缓存做回归检查。
- 追踪范围不足属于可见性问题，不应被时间轴伪装成位置纠偏。单独记录实体缺失、生成延迟和位置偏差。
- 轨道模式迁移可能增加初始快照尖峰。使用批量轨道快照和实例索引，并记录峰值而非只看平均带宽。

## Migration Plan

1. 修正/补充诊断，区分服务器时间、客户端时间、轨道时间、收包时间和位置投影误差。
2. 增加无世界轨道接口和时间映射纯函数，不改变现有实体同步行为。
3. 增加轨道快照、scope 版本、生命周期和实例身份；先以兼容模式验证重追踪/重载。
4. 选择球弹/编队弹等确定性路径做单一实体类型试点，比较原版、render-state 和轨道模式。
5. 通过带宽与画面验收后，才关闭试点类型的位置驱动；其余实体继续兼容模式。
6. 将轨道身份、时间和生命周期接口交给 `danmaku-event-sync`，由后者接管非确定性状态。

## Open Questions

- 服务器时间使用 `gameTime`、模组 epoch 还是按维度维护的单调序列？需要覆盖暂停、降速、重载和跨维度。
- 客户端时间锚点如何估计传播延迟：只使用单向锚点，还是增加轻量往返/确认？质量门槛是什么？
- 轨道快照继续复用实体生成包，还是使用独立轨道 payload？需要测量包量、实体生命周期复杂度和丢包恢复成本。
- 轨道模式是否保留实体位置包作为纯诊断，还是完全停止发送？两种方案的服务端/客户端成本需实测。
- 旧存档缺少轨道身份时，是长期兼容还是首次快照后转换？转换时如何确保不重复生成实体？
