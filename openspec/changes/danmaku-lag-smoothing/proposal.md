## Why

**本变更为备选项，不在关键路径上。** 先用**未经任何优化**的现存弹幕模式，在普遍网络环境下验证其流畅度；只有当实测证据表明存在可见问题时，本变更才应被实施。

### 现状的一处结构性问题

`AbstractDanmakuProjectile.lerpTo` 只在误差超过固定绝对阈值（1.0 格²）时硬纠正位置包：

```java
if (errorSqr > POSITION_CORRECTION_THRESHOLD_SQR) { this.setPos(x, y, z); }  // :459
```

稳态误差 ≈ `L × v`（L = 网络延迟 tick 数，v = 弹速）。因此阈值是一个**速度相关的分界线**：

```
v < 1/L（如 L=3 时 v < 0.33 格/tick）→ 误差恒低于阈值 → 永不纠正 ⇒ 永久滞后 L 个 tick
v > 1/L                              → 每个位置包都超阈值 → 每 2 tick 硬拽一次
```

模组内大半弹幕速度在 0.2~0.5 之间，即：**约一半弹幕永久性地比服务端晚约 150ms 跑且永不收敛，另一半每 2 tick 被拽一次。** 这不是「抗抖动」，是「按速度分裂成滞后与抖动两种失败」。

### 为什么不是「通用帧同步的平滑拉回手段」

jitter buffer 与输入预测解的是**输入延迟**问题（网络抖动使重放时间轴不稳 → 缓冲 → 预测缺失输入）。此处的条件不成立：

- 弹幕运动是 `tickCount` 的**纯函数**，其「输入」（初速 + 行为参数）在 spawn 包中一次性给全
- ⇒ 客户端自 spawn 起**已知道整条未来轨迹**，预测早已免费获得
- 真正缺失的不是预测，而是**呈现相位**：客户端在 `t` 绘制 `f(t)`，而服务器钟上的「现在」是 `f(t + L)`

**这不是抖动，是一个恒定的相位偏移。** 缓冲解决不了常量偏移，也无处可缓冲——弹幕运动在给定同步状态下完全确定（撞墙即死、`splitFired` 由 `tickCount` 派生、灵符 `targetLost` 由同步目标位置派生、激光长度由双端各自 clip 同一份同步方块状态）。

### jitter buffer 治不了的三件事

即便引入也不解决，故 MUST NOT 作为本变更的目标：

```
① clientTrackingRange = 8 格 → 环半径 10 的外圈在客户端【根本不存在该实体】——可见性问题
② spawn 延迟：弹在服务端 tick S 生成，客户端 tick S+L 才知道，该窗口内玩家【看不见它】
   ——需要预警（激光的 DELAY 期即此用途），不是平滑
③ 密度尖峰：一 tick 内生成 200 颗 = 一帧内 200 个 spawn 包——带宽/CPU 突发，不是平滑
```

## What Changes

### 第 0 步：诊断先行（无条件实施，且是本变更的准入闸门）

本变更 MUST NOT 在有实测数据之前实施任何修法。先补齐测量能力：

- `DanmakuBudget` 的统计 SHALL 增加两个维度（现有 5 个计数器全是数量、零时间与滞后维度）：
  - **硬纠正计数**——每 tick 被 `lerpTo` 阈值触发的次数，按弹速分档
  - **滞后估计分布**——每枚弹的实测滞后 `L̂` 的 min / 中位数 / p95
- 提供一个可读的诊断输出（`/gs_boss danmaku` 扩展或独立子命令），使「是否需要本变更」成为**可判定的决策**而非口味问题

**准入判据**（实施前由用户依实测填写）：

| 实测结果 | 结论 |
|---|---|
| 硬纠正计数 ≈ 0，且 p95 滞后在「一个 tick 的位移小于一个屏幕像素」以内 | 现存方案足够，**本变更整体关闭** |
| 硬纠正计数高但滞后分布小 | 只需「速度相对阈值」一项（改动最小） |
| 滞后 p95 明显，且弹幕移动可见地落后于其逻辑位置 | 走「相位推前」 |

### 第 1 步：三个候选修法（按风险递增，二选一或三选一）

三者互斥，**第 3 项是前两项的超集**。

**候选 A：速度相对阈值**（改动最小，只改判据）

```
接受位置包：|serverPos − predictedPos| < v × MAX_LAG_TICKS
拒绝：       否则
```

判据含义：「这个误差能否用弹自身在插值窗口内的移动解释掉」。`MAX_LAG_TICKS ≈ 4`（200ms）时，0.2 格/tick 的弹容忍 0.8 格、0.5 格/tick 的弹容忍 2.0 格——**任何速度都不再有永久滞后**。真失步是方向性的（漏收一次 `setVelocity` 会使分歧远大于此），故仍能被拒。

- 消除永久滞后 ✓　消除抖动 ✗（快弹仍每包硬拽）
- 改动面：一行判据

**候选 B：模拟位置与渲染位置解耦**

位置包写入独立的渲染位置字段，**MUST NOT** 覆写模拟位置；渲染时在两者之间插值。

- 消除抖动 ✓　**消除永久滞后 ✗**——在两个都滞后的量之间插值，只掩盖不消除
- 改动面：渲染路径

**候选 C：相位推前 `f(t + L̂)`**（唯一同时消除两者的方案）

```
每个位置包到达时：
  e  = serverPos − clientSimPos
  L̂ = e · v̂ / |v|                     投影到速度方向 → tick 单位的滞后
  L̂ ← EMA(L̂)                          窗口 3~5 包（config 可调）

渲染位置 = f(tickCount + L̂)
判定仍在 t 上计算（服务端才是权威，客户端只负责绘制），两者互不干扰。
```

**这不是外推。** 现有运动模型为「匀速 + Rodrigues 旋转」，闭式求 `f(t + L̂)` 只是把旋转角从 `curveRate·t` 换成 `curveRate·(t + L̂)`——**精确值而非近似**。任何速度下均消除滞后，且渲染位置是 `L̂` 的连续函数，**不随包的到达而跳变**。

- 消除永久滞后 ✓　消除抖动 ✓　近似误差：无（闭式）
- 改动面：渲染路径 + 一个 EMA 标量

### 硬性约束

- **L̂ MUST 钳位**（建议 0~10 tick）。否则若模拟本身存在非确定性，`L̂` 会漂移去补偿，**把同步 bug 从「硬失败」静默转成「错渲」**。钳位使真失步以硬纠正形式暴露，而不是变成数十 tick 的外推。
- **静止弹 MUST NOT 估计滞后**（`|v| < ε`）。悬停与溜め弹无滞后可言，投影无定义。
- **L̂ 估计在曲射下的偏差**可接受：90°/s、3 tick 滞后下，`e` 沿路径而 `v̂` 沿当前切线，夹角约 7°，`L̂` 偏差约 0.1 tick。
- **降级路径**：`L̂` 无效（`e` 与 `v̂` 不共线、或 `|v| < ε`）时 MUST 回落到候选 A 的判据行为，MUST NOT 跳过位置包。
- **`lerpTo` 的所有权**：本变更接管「位置纠偏与渲染定位」。`danmaku-budget-and-sync-correctness` MUST NOT 同时包含该项的修法，两者不得并行修改同一行为。

## Impact

- **前置条件**：第 0 步的诊断能力 MUST 先行落地。
- **依赖**：第 0 步的诊断挂在 `DanmakuBudget` 上，与 `danmaku-budget-and-sync-correctness` 的 tick 计时维度是同一次改动，建议合并实施。
- **风险（这是它被列为备选项的原因）**：
  - **`L̂` 吸收真 bug**——若运动学存在非确定性，同步缺陷会退化为静默错渲而非显式失败。钳位只能限制幅度，不能根除。
  - **需要手感验证**——平不平滑、延迟感不性感是感知属性。算法正确性可单测，**观感无法自动验证**。
  - **子 tick 精度**——现有渲染已用 `partialTick` 在 `oldPos`/`pos` 之间插值。分数 `L̂` 与该插值的叠加关系需实测确认，初始估计可能有偏差。
  - **L̂ 的窗口取舍**——短窗（3~5 包）跟得紧但噪，长窗（10+）稳但跟不上延迟抖动。起步 5，实机调。
- **收益**：`L̂` 估计收敛后，位置包**第一次有了用途**（携带权威位置供相位对齐），而不再是发出后被阈值比较丢弃的冗余流量。

## 自动化验证的边界

以下 MUST 由自动化测试覆盖（本仓库现有测试全为无世界的纯静态测试，故属新增类别）：

- 滞后估计的收敛性：给定恒定滞后与噪声，`L̂` SHALL 收敛到真值
- 闭式一致性：`f(t + L̂)` 闭式求值与「逐 tick 步进到 `t + L̂`」SHALL 逐位相等
- 钳位生效：注入远超上限的误差时 MUST 触发硬纠正而非外推
- 静止弹：`|v| < ε` 时 MUST NOT 估计滞后
- 分档判据：候选 A 的阈值在 `v → 0` 与 `v` 极大两端的行为

以下 **MUST NOT 尝试自动化**，只能由用户在实机判断：

- 「弹幕看着是否平滑」
- 「读作零延迟」
- 「EMA 窗口取多少手感最好」
