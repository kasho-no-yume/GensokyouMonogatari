## Context

两个数值 change 已归档（2026-11-04）。它们的代码、单测、模型报告与文档已交付；1.6 数值关卡由用户审核通过，但明确“数值长期可调、后期全面实测”。剩余工作全部是**实机验证 + 数据驱动的微调**，需要独立跟踪。

## Goals / Non-Goals

**Goals:** 在真实服务器/客户端环境验证已交付行为；收集时长、资源、生存、出货分布数据并与理论对比；对确认偏差提出有据可查的候选调整；保持所有调整经过用户审核与回归测试。

**Non-Goals:** 不重做机制、不新增属性/卡片、不改变仪式经济、不在没有数据的情况下调常数、不把“有限样本通过”当作全局最优证明。

## Decisions

### D1 数据优先

每次实机测试都必须记录到验收文档的登记表（场景/数值/预期/实际/偏差）。调参提案必须引用具体记录行；没有记录的“手感不适”不构成调参依据。

### D2 阈值沿用已审核口径

- 同阶 BOSS 理论全命中时长：1 阶 2–5 分、2 阶 3–8 分、3 阶 5–12 分、4 阶 10–16 分、5 阶 15–20 分。
- 无回血直接耐弹基线 2–8 次；治疗/护盾收益另报。
- 攻速实际交付 ≈ 基准 ×(1+攻速)，允许 ±30% 观测误差（命中/停顿）。
- 回灵/汲取与账本对账：固定窗口总量误差 ≤ 1 个整格；停火恢复按 0.12%/s（全甲 0.18%）校验。
- 核出货：10 万样本统计已在 `core-generation.md`；实机抽查只核对结构（条数/唯一/类型混合），不重复做百万级抽样。

### D3 调整流程

1. 发现偏差 → 记录数据并归因（口径错误 / 常数 / 实现 bug / 观测条件）。
2. 若是实现 bug → 本 change 开修复任务（可另立 change）。
3. 若是常数问题 → 更新候选表（保留旧值）→ **用户审核** → 改 `BuildNumbers`/`CoreAffixCatalog` → 全量 `tools/gradle_task.ps1 test` + `build` + 重新生成分布/可达性报告 → 更新文档。
4. 每次调整后回归同名单测；被驳回的候选也记录（append-only）。

### D4 已知待复评项

- 攻速词条权重 2.0 与窄带组合导致高攻速投放≈0（10 万样本 T1/T2 高值 0 次）——按实机体验决定是否降权重/放带宽。
- 治疗统一系数 0.5、上限 1.5（×2.5 封顶）是否在所有治疗卡上成立。
- 核池绝对带/预算上限在真实出货中的观感（过低/过高）。
- T3 弹幕核（激光炮）与 Lv3 武器等级核缺少配方——登记项，若启动需另立 change。
- 三控制卡（黑暗/蛛网/疫符）专属最短冷却：当前“先记录不加锁”，实测占空后最终裁定。

## Risks / Trade-offs

- [逐次微调导致基线漂移] → 每次调整更新审核表并保留旧值与理由；同批调整集中审核，避免碎片化改动。
- [实机样本少导致过拟合] → 阈值按“档位区间”判定，不按单局精确值；结构性问题才动常数。
- [调参绕过审核] → 所有数值改动必须先在候选表登记并经用户确认；本 change 的 tasks 不设“直接改数值”条目。

## Migration Plan

无存档/数据迁移。若微调触及已发布常量，随版本发布说明记录（含改动前后值）。
