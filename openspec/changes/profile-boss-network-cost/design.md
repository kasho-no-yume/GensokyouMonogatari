## Context

**要回答的问题**：一场 BOSS 战（召唤→死亡），服务端到**某一个客户端**的链路消耗是多少？
峰值多高？哪张符卡最贵？单弹生成成本多大？——这些问题至今没有任何实测数据。

**为什么现在**：`danmaku-track-scope` 的门槛是「生成突发的实测带宽基线」，悬置已久；
弹幕密度继续提升前需要它。且现有 `net_jitter_proxy.py` 已在链路上，具备扩展为观测点的条件。

**现状约束**：

- 开发/测试为**同机**（client + dedicated server），流量走 loopback——loopback 容量近无限，
  适合测 **offered load**（服务端发出的原样），但看不到真实瓶颈；瓶颈由后继变更在代理处合成。
- 测试服务端配置：`online-mode=false`、`network-compression-threshold=256`。
  ⇒ 链路**不加密**，但**启用 zlib 压缩**（>256B 的包在线上是压缩后的字节）。
- 环境：Python 3.11.3，PIL 12.1.1、numpy 2.4.2 **已装**，matplotlib **未装**。
- 既有诊断在 Java 侧（`DanmakuBudget`、`/gs_boss danmaku`），BOSS 生命周期与符卡切换均有钩子。

**两条链路的字节口径不同，必须分开说**（本设计最重要的一个区分）：

```
  服务端逻辑包                      线上（客户端实际收到）
  ┌──────────────┐                 ┌──────────────┐
  │ Packet 对象   │ ──帧编码──zlib──│ 压缩后的字节  │
  │ 63 int 参数   │                 │ 可能只有一半  │
  └──────────────┘                 └──────────────┘
        ↑ 语义在这里                      ↑ 带宽真相在这里
     包类/实体类型可读                  但读不出包类
```

⇒ **语义**与**线上真相**各在一处，无法用单一观测点同时拿到。故本设计用两层观测互补。

## Goals / Non-Goals

**Goals:**

- 产出一场 BOSS 战的**可复现运行账**：逐窗口字节序列（含压缩后线上字节）、包类分解、
  符卡归因、峰值与放大率。
- 全程**不依赖任何外部抓包工具**（无 Wireshark / pktmon）。
- 观测**不改变被观测对象**：零延迟、零包改写、零行为改变。
- 报告图为 **PNG**，不引入新依赖。

**Non-Goals:**

- 写入限速 / 带宽档位扫描（后继变更 `simulate-link-bottleneck`）。
- 丢包 / 乱序模拟。
- 代理侧 MC 协议解析（包类归因由服务端 handler 承担）。
- 逐字段协议解码、实体类型的精确到每包（v1 按包类聚合，实体类型仅对 spawn 类包归因）。

## Decisions

### D1: 线上字节曲线由**代理**产出，且**不解析协议**

代理只需按读取块累计字节数、按时间窗口落盘。它天然对加密/压缩免疫——因为它数的就是
链路上流过的字节。故：

- 曲线骨架（每秒/每 50ms 的 s2c、c2s 字节量）= 代理。
- 峰值与突发 = 代理按**细窗口**（默认 50ms）采样后由报告聚合；均值会掩盖 spawn 突发，
  细窗口是抓突发的前提。
- 代理不承担任何包类解析职责（见 D2 与其被否的方案）。

### D2: 包类/实体归因由**服务端 Netty 出站 handler**产出

在玩家的出站管线中、**帧/压缩编码器之上**插入一个 `ChannelOutboundHandler`，观测 `Packet`
对象。理由：

- 它所在的位置看得到**明文 `Packet` 类与实体类型**，免疫加密与压缩；
- 天然按玩家分（每个 `Connection` 一个 handler）；
- 天然对齐服务端 tick（可与符卡 marker 直接关联）。

统计：每包类（`ClientboundAddEntityPacket` / `SetEntityData` / `MoveEntityPacket` /
`RemoveEntities` / 区块 / `LevelChunk` / 音效 / 粒子 / 交互 …）的**包数**与**压缩前字节数**，
按窗口/tick/玩家聚合。**入站方向同理**（可选，先做服务端→客户端）。

**⚠️ 口径差异（必须写进报告）**：handler 拿到的是**压缩前**字节。压缩开启时，它与 D1 的
线上字节不是同一个数。报告 SHALL 同时给出两者并显式标注，不做「相等」的假设。

### D3: **否决**在代理侧解析 MC 帧

曾考虑的方案：代理读 Varint 帧长 + 包 id，绕过服务端改动。被否，理由三条：

1. **压缩阈值是有状态迁移的**：登录期未压缩，服务端在握手中途发 `Set Compression` 才启用，
   之后帧格式变成 `[总长][解压后长或0][包体]`。代理要维护「登录/游玩」两套包 id 命名空间
   与压缩开关的迁移状态机。
2. **版本耦合脆弱**：包 id → 名称的映射随协议版本与 mod 变化，错一位就全表错位，且没有
   自检信号。
3. **收益已被 D2 覆盖**：D2 更稳、更全（含实体类型），代价只是一个 handler。

⇒ 代理保持「哑字节计数」，这是它最稳的职责，也是后继限速变更要复用的形态。

### D4: 时间基准与对齐

- 代理与 marker 均记录**墙上时钟**（`time.time()` / `System.currentTimeMillis()`）。
  同机运行时两者时钟偏移≈0；报告记录一次估计的偏移量并标注。
- marker 另带**服务端 tick**（`level.getGameTime()`），供与服务端 handler 的 tick 聚合对齐。
- 对齐以墙上时钟为主键，tick 为辅证。**不假设三者天然对齐**，报告给出对账误差。

### D5: 输出分「原始」与「合成」两级

- 代理与服务端 handler 只写**原始记录**（JSONL，追加、随写随 flush），崩溃安全、可离线重析。
- `boss_net_profile.py` 读原始记录 + marker，产出 CSV / PNG / 文本摘要。
- 分离理由：live 路径保持最小（不引 PIL、不做分析）；同一场战斗可反复出不同视角的图。

### D6: marker 流复用既有钩子，落盘在最贴近日志处

- 召唤：`EntityJoinLevelEvent`（`DanmakuBudget` 已订阅）过滤 `AbstractTouhouBoss`。
- 死亡：`AbstractTouhouBoss#die` / `dropThemedCard`。
- 符卡切换：`AbstractTouhouBoss#onCardChanged`（与既有 `announceCardName` 同处）。
- 写 `server/` 下的 JSONL（gitignore 内）。这些钩子全在服务端线程，逐行 flush 无锁。

### D7: 报告图用 PIL，不引入 matplotlib

PIL 已在仓库依赖中（`gen_tex.py`）。用 PIL 画「以时间轴为 x 的堆叠/阶梯面积图 + 符卡竖线
标记」即可满足需求。matplotlib 被否（未装、重）。备选 SVG（纯文本、浏览器可看）可作补充，
但不作为主路径。

### D8: 一层对账，作为自检

报告的文本摘要 SHALL 给出：`服务端 handler 累计字节` 与 `代理累计字节` 的差，并解释其来源
（压缩率 + TCP/IP/帧开销 + 非本模组流量）。**对账不平 = 有观测盲区**，必须显式暴露，
不得静默。

### D9: 为后继限速留接口

代理的计量模式与限速模式共享同一条 relay 路径与同一种「按连接/方向记账」结构；
`--profile` 与未来的 `--rate` 可叠加。本变更不实现 `--rate`，但字节记账的落点即为限速所需
的观测点。

## Risks / Trade-offs

- **[代理只数字节，读不出包类]** → 由服务端 handler 补齐；两者在报告中并列，不混算。
- **[压缩前/后字节口径不同，读者误当相等]** → D2/D8 强制并列与对账标注。
- **[同机 loopback 无瓶颈，测的是 offered load 而非真实链路]** → 明确声明产物是 offered
  load；真实瓶颈留待后继变更在代理处合成。
- **[服务端 handler 的管线插入点/处理器名随版本变化]** → 设计与实现时以「帧编码器之上、
  取 `Packet` 对象」为准，具体管线名（`encoder`/`prepend`/`compression`）在实现时核实；
  加断言/日志，插不上时显式报错而非静默不计数。
- **[多玩家时无法区分「哪个客户端」]** → 每个 `Connection` 独立 handler；代理按连接 id
  区分。报告可按玩家过滤。
- **[墙钟对齐在跨机时不成立]** → 本变更定位同机；报告记录偏移估计，跨机场景显式标注不可信。
- **[marker 与字节的符卡归因是近似]** → 符卡切换同一 tick 内可能已有前一张卡的余弹；
  报告按 marker 时刻切段是**近似**，标注之。

## Open Questions

1. 服务端 handler 是否需要同时覆盖**入站**（客户端→服务端）？首版可只做 s2c（瓶颈方向），
   入站按需再加。
2. 窗口粒度：默认 50ms 是否够抓 spawn 突发？可能需按 tick（50ms）保留、报告再聚合。
3. 是否需要把「每弹生成成本」直接算成 `bytes_per_bullet`——需要 handler 识别 spawn 包并
   除以窗口内 spawn 数；实体类型是否够用，还是需要 mod 层的发射计数（`DanmakuBudget.emitted`）。
4. 观测命令的形态：`/gs_net start|stop|mark <label>`（手动打点）是否必要，以补自动 marker
   覆盖不到的场景（如玩家中途加入）。
