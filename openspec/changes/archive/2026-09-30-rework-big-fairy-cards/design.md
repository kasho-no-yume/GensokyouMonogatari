## 1. 原始需求（逐字）

> boss如果在血量到达转阶段，但还在使用上一个符卡，须等待上一个符卡运行完再继续下一个阶段的符卡。避免符卡之间的叠加。
>
> 普通攻击手段，与下述所有符卡叠加。大妖精每3秒，发射5*5的弹幕墙，弹幕之间的发射夹角10°，中心弹幕朝着玩家方向。
> 1阶段符卡：66%~100%血时，花符[弹幕花环]。大妖精悬停不动，每有一名玩家，就在背后生成一个由48个弹幕组成的环。弹幕依次出现，间隔0.05秒生成一个，每个弹幕生成3秒后，朝玩家方向以6格每秒的速度发射。因不同玩家而生成的环须追踪各自的玩家。不同环之间的同一序列的弹幕是同时生成的。所有弹幕发射完后（可以认定为从生成环开始过去了6秒），大妖精进入6秒的随机移动时间。重复此过程。
> 2阶段符卡：33%~66%血时，花符【花之海洋】。该弹幕玩家无关。做一个由约46个弹幕（中心一个大的，花瓣9个小的，5个花瓣）组成的花状弹幕阵列，大妖精每0.2秒随机方向向周围以12格每秒抛射16个这样的花。花不必自旋，抛射方向不必是花平面的法线方向，可以是任意方向。花运动1秒后悬停2秒后，花的花瓣小弹幕朝着各自到中心连线的反方向以4格每秒的速度射出。中心大弹幕选随机目标玩家方向以6格每秒的速度射出。大弹幕的伤害需要是标准伤害的4倍。在此符卡过程中，大妖精可以移动。符卡使用循环周期为10秒。
> 3阶段符卡：0~33%血时，夏符【雨季喷泉】。此阶段中，大妖精持续移动。每秒在大妖精半径30内随机24个点，在这些点的xz坐标，y坐标为大妖精上方60格的地方生成蓝色弹幕，朝地面竖直向下射出，速度为6格每秒。同时，每秒从地面上取点，从该点竖直向上射出淡蓝色激光（预警2秒，持续6秒，长度80）。每5次取点，至少有一次要取到某一个玩家所在的xz坐标。

### 1.1 原文勘误

原文保留不改，此处单独记录作者后续的口头修正，避免读者把两版混读：

| 位置 | 原文 | 修正为 |
|---|---|---|
| 2阶段发射节奏 | 「每0.2秒…抛射16个这样的花」 | 「每0.2秒抛射**一朵**，一共抛射**16朵**」——16 朵在 **3.2 秒内**抛完，不是每 0.2 秒抛 16 朵 |

修正后的算术：16 朵 × 0.2s = 3.2s 抛射窗口；随后是炸开花的过程（每朵 1s 飞 + 2s 悬停 = 3s，故最后一朵在 t≈6.2s 炸开）；10 秒周期的余下约 3.8 秒为空窗期。

### 1.2 实机反馈后的追加修订

以下三条来自第一次实机验收，均为**对原文的修订**（原文保留在 §1.1 不动）。

| # | 反馈 | 修订为 | 为什么 |
|---|---|---|---|
| R1 | 「悬停时全部集中在一起，没分开」 | 抛射段 **1s → 3s**，循环 **10s → 12s**，寿命 8s → 10s | 抛射行程 = ½·0.24·ramp。1 秒只有 **2.4 格**，于是 16 朵全部停在 BOSS 身周 2.4 格的球内——方向虽全向随机，但**半径就是分散度**，2.4 格撑不起一片海。3 秒 = 7.2 格。<br>循环 +2s：末朵在第 60 tick 抛出、第 160 tick 爆散，240 tick 留 80 tick 余量；寿命 200 = 爆散前 100 + 散开 100，同时满足 lint「无害期 ≤ 寿命一半」 |
| R2 | 「激光是白灰色，并非淡蓝色」 | **修根因**：`TrackRunner` 改用 `track.color()`，并把 `at(5)` 调到 #7FB4FF | 淡蓝声明在轨 2，运行时拿到的却是 `palette.at(卡内轨序)` = `at(1)` #FFD9F0（极淡粉白）——**符卡表里声明的颜色全程是死字段**。过淡的色再叠上激光的加法发光就洗成白灰。所以既要把色号给够（蓝分量明显高于红），也要修「声明色不被读取」这个结构问题。见 §3.15 |
| R3 | 「花弹幕需要改成粉红色」 | `at(2)` #B8FFC9 绿 → **#FF8AD4 粉红** | 与 R2 同一根因：这条轨声明的是 `at(2)`，从未生效过（实际取到 `at(0)` #9BE7FF 淡青）。R2 修好后声明色才第一次真的显形，故同时调色号 |

**R2 顺带改变了三只其他 BOSS 的实际弹幕颜色**（狐、纬、面的部分轨道此前拿到的也是「按轨序」而非其声明色）。这是修正而非回归：它们声明的色号本来就在各自色盘内，只是一直没被读取。lint 现已断言「每条轨的声明色属于该 BOSS 的签名色盘」。

## 3. 与现有实现的落差

按「缺原语」列出，每条注明它卡住哪一条需求。**这些是实现债，不是设计债**——设计本身已定稿。

### 3.1 阶段推进：需要「挂起切卡」

`AbstractTouhouBoss#syncCard` 每 tick 调 `runner.selectCard(阈值)`，命中即刻切换并把 `TrackRunner.tick` 归零，于是新卡从第 0 拍开始——符卡会在半途被拦腰截断。

`TrackRunner` 已有 `currentCardDuration()` 与一个从未被消费的 `currentResolved` 标志，但前者对 `repeatEvery > 0` 返回的是**周期**而不是总长。缺的是：每卡声明循环长度 + 一个「已到循环边界」的信号供 `syncCard` 消费。

### 3.2 默认攻击不能进 `BossCards`

按项目规范，默认攻击是**独立于符卡表的一条常驻轨**（符号卡↔符卡永不叠加、符卡↔默认攻击可以叠加），必须做成实体类上的第二发射器，频率与参数全从 config 读。

config 里已有一个**死键** `bigFairyShotIntervalTicks`（默认 80，无任何读取点），可复用为频率项；还需新增弹速、尺寸、颜色、格数、角度间隔等项。

### 3.3 缺「拍级寿命」

2阶段花瓣定为 8 秒，但 `Track.Beat` 与 `Behaviour` 都没有寿命字段。`AbstractDanmakuProjectile#setLifetimeTicks` 存在，只是轨道层够不着。

环与雨决定不限寿命（D18），所以这项只为花瓣服务。

### 3.4 缺「二维角度栅格」几何

普通攻击的 5×5 墙需要两个轴各 10° 间隔的固定方向偏移。`FAN` 只绕 `up` 轴偏转 = 纯水平张角，**没有纵向参数**。需要新形状。

### 3.5 缺「零速率期走接触判伤」

阶段1 等待期要能伤玩家（D7）。现状：`stationary` 只由 `isHovering()` 置位，走的是 `checkStationaryEntityHit()`（AABB 接触判伤）；而速率曲线把速度压到 0 时走 `DanmakuHitScan.sweep`，零位移恒 MISS（坑 6）。

最小改法：在 `AbstractDanmakuProjectile#tick` 里把「速率曲线当前速率为 0」也算作 `stationary`。这是一处小改，不是新原语。

### 3.6 缺「定时重瞄」——全套需求里唯一引入实体引用的地方

D9 要求弹在第 3 秒起飞时重新瞄准所属玩家。这与项目一贯原则冲突：`FormationFrame` / `DanmakuSpeedProfile` 一律「MUST NOT 存在承载编队参数的实体」，理由就是实体方案会引入追踪范围、客户端卸载导致全批脱钩、换阶段销毁时序、孤儿弹处置、弹引用失效一整类问题。

可行做法（须接受一条已知代价）：弹只持有目标 **entityId**（一个同步 int），在起飞那一 tick 由**服务端**解算方向并写回同步数据，客户端收到即生效。
代价：客户端的起飞视觉比服务端晚 1~2 tick（50~100ms），命中判定完全不受影响（服务端权威）。
若不接受这条延迟，退路是退回「出生瞬间锁定方向」——那就不需要任何新原语。

### 3.7 缺「逐发随机平面」

D12/D13 要求全向 360° 随机抛射，且花平面与抛射方向不必成法线关系。

`Geometry` 的 14 个形状**只准用 BOSS 局部基**（forward / right / up）；`ROSETTE` 的花平面恒为「面向主目标的竖直面」。`Behaviour.Formation` 是**轨级**声明（一轨一个自转轴），救不了「16 朵花各自一个平面」。

服务端真随机是安全的（几何只在服务端求值一次，位置随即烘进弹的出生数据），所以这不是同步问题，是几何表达力问题。

### 3.8 缺「按年龄切换运动方向」

花瓣在悬停满 2s 后朝各自半径的反方向射出。现有 6 种 `Motion` 里：
- `CURVE` 是**等角速度绕单轴**——每颗弹转同样的角度，做不到 45 颗各自转向自己的半径；
- `SPEED_PROFILE` **只改速率不改方向**（`alongAxis(velocity, speed)` 只改模长）。

需要一个新 `Motion.Kind`，或一个「径向爆散」形态。

### 3.9 缺「逐发伤害乘数」

中心弹 4× 伤害。`damageScale` 是**轨级**的（`TrackRunner#emitTrack` 给整条轨一个 damage），一轨 46 发共享。

拆成两轨（花瓣一轨、中心一轨、`damageScale(4.0)`）也解决不了：两轨无法共享同一个随机抛射方向与同一个花的生命周期。

### 3.10 缺「体积内随机撒 N 个点」

阶段3 雨的 24 个随机点。13 个形状**全部从单一原点展开**：
- `FALL_FROM_ABOVE` 是规则网格（3×3 那种），不是随机；
- `SCATTER_STATIC` 是正圆环；
- `LATTICE` 的随机是围绕**目标**的，且只服务激光。

### 3.11 缺「地面吸附」

两处需要：雨要从 BOSS 上方 60 格往下找第一个空气；激光要从地面点起竖直向上打。

`Geometry` 不接触 `Level`，找不到地面高度。
好消息：激光本体、`Projectile.laser(...)` 与 `Track.Builder#laserAt` 入口**都已就绪**（`LaserDanmaku` 有 `Phase{DELAY, ACTIVE, DONE}`、预警指示线、每 5 tick 射线判伤），缺的只是生成点。
地面吸附应放在 `DanmakuEmitter`（那里有 `boss.level()`）；激光是静态的、出生点烘一次即成，不涉及双端一致性。

### 3.12 缺「移动锁」

阶段1「悬停不动」+「位置锁死、保留转向」（D10）。`AbstractTouhouBoss#tick` 无条件调 `steerNow()`，需要新增一个覆写点：跳过 `steerNow()`，保留 `faceRandomTarget()`。

### 3.13 `Shape.Params.size` 是死参数

`DanmakuEmitter#create`（第 118 行）把**弹速**传进了 `SphereDanmaku` 构造器的 `size` 形参：

```java
SphereDanmaku sphere = new SphereDanmaku(
        server, boss, damage, color, (float) speed, NO_WHITELIST);
//                                   ^^^^^^^ 形参是 size（球体直径）
```

默认档案 `visualScale = hitboxScale = 1.0`，故**所有 BOSS 弹幕的实际直径 = 弹速**。当前大妖精三张卡声明的 size 是 0.95 / 0.85 / 1.05，实际发出来是 0.30 / 0.28 / 0.22——比小妖精（0.4）还小。

D16 的「中心弹直径 2 倍」做不出来，**必须先修这个串位**。注意它会一次性改掉四只 BOSS 的全部弹幕观感与判定尺寸，不只大妖精。

（其余 12 处 `new SphereDanmaku` 调用点都传了真实 size：0.35 / 0.4 / 0.8 / STRESS_SIZE 等，只有这条生产路径串位。）

### 3.14 `TrackLint.steadyStateEstimate` 对显式时间线会算爆

估值公式是 `Σ beats 的 (count × 停留) / max(1, repeatEvery)`。`repeatEvery = 0` 时分母取 1，于是**每一个显式枚举的拍都被当成永久每拍发射**。

本方案三张卡全是显式时间线：
- 阶段1：48 拍逐颗（每拍 1 发）
- 阶段2：16 拍逐朵（每拍 46 发）
- 阶段3：20 拍逐秒

以阶段1 为例：`48 × 1 × (12 / 0.3) / 1 ≈ 1,920`，远超 `STEADY_STATE_BUDGET = 120`。

这个估值对「会停的编排」本身是错的（skill §4 那张「5 拍 × 20」样板今天也过不了 lint）。须先修判据或改公式，否则三张卡全部 lint 红。

### 3.15 顺带发现（不在本次必须处理，但记录在此）

- `Track.color()` **全仓库无人读取**。运行时颜色取自 `TrackRunner#emitTrack` 的 `palette.at(轨序)`，所以色盘分配（D22）必须按**卡内轨序**排，不能按声明色。
- `SpellCard.name()` 无 UI 消费点，玩家看不到符卡名（见 §5）。
- `BIG_FAIRY_MAX_HEALTH` / `BIG_FAIRY_DAMAGE` 只作静态属性种子，`applyStats()` 在首个 aiStep 就用 `bossSeconds` / `bossHits` 算出的值覆盖。

## 4. 密度算术与风险

两道闸：
- **实体硬上限** `danmakuEntityCap = 800`。`canEmit()` 只在 `TrackRunner#emitTrack` 的**每目标一次**处检查，**不在每发处检查** ⇒ 溢出会整拍溢出，本拍剩余发数被 `return` 掉。现象是「一坨爆发然后静默」，不是平滑降级。
- **`TrackLint.STEADY_STATE_BUDGET = 120`** 颗/玩家（且该估值对显式时间线本就算错，见 §3.14）。

| 来源 | 单次发射 | 周期 | 峰值在场 | 判定 |
|---|---|---|---|---|
| 默认攻击 | 25 | 3s | ~25（飞行 2~3s） | 安全 |
| 阶段1 环 | 48 × 5人 = 240 | 12s | 无寿命约束下取决于地形：撞人/撞地约 1~2s 内消解则 ~40；开阔地一路飞 60s 则堆到 **~1,200（破）** | **地形依赖，需实测** |
| 阶段2 花 | 16 × 46 = **736** | 10s | 736 = 上限的 **92%** | 8 秒寿命下可过，但只剩 8% 余量 |
| 阶段3 雨 | 24 | 1s | 掉到地面约 11s ⇒ ~264；若 60 格内无地面则按 1200 tick 上限 ⇒ **1,440（破）** | **地形依赖，需实测** |
| 阶段3 激光 | 1 | 1s | 6（6s 持续） | 安全 |

**最紧的一处是阶段2 的 736 / 800。** 改动下面任何一个数都会立刻破：
- 16 朵 → 17 朵即 782，加上默认攻击与阶段切换残留就撞线；
- 46 弹 → 47 弹即 752；
