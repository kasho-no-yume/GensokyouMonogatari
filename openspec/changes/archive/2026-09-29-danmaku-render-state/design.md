## Context

当前弹幕实体的 `Entity.position()` 同时承担三种职责：客户端预测的模拟位置、服务器位置包提供的权威样本和 renderer 的绘制位置。`lerpTo` 在误差超阈值时直接调用 `setPos`，因此纠偏不仅改变画面，还会改变下一 tick 的运动段。编队弹尤其容易因此形成反馈回路。

本变更先建立状态隔离层，并提供实体级最小初始化/重建闭环。它不负责完整的服务器时间轴和轨道级同步，也不负责改向、分裂等事件协议；最小重建契约用于避免客户端进入失步状态后没有恢复出口，并为后续时间轴和事件同步提供一致的接入点。

## Goals / Non-Goals

**Goals:**

- 让位置包只进入权威样本层。
- 让 renderer、激光裁剪和包围盒使用统一的渲染状态。
- 在正常网络抖动下平滑追赶，不产生周期性硬拉回。
- 在不可解释误差下显式进入失步重建状态。
- 提供最小权威重建数据及获取路径，使失步状态能够恢复，而非无限等待未来变更。
- 保持服务端逻辑和客户端视觉状态的职责边界。

**Non-Goals:**

- 不实现轨道级参数分发和共享服务器时钟；允许实体级恢复携带建立一致运动状态所必需的数据。
- 不实现改向、分裂、目标切换等事件协议。
- 不改变服务端命中判定或客户端模拟的玩法权威性。
- 不承诺仅靠渲染层消除实体追踪范围不足。

## Decisions

### 1. 三态分离

客户端状态明确拆为：

```text
simulationState      供本地轨道/实体模拟使用
authoritativeSample  最近服务器位置或状态样本
renderState           供 renderer 使用的连续位置和阶段
```

选择独立状态而不是仅在 renderer 中临时插值，是因为激光包围盒、激光方块裁剪和不同弹幕 renderer 也必须读取相同位置；临时插值会重新产生多个坐标来源。

### 2. 正常样本不改模拟位置

`lerpTo` 只记录样本和采样时间。可信样本通过渲染追赶器影响 `renderState`，不调用 `setPos`。只有显式失步重建才允许替换模拟状态，并且重建后清空旧样本和追赶速度。

这比速度相对阈值更安全：阈值只能判断误差大小，不能防止纠偏反馈污染下一 tick。

### 3. 渲染追赶器使用有界速度

渲染位置向目标位置连续追赶，具有最大每 tick 位移和最大积累相位。追赶器不得无限外推；样本翻转、误差超界、轨迹切线不一致或实体生命周期不一致时进入 `UNCERTAIN`/`DESYNCED`。

候选方案中，直接硬纠正视觉位置会保留拉回；无界 EMA 可能把真正失步静默吸收，因此采用有界追赶器加显式重建。

### 4. 统一渲染访问层

所有弹幕 renderer 通过统一的渲染状态访问器取得位置、旧位置、阶段和几何起点。激光长度缓存按渲染状态版本或服务器样本版本失效，不能继续以原始实体位置作为唯一裁剪起点。

### 5. 兼容旧路径

在轨道/事件同步尚未启用的实体上，状态容器仍可接收原版位置样本并标记为 `LEGACY_POSITION`。兼容模式必须在诊断中可见，且新旧路径不能同时改写模拟坐标。

### 6. 第一阶段包含最小重建闭环

原版位置包只能提供位置等有限信息，不携带可用于本协议的服务器采样时间、恢复版本和完整运动状态。客户端接收时间不是服务器采样时间；不得由一个位置点反推曲线轨迹的唯一年龄，也不得把位置投影估计当作实测年龄差。

最小重建数据必须在同一权威采样边界下表达：

- 实体身份与客户端世界/追踪生命周期的有效性，防止旧响应应用到新的实体实例。
- 恢复版本或请求关联标记，使重复应用幂等，过期响应不能覆盖已经接受的新恢复状态。
- 权威采样时间、该时刻的弹幕年龄，以及建立本地年龄锚点所需的信息。锚点必须与接收时的本地计数关联，不能无条件再叠加客户端已经运行的全部 `tickCount`。
- 位置、运动方向/速度和该运动模式恢复所需的参数与阶段。若复用已同步参数，必须明确如何保证这些参数和恢复样本一致；单独设置位置不构成完整重建。

完整轨道 ID/索引分发、共享时钟漂移校准和事件重放仍属于后续变更。第一阶段的恢复数据也不能被解释为已经具备这些能力。

实现前必须确定初始化、失步后获取恢复数据的具体路径，以及等待期间的有限表现策略、超时处理和请求合并/限频。不得依赖尚未实现的未来快照，也不得通过本地销毁服务器仍存活的弹幕来掩盖失步。

应用恢复数据时，在同一个客户端更新边界原子建立模拟状态和年龄锚点，清理旧样本、追赶速度及几何缓存，再重新建立渲染基准。网络往返期间的数据陈旧性必须显式处理，不宣称收到恢复样本就等于获得服务器当前时刻的状态。

### 7. 渲染接入必须覆盖实体分发与独立 tick 路径

renderer 的局部几何变换之外，还必须审计原版实体渲染分发器的世界坐标插值，避免只改局部几何却保留原始实体坐标平移。渲染包围盒与逻辑碰撞箱分开管理，不能为了视锥剔除改写玩法碰撞箱。

`LaserDanmaku.tick()` 不调用基类弹幕 tick，状态生命周期更新不能只挂在基类 tick 中。激光服务端判伤使用的起点/长度与客户端视觉起点/裁剪缓存也必须明确分开，禁止把共用 `getActualLength()` 的权威输入替换成渲染输入。

## Risks / Trade-offs

- [Risk] renderer 与实体原版插值叠加造成双重平滑。→ 明确渲染状态的 old/current 值并审计 `partialTick` 使用，只保留一层插值。
- [Risk] 样本超界后没有及时重建会造成短暂错位。→ 设置最大等待窗口和失步诊断，超时请求/等待快照。
- [Risk] 激光包围盒使用渲染位置后可能改变视锥剔除结果。→ 包围盒按当前渲染起点和最大几何长度构建，并增加长激光测试。
- [Risk] 旧代码直接调用 `position()`。→ 逐个审计弹幕相关 renderer 和视觉逻辑，统一替换访问点。

## Migration Plan

1. 增加客户端状态容器和纯函数追赶器，不改变网络行为。
2. 让 `lerpTo` 写入权威样本，暂时保留兼容模式诊断。
3. 迁移 renderer、激光裁剪和包围盒到统一渲染状态。
4. 接入实体级最小初始化/重建数据、获取路径和缓存清理，验证失步到恢复的闭环。
5. 在轨道同步变更中将 `LEGACY_POSITION` 替换为时间轴/关键帧模式。

## Open Questions

- 失步重建应由同一实体重置，还是销毁并等待新的实体/轨道快照？
- 渲染追赶的最大速度是否按弹幕速度分档，还是使用统一的视觉上限？
- 客户端暂停后恢复时，是否立即跳到最新渲染状态，还是限制恢复追赶时间？
- 最小重建数据采用何种 payload、身份/版本字段，以及如何与现有 `SynchedEntityData` 保证一致采样？
- 初始化与失步恢复分别采用主动推送还是按需请求？如何合并密集弹幕的恢复请求，并定义等待/超时行为？
- 无服务器采样时间的 `LEGACY_POSITION` 样本如何定义可信性和有限渲染目标？不能直接将陈旧坐标当成当前目标，也不能仅凭位置相同判定重复包。
- 追赶上限如何约束额外纠偏而非弹幕自身运动，避免高速弹永远追不上？没有可信时间映射时，“最大相位”如何度量？
