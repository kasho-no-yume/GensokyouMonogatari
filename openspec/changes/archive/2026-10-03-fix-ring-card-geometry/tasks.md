      因比名字而恒不成立的旧代码成立（见 `BigFairyEntity:199-202`）。

## 3. lint 判据复核（需要判定，不是机械修改）

- [x] 3.1 跑 `TrackLint` 对 `count=48` 的判定，记录它是否被拒以及**理由**。
      **验收**：无论结论如何，MUST 写进 `danmaku-track-composition` spec，
      MUST NOT 只留在 lint 代码里。 ✔
      **实测**：被拒，原文「违反 R1 前向威胁——侧挂圆盘单拍排满且未留缺口（gapDeg=0）」。
      结论已写入 spec 的 `幕墙判据 SHALL 以可读性而非形状身份判定`。
- [x] 3.2 判定「单拍铺满一面墙」与「单拍铺满 + 静止等待期」是否应分别对待。
      参照量：环卡声明了 `harmlessTicks = 60`（3 秒无害期），
      而既有 lint 用例 `count=12` 没有声明无害期且 `speed > 0`。
      **验收**：若判定为分别对待，MUST 新增一条可区分二者的判据
      （例如「声明了无害窗口的单拍铺满不算幕墙」），并为该判据写正反两向测试。 ✔
      **判定：分别对待。** 理由：
      1. R1 针对的是「不可读」的墙，而可读性来自**时间窗**。静止三秒的闭合圆盘是预告。
      2. 既有 lint 用例是「瞬间铺满并立刻流动」，那才是没有观察余量的那种。
      3. R2 已通过 `Shape.guaranteesGap` 把 `DISC_RING` 视为三维有解，R1 不查该方法是矛盾而非深意。
      **判据用运动类型 `RECLAIM`（先停住、到 `atAge` 才启动）而非 `harmlessTicks`** ——
      无害只说明不掉血，不说明不动；一批在无害期仍在飞向玩家的闭合墙仍然是墙。
      **正反两向测试**：`discRingThatParksBeforeFiringIsNotAWall`（正向）、
      `harmlessWindowAloneDoesNotExcuseAFlowingRing`（反向：只有无害期仍在流动 ⇒ 仍拒）、
      `parkingExemptionDoesNotGeneraliseToOtherMotionKinds`（反向：例外不扩大到 `HOVER`，
      防止有人把 R1 改成「`DISC_RING` 一律放行」而让既有判据变成空断言）。
- [x] 3.3 若判定为「同样对待」：MUST **停下来找用户确认**，
      因为修法是让环卡留 gap（环变 C 形），那是内容变更而非缺陷修复。
      **验收**：本任务在未获确认前 MUST NOT 被标记完成。 ✔ **不适用** ——
      3.2 判定为「分别对待」，故走的是加判据这条路，环的玩法数值一字未改。
      若日后改判为「同样对待」，则 MUST 停下找用户确认。
