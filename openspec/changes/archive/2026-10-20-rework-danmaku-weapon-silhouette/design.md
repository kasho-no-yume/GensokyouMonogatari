# Design: rework-danmaku-weapon-silhouette

## Context

本变更承接 `rework-danmaku-weapon-orb`（已归档）的成果并推翻它的两条核心假设。

上一轮把主武器从「符星铳」改成了「千机核心」球形外壳，并确立了三条规则：
① 外壳形态随 slot1 所装弹核变化；② 壳色取 `TierPalette` 品阶色；③ 动态化只在品阶色 ±30° 内摆动。

实现落地后发现三条都没达到预期效果，且根因各不相同。

### 事实一：发白是**算术溢出**，不是审美问题

现渲染器 5 层，4 层加法混合，且 4 层**全都携带同一个饱和品阶色**（`CoreOrbRenderer#renderByItem`）：

```
① 内层壳   additiveGlow    α=60    品阶色 × 1.35
② 焦点核   additiveGlow    α=235   品阶色
③ 外  壳   entityTranslucent α=205  品阶色          ← 唯一 alpha 混合层
④ 外  晕   additiveGlow    α=70~110 品阶色
⑤ 环绕环   additiveGlow    α=150   品阶色
```

亮度调制走的是 RGB 乘法 + 逐通道截顶（`CoreOrbRenderer#vertex`）：

```java
float band = 1.0F + flowScale * 0.42F * sin(...);
consumer.addVertex(...).setColor(Math.min(255, (int)(r*band)), ...);
```

代入阶 1 绿 `#4CAF50` (76,175,80)：

| 步骤 | R | G | B | 发生了什么 |
|---|---|---|---|---|
| 品阶色 | 76 | 175 | 80 | |
| × band 1.567（内层壳 flowScale 1.35） | 119 | **274→255** | 125 | **主通道被截顶 → 色相自己漂移、饱和度塌掉** |
| × 贴图灰度 140~255 | | | | 贴图**零色相信息**（`core_orb.py` 明确"MUST 保持中性灰"） |
| ①+②+④ 加法求和 | ~160 | **364→255** | ~168 | **再次截顶** |

结果 `(160, 255, 168)` = 发白薄荷绿。阶 3 金 `#FFC107` 更惨：band 一步就把 R(399)、G(302) **双双截顶**，加法再截 → `(255, 255, 12)` 黄白。

**结论：只要保留"多层加法叠同一个饱和色 + RGB 侧乘法截顶"这套算法，任何品阶色都会被洗成白色。** 这不是调参能救的。

### 事实二：`band` 只调亮度，**色相从不流动**

`band` 是 RGB 的**等比缩放**——R/G/B 同时乘同一个系数。后果有两个：
- 亮度调制**不改变色相**，所以"流光"读出来是"一片颜色上打明暗"，不是"色彩在流"；
- 等比缩放 + 逐通道截顶 = **色相随亮度漂移**（绿通道先撞顶 → 绿变青绿）。

### 事实三：焦点核读不出武器

外壳实心（α=205）、焦点核埋在球心且只占视高 40%：

| 核 | 现有焦点核 | 玩家读到的 |
|---|---|---|
| 飞刀 | **一片**平面刀身（`standingBlade`） | 一根线 |
| 激光 | 0.11 半径小棱镜 | 一个点 |
| 单发玉 | 0.16 半径小球 | 一个点 |

「外形随核变化」是上一轮变更的**核心诉求**，但它在用户最在意的三对核上全部失效。

### 事实四：空槽是**初始形态**，却是最灰的那个

玩家拿到武器时看到的就是空核心态。现在它是 `EMPTY_COLOR = 0x8A90A4`（灰蓝）的小球——**最灰、最小、最没表现力**。而空核心恰恰是整件物品的"未装配"叙事核心。

### 事实五：品阶只随装入的核而来

**空核心没有品阶。** `TierPalette.rgb(tier)` 只在装入弹核后才存在（tier 取自核的 `requiredTier`）。因此"空核做全色相流光"**不与品阶色环冲突**——品阶色环约束的是「品阶化资产」，空核心不是品阶化资产。

`openspec/project.md` §5.4 现行措辞把"球形核心"直接举名为动态化资产并锁死 ±30°，这条需要一条**例外**，而不是整体推翻。

### 事实六：上一轮的「MUST NOT 呈枪形轮廓」条款，其本意不是"不许有枪"

`weapon-gui-visual` 的「图标可辨识」场景写的是 "MUST NOT 呈枪形轮廓"，其上下文是"图标呈球形核心轮廓，与'封装一枚弹幕核'的用途相符"。它的本意是**防止回归成旧「符星铳」那一把固定的枪**（上一轮变更的 Why 第一条就是"形象与系统结构不匹配"）。

新诉求"飞刀武器放 3 把飞刀、激光武器放个高科技激光枪"与那个本意**并不矛盾**——它要的是**外形随核变化**，而不是"永远保持球形"。

## Goals / Non-Goals

**Goals**

- 空核心态（未装核）呈现**全彩流光球 + 火冠气焰**，且**不出现任何发白**
- 装核态的外壳**直接变成该核种类对应的武器轮廓**（飞刀 = 3 把飞刀、激光 = 高科技激光枪）
- 消除 RGB 侧乘法截顶导致的**色相漂移与发白**（结构性解决，不是调参）
- 气焰的归属明确：**只属于未装核态**；装核后各武器形态自带辉光/轨迹
- 形态映射以 `DanmakuKind` 为准（LASER 暂不拆机枪/炮）

**Non-Goals**

- 不改任何玩法数值（伤害、射速、耗灵、射程、命中判定）
- 不改存档格式、不新增网络包、不新增配置键
- 不改弹幕本体的渲染（`AbstractDanmakuRenderer` 一族）
- 不改装配台 GUI 的槽位布局（弹核槽仍在球心）——**球心槽的叙事与新形态兼容**：装配台画的是**未装配核心的剖面**，装上核后核心才显形
- 本轮**不拆分**激光机枪 / 激光炮的外壳档案
- 不引入自定义 shader / 粒子系统（保持"纯 quad + 顶点色"的技术栈）

## Decisions

### D1：形态二分 —— **沉睡态**（未装核） / **显形态**（装核）

**选**：把主武器的视觉拆成两个互斥形态，由 slot1 是否为空决定。

```
        装 核 前                          装 核 后
   ┌────────────────────┐          ┌────────────────────┐
   │      ▲ ▲ ▲          │          │                    │
   │    ╱ ▲▲▲ ╲         │          │   ▤ 该核的武器轮廓   │
   │   │  ◉  ◉  │ ←暗腔  │  ────▶  │   ◈ 核自带的焦点光   │
   │   │ ◍◍◍◍◍  │        │          │   ↝ 核自带的轨迹      │
   │    ╲ ◍◍◍ ╱         │          │                    │
   │   ▲╱     ╲▲ ←火冠  │          │                    │
   │    ╰─────╯         │          │                    │
   └────────────────────┘          └────────────────────┘
    品阶：无                           品阶：核的 tier
    色相：全光谱流光                    色相：品阶色 ±30°
    气焰：火冠                          气焰：无
```

**理由**：这个二分不是"两套外观"，而是**同一件东西的两个状态**——「核心在沉睡 / 核被装入、核心显形」。它同时解决了三件事：

1. 给空核心态一个**有表现力的初始形态**（玩家拿到武器时的第一印象）；
2. 把"装核"变成一次**可见的形变**（升级反馈曲线：沉睡的混沌彩虹 → 装核后的专精单色 + 武器形态）；
3. 让"全彩流光"有了**合法的归属地**（空核无品阶，见 D4）。

**替代方案（已否决）**：*所有形态都带全彩流光*。装核后彩虹色会与品阶色打架，且品阶不可辨——正是 §5.4 要防的事。

### D2：装核态外壳 = **武器轮廓本身**（不是"容器里装着武器"）

**选**：外壳的几何**就是**该核对应的武器形状，不再是"装着武器的球壳"。

**理由**：用户诉求的原话是"飞刀武器放 3 把飞刀，激光武器放个高科技激光枪"——**"放"** 的落点由 D1 已定（放进球里的"球"= 空核沉睡态），而装核态则直接长成武器。若保留"球壳包着武器"，武器只占视高 40%，等于回到事实三的老问题。

**代价**：推翻 `weapon-gui-visual` 的「MUST NOT 呈枪形轮廓」场景。**这是有意为之**（见事实六），需在 spec delta 中显式改写，并在 release notes 中说明。

**替代方案（已否决）**：*保留球壳 + 放大焦点核到 60%*。改动小，但"球里装着把枪"仍然读作"球"——玩家依旧第一眼看到的是球，不是武器。

### D3：色彩合成改为 **HSV 空间** + **加法预算**

**选**：两条结构性规则，取代现有"调 band / 调 alpha"的调参路线。

**R1｜加法预算（防溢出）**

```
任一像素上：  本体层峰值 ≤ 0.62 (158/255)
            + 所有加法层贡献之和 ≤ 85/通道
            ────────────────────────────────────────
              合计 ≤ 243/255   →   结构上不可能截顶
```

**R2｜HSV 空间合成（防色相漂移）**

色相与亮度调制 MUST 在 HSV 空间做，**MUST NOT** 用 RGB 乘法 + 逐通道 clamp。

```
现在（错）：  RGB 乘法 → clamp     → 主通道截顶 → 色相漂移 → 发白
改后（对）：  HSV 空间合成           → 色相连续流动 → 饱和度不掉 → 彩
```

现有 `faceColor()` 已经走 `Color.RGBtoHSB` → `HSBtoRGB`，方向是对的；**错的是 `band` 的乘法在 RGB 侧做**（`vertex()` 里 `r*band`）。本变更把亮度调制搬进 HSV 侧（改 `bri` 而非改 RGB），并把色相偏移交给 `hue`。

**理由**：R1 与 R2 缺一不可。R1 单独用 → 亮度不漂但流光只读作明暗；R2 单独用 → 色相会漂但不会溢出。**两者合起来才是"全彩流光"**。

**R1 的关键性质：它与渲染顺序无关。** 加法层无论画在本体之前还是之后，合计上限都成立——这消除了"必须搞清 `entityTranslucent` 与自建 `additiveGlow` 在同一 framebuffer 里的提交次序"这个脆弱前提。

### D4：空核态**不受品阶色环约束**

**选**：`openspec/project.md` §5.4 补一条例外：

> **未装配形态（无品阶归属）SHALL NOT 受品阶配色环约束**，MUST 使用全光谱流光；
> 一旦装入弹核，MUST 立即回到该核品阶色 ±30° 区间。

**理由**：品阶色环的立意是"玩家能从颜色读出阶位"。**空核没有阶位**，对它套品阶色是空转——现在给的就是 `EMPTY_COLOR = 0x8A90A4` 灰蓝，既不传达信息，又让初始形态最没表现力。装核后立刻回到品阶色，**可辨性一点没损失**。

**改的是 §5.4 的适用边界，不是它的精神**（"色相唯一来源是 `TierPalette`"仍然成立——装核态的品阶色仍只有 `TierPalette` 一个出处）。

### D5：加法层**色相分工**

**选**：**同一个色相 MUST NOT 被两个加法层同时持有。**

| 层 | 混合 | 色相 |
|---|---|---|
| 本体（品阶色 / 空核彩虹） | alpha | **独占** |
| 内部翻涌 | additive | 本体的**互补色** |
| 外晕 | additive | 本体的互补色（更暗） |
| 气焰 | additive | **暖色**（根部随流光，尖端偏白） |
| 环绕环（等级） | additive | 白金 |
| 色散薄边 | **本体内** | 轮廓处 ±40° |

**理由**："全彩"由**层间色相分离**达成，而不是全色相循环。层间分离既拿到了多色相同框的观感，又让品阶色（本体层）始终独占、始终可读。这条也解释了 D4 为什么可以成立——**品阶色没被稀释，因为它只在一层里。**

**色散为什么不做成加法层**：三通道同加 = 白边。棱镜色散 MUST 做进**本体层的色相**里（轮廓处把色相拆开 ±40°），代价为零、不占预算。

### D6：火冠气焰**只属于未装核态**

**选**：`EMPTY` 态专属。装核态的武器轮廓**自带**辉光/轨迹（飞刀的拖痕、激光的驻轴光轴、符纸的金色符文流），**MUST NOT** 另加气焰。

**理由**：用户明确"只有没装弹幕核的武器核心才有气焰"。且这在语义上自洽——**气焰是"未装配"的生命力表现**，武器形态一旦显形，气焰就转化为武器自身的能量表现。两套表现同时出现会互相稀释。

**火冠的具体形态**：8~12 条火舌，每条 2~3 个 quad，沿 +Y 立起、尖端收成点；每条有独立相位（不同步地舔）+ 轻微方位角摆动（摇曳）。**火舌根部颜色取其下方球面的流光色**——气焰与球面永远同色系，不会割裂。

### D7：形态映射以 `DanmakuKind` 为准，SPHERE 保留覆盖

**选**：

| `DanmakuKind` | 档案 | 形态 |
|---|---|---|
| —（未装核） | `DREAM` | 全彩流光球 + 火冠 |
| `CONE` | `DART` | 三枚锥矢斜向前一字排开 |
| `SPHERE` | `BALL` | 一颗饱满大玉球 |
| `SPHERE`（覆盖） | `SCATTER` | 五颗小珠呈扇形散开 |
| `KNIFE` | `BLADES` | 3 把飞刀（品字：1 前 2 后） |
| `TALISMAN` | `PAPER` | 方形符纸，四角封印钉 + 中央朱印 |
| `LASER` | `GUN` | 高科技激光枪 |

**SPHERE 必须两分**：`weapon-gui-visual` 的「同种不同形」场景是硬条款（单发玉 = 重炮大玉 vs 散弹玉 = 五瓣散珠），沿用既有"核覆盖档案"机制（`BulletCoreItem` 持 shell id），不新增机制。

**LASER 暂不拆**：用户决定"目前只需要对齐各自的核种类就好"。激光机枪（tier 2）与激光炮（tier 3）共用一个档案——**已知取舍**：两者在物品栏里长得一样，只能靠品阶色（蓝 vs 金）区分。列入 Open Questions。

**"三把飞刀"的具体构图**：品字形（1 前 2 后），而非现在的"2 片交叉刃 + 1 片竖刀身"。三把都带完整的 3D 刃形（有刃口高光面 + 有厚度的刃背），而不是一片平面。刃尖统一朝外（= 穿透方向）。

### D8：球心暗腔承担**三重语义**

**选**：空核球心保留一圈**反向旋转的暗色涡旋**（不是纯黑孔）。

```
① 保留"未装核"的可读性 —— 满足 weapon-gui-visual「空槽见空腔」场景
② 天然的视觉焦点 —— 气焰的根部正好从这里起
③ "在等待被填入"的呼吸感 —— 反向旋转
```

**理由**：纯彩虹球若没有暗腔，会完全丢掉"这是空的"这一信息。而现在的实现里，空槽只有一颗灰蓝小球 + 空的几何，信息同样很弱。暗腔把两者结合起来。

### D9：几何缓存策略不变，但缓存键换档案

沿用上一轮的"静态几何按档案 id 缓存"（`SHELL_CACHE` / `GLYPH_CACHE` 两个 `EnumMap`）。新形态下：

- **轮廓几何**（武器外形、飞刀、符纸、激光枪）—— 静态，按档案 id 缓存；
- **火冠** —— 顶点位置随时间变（相位/摆动），但**拓扑与相对形状不变**，故仍可缓存"单位形状"，逐帧只改顶点变换与颜色；
- **焦点核** —— 各武器自带，静态缓存。

**代价**：火焰的逐帧顶点更新比球面稍贵，但火焰 quad 数量级（~10 条 × 3 quad = 30 quad）远低于球面（~120 quad），不构成问题。

### D10：静态兜底图标与新形态一致

`textures/item/danmaku_weapon.png` 当前画的是一枚紫灰色素球，是**动态渲染器的静态兜底**（particle 贴图 / 资源包缺失时用）。它 MUST 与新的空核沉睡态一致（彩虹球 + 火冠的剪影），否则动态渲染失败时会看到一个与设计不符的紫灰球。

**用 `tools/gen_tex.py` 的 ASCII 流程重画**（`tools/textures/core_orb.py`），MUST NOT 用逐像素坐标循环脚本。

## Risks / Trade-offs

**[加法层与本体层的提交次序未知]** → `entityTranslucent` 与自建 `additiveGlow` 在同一 framebuffer 里的先后由 `RenderType` 的 bucket 决定，不由调用顺序决定。**R1 加法预算与次序无关**（合计上限恒成立），故不构成风险；但**必须实跑确认各层的实际观感**（某些次序下加法层会被本体 alpha 吃掉，表现为"太暗"），必要时调各层 alpha 而**不是**放宽预算。

**[16px 物品格里武器轮廓读不出来]** → 激光枪尤其危险（细长 + 多零件）。缓解：① 每个轮廓必须提炼出**一个**最小识别特征（激光枪 = 枪口一点白光 + 机匣上的发光带；飞刀 = 三条锐利剪影）；② 提供静态兜底图标（§D10）；③ **必须实跑在物品栏 + 手持两种上下文里验证**——手持时物品被放大，可读性远好于物品栏。

**[装配台 GUI 的"球心即弹核槽"与新形态语义冲突]** → 装配台画的是**未装配核心的剖面**（球 + 中心空腔 + 装入的核），装上核后核心才显形——**叙事自洽**，故不改 GUI 布局。但需在 spec 中把这条语义写明，避免后人误改。

**[LASER 两核共用档案]** → 激光机枪（tier 2）与激光炮（tier 3）在物品栏里长得一样，只能靠品阶色（蓝 / 金）区分。**已知取舍**（用户拍板"先对齐核种类"），列入 Open Questions，不在本变更解决。

**[推翻「MUST NOT 呈枪形轮廓」引发规格争议]** → 该条款的本意是防回归旧枪（事实六），不是"不许有枪"。必须在 spec delta 中**显式改写条款本身**（而非悄悄绕过），并在 release notes 中写明"这是有意的条款推翻，理由是外形随核变化是更强的诉求"。

**[全彩流光可能与"品阶可辨"的用户心智冲突]** → 玩家若在**空核态**看到彩虹，会不会误以为"彩虹 = 高阶"？缓解：空核态**没有任何核**，玩家无从对比；且彩虹只出现在"还没装核"的那一刻。装核后立刻变成单一品阶色，反差本身就是"专精"的表达。

**[空核态全彩流光在暗背景下过曝]** → 暗背景下加法层会显得比亮背景下强。R1 的 85/通道上限正是为此留的余量；若实跑仍过曝，调各层 alpha 而不放宽预算。

## Migration Plan

无存档格式变更、无配置键变更、无网络包新增。**全部为纯客户端表现，MUST NOT 参与任何玩法判定**（沿用上一轮已确立的约束）。

- **武器与核的 NBT 结构不变**（`weapon_slots` 三槽快照），老存档的装配配置继续可读。
- **几何档案 id 变化**：`CoreShellProfile` 枚举项重命名/重定义。**已核实**该档案是 `BulletCoreItem` 上的 `private final CoreShellProfile shell` ——**编译期常量，不落 NBT**（`shell()` 直接返回该字段），故老存档无兼容问题，枚举更名不影响任何存量数据。
- **`tools/textures/core_orb.py` 与 `textures/item/core_orb_shell.png`**：贴图仍 MUST 为**灰度乘法遮罩**，MUST NOT 烘焙色相（色相全在渲染层）。渐变方向可能需按新几何重排。


## 实施阶段的修正（落地后回填）

本节记录**实施中发现并修正**的决策——它们推翻了上文的部分设想，故 MUST NOT 只读上文。

### E1：几何从渲染器里拆出来（`CoreOrbGeometry`）

**原设想**：几何与着色同在 `CoreOrbRenderer`。

**落地问题**：`CoreOrbRenderer` 继承 `BlockEntityWithoutLevelRenderer`，加载它会连带初始化原版
`Blocks`（静态初始化读方块属性）→ 单测环境抛 "Not bootstrapped"；而 NeoForge 的
`Bootstrap.bootStrap()` 又需要 FML 的 mod 列表（`LoadingModList.get()` 为 null）→ 单测里也无解。

**修正**：几何抽到 `CoreOrbGeometry`（纯向量运算，只依赖 `Vec3`），着色口径抽到
`CoreOrbPalette`（只依赖 `java.awt.Color`）。两者都不碰客户端类，于是：

- 轮廓形状可以被**离线光栅预览**并断言（`CoreOrbPreviewTest` → `build/preview/core_orb_*.png`）；
- "七个档案的剪影真的各不相同"从"只能靠实机眼睛"变成**机器可验证**。

### E2：能量件与火冠改为**实体层**，不是加法层

**原设想**：能量件 / 火冠走加法，靠"加法预算"控制亮度。

**落地问题**：加法层的贡献被预算压到 20~30/255，即背景上的 **8%~12% 亮度**——火焰与拖尾
**根本看不见**（第一版预览里火冠是深褐色的，几乎与背景同色）。

**修正**：绘制层按**职责**分混合方式：

| 层 | 混合 | 理由 |
|---|---|---|
| 本体 / 能量件 / 火冠 | **alpha** | 它们是"实体"（轮廓上的零件、火焰）。加法叠出来的实体在通道预算下必然发暗 |
| 外晕 / 环绕环 | **加法** | 它们是"薄的一层光"，加法才对 |

于是加法预算腾出来了：外晕 46 + 环绕环 22 = 68 ≤ 85，比原来宽裕得多，
**而火冠 / 拖尾 / 光轴全部变成看得见的实体**。

**连带**：R3 的措辞从"品阶色只由本体层持有"改为"品阶色的**纯本色**只由本体层持有；
能量件 MAY 用其高亮变体"。

### E3：逐面虹彩微偏 MUST 以扇区**中心**为基准

**落地问题**：`face` 原本直接存扇区序号，着色时按 `(face - 1.5)` 偏移。24 扇区下
偏移范围变成 −9° ~ +129°——球体直接变成品阶外的杂色（预览里下半个球是紫的）。

**修正**：`face` 存"扇区序号相对中心的偏移"，微偏系数降到 0.5°/格，总偏移落在 ±6° 内。

### E4：能量纬线 MUST 绕**模型的 X 轴**成环

**落地问题**：`latticeBand` 原本绕 Z 轴成环，而模型的 Z 轴在屏幕上指向右（长轴）——
侧视下绕 Z 的环退化成**一条竖线**（第一版预览里球上确实只有一条竖线）。

**修正**：纬线改绕 X 轴（= 屏幕深度轴），侧视下才是一圈。

### E5：挤出体的端面扇形三角形 MUST NOT 各带不同 `face`

**落地问题**：`extrude` 的端面用扇形三角化，每个三角形原本带着自己的 `face`（= 轮廓边序号），
于是相邻三角形在接缝处跳一个色相——符纸上出现一片**斜纹**。

**修正**：端面三角形的 `face` 恒为 0（逐面微偏本就是给"旋转体的角向面"用的）。

### E6：枪身 MUST 拆成若干块

**落地问题**：一整块多边形轮廓在 16px 物品格里读作"一根长板"（第一版预览就是一根斜楔子）。
自交检查虽然通过，但**可读性**不成立。

**修正**：拆成枪管 / 消焰器 / 机匣 / 枪托 / 握把 / 散热鳍若干块，各块轮廓在小尺寸下都在。

### E7：兜底图标被旧工具抢占

`tools/textures/danmaku_weapon.py`（旧「符星铳」枪形图标工具）与 `core_orb.py` 都写
`item/danmaku_weapon`，按文件名顺序后者后跑 → **兜底图标一直是旧枪**。
已删除前者（上一轮变更清 `danmaku_weapon1.png` 时漏了工具侧）。

### E8：VertexConsumer MUST NOT 跨 `getBuffer` 调用持有（实机崩溃）

**现象**：物品栏 / 快捷栏里带着「千机核心」就必崩。
`IllegalStateException: Not building!`，栈在 `CoreOrbRenderer.vertex → BufferBuilder.addVertex`，
触发点是**外晕层**（本体层先画，正常；外晕层拿到的 consumer 已经失效）。

**根因**：1.21.1 的 `MultiBufferSource.BufferSource#getBuffer` 里——

```
ByteBufferBuilder bytebufferbuilder = this.fixedBuffers.get(renderType);
if (bytebufferbuilder != null) {
    bufferbuilder = new BufferBuilder(bytebufferbuilder, ...);        // 独占缓冲，不顶别人
} else {
    if (this.lastSharedType != null) {
        this.endBatch(this.lastSharedType);                          // ← 把上一个共享者 endBatch 掉
    }
    bufferbuilder = new BufferBuilder(this.sharedBuffer, ...);
    this.lastSharedType = renderType;
}
```

共享缓冲只有一个。某个 RenderType **首次**占用它时，上一个占用者会被 `endBatch`——
`BufferBuilder.building` 置 `false`，之后往那个 consumer 写顶点就抛 "Not building!"。

本实现把两个 `getBuffer`（加法辉光 / 半透明本体）提到方法开头再依次写入，
于是**第二个 `getBuffer` 把第一个顶掉了**——本体层因为拿到的是后取的那个所以正常，
外晕层回头写先取的那个就炸。

**修正**：**取缓冲与写入 MUST 绑在一起**（取 → 写 → 取 → 写）。仓内其余渲染器
（`CrystalRenderer` / `RitualCoreRenderer` / …）一直是这个形状，所以它们没事。

**结构性保证**：新增 `emitTo` / `emitFlameTo`，把"取缓冲 + 写入"并成一个方法，
调用方拿不到 `VertexConsumer`，也就无从跨 `getBuffer` 传下去。
另有 `CoreOrbBufferStructureTest` 守住这条结构。

> **这条契约无法写成单测**：验证它需要真实构造 `RenderType`，而 `RenderType` 的静态初始化
> 会连带初始化原版注册表（`BuiltInRegistries → Blocks → SoundType → SoundEvents`），
> 单测环境没有原版引导就抛 "Not bootstrapped"；NeoForge 的 `Bootstrap.bootStrap()`
> 又需要 FML 的 mod 列表（`LoadingModList.get()` 为 null），同样不可用。
> **真正的验证在实机**：载入带该物品的存档，看日志。
