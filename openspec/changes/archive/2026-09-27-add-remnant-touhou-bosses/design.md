## Context

召唤侧基础设施已交付（`add-hyakki-yagyo-summon-ritual`）：`hyakki_yagyo_circle` 三阶仪式、祭品化召唤会话、充能/爆散/降临演出、咒符条血条，以及留作挂钩点的 `effect` 字段（当前填的是占位值 `hyakki:balance_test_boss`）。

本变更只负责**被召唤出来的东西**。三块既有积木需要评估可用性：

| 需要的能力 | 现状 | 判断 |
|---|---|---|
| 弹幕弹种 | `AbstractDanmakuProjectile` 四个子类（球/刀/符/激光），支持匀速/追踪/激光三种运动状态 | **需扩展**：无曲射、无分裂、无悬停、无溜め |
| 弹幕编排 | `TestBossPattern` 是 `enum` + `switch`，硬编在 `BalanceTestBossEntity` 上；玩家侧的 `FirePattern` 是**单发描述符**，无法表达多拍序列 | **需新建**：两者都不能表达"并发轨道" |
| BOSS 血条 | `entity.TouhouBoss` 空标记接口 + `TouhouBossBarRenderer`（common 侧接口，客户端订阅 `CustomizeGuiOverlayEvent.BossEventProgress`） | **白捡**：实现接口即得咒符条 |
| 玩家受击管线 | `DamageEventHandler`：擦弹 → 指数减免 `2^-P` → 护盾系数；`TouhouCombatEvents`：90% 非弹幕抗性 | **沿用**：BOSS 弹伤预算按此反推 |

关键约束：`Projectile` 无重力（`AbstractDanmakuProjectile` 直接继承 `Projectile` 而非 `ThrowableProjectile`，为绕开 0.99 空气阻力），故"悬停"不需要对抗重力，只需清零速度。

## Goals / Non-Goals

**Goals**

- 轨道/节拍编排模型：符卡 = 阶段 = 1~3 条并发轨道，每轨 = 节拍时间轴
- 三维可读性契约 R1/R2/R3 可判定，并派生"每轨一种独占视觉标识"
- 四种新增弹幕行为以 flag 形态落在既有基类上
- 共用 BOSS 基类：符卡阶段切分、距离带移动策略、≤5 多目标、掉落钩子、HP 分档
- 数值从"倍带"改为"秒带"，并修 `referencePlayerEhp` 的 cap 缺陷
- 残影的占位渲染可零成本替换为正式模型（`project.md` §5.2）

**Non-Goals**

- 百鬼夜行配方条目、`effect` 字段填写、台位分档
- 玩家神恩门槛（`minPlayerTier` 泛化）
- 祭坛阶数可达性、`ritual_stone_2/3` 配方
- **符卡名在血条上的显示**——咒符条当前**不绘制原版名文本**（`D10` 的事件取消同时跳过原版名），显示符卡名需改 `TouhouBossBarRenderer`，属隔壁文件
- 整颗符卡星用途、円经济、物品经济纵深

## Decisions

### D1 — 轨道与节拍用 Java 记录 + builder，不用 JSON

**选择**：Java record 定义几何，builder 组装成轨道，boss 持有一个按阶段分组的轨道表；**标量走 config**。

**理由**：与玩家侧 `FirePattern`（record + `Supplier` 标量）同构，几何最终要调 `AbstractDanmakuProjectile` 的构造与运动方法，JSON 只会把这段逻辑挪到 loader 里再加一层校验。约 28 条轨道（4 boss × 3~5 符卡 × 1~3 轨）由类型系统兜住，测试可直接构造。

**代价**：内容改动要碰 Java，不能纯数据热更。**否决**——为 28 条轨道引入一个几何 DSL loader 的校验与报错面不划算；真到轨道数上百再抽数据层。

### D2 — 四种新弹幕行为做成基类 flag，不做新实体类型

**选择**：`AbstractDanmakuProjectile` 增一个同步字节存行为 flag（曲射/分裂/悬停/溜め 各一位）、一个同步 int 存参数（曲射轴用欧拉角编码、悬停 tick、分裂数、溜め半径）。

**理由**：新实体类型 = 注册表项 + `EntityType` + 渲染器 + model JSON + lang 键 + 生成管线，四份成本乘以四。flag 落在既有基类上则四份成本只付一次。

**关键约束**：该基类文档明确"渲染与运动学所需的数据全部通过 `SynchedEntityData` 下发，客户端与服务端各自按相同规则推进"。**新行为必须两端同规则**，故 flag 与参数都要同步，不能只走服务端。

### D3 — 悬停 = 到达 tick 后速度归零，不加反向力

**选择**：`hoverTicks > 0` 时，弹在 `lifetime - hoverTicks` 那一 tick 把 `deltaMovement` 清零并停止推进；`hasPhysics` 保持关闭，命中判定与存活不变。

**理由**：`Projectile` 本就无重力，"定住"不需要对抗任何力，只需要停止积分。清零速度比反向力稳定（不会漂移、不会因浮点误差缓慢滑走）。

**连带**：悬停弹必须仍然造成伤害——它是**幕**的组成部分（东方「幕張る」弹幕的三维版：静止弹幕织成一道可穿越的幕墙），不是纯特效。故不清除 hitbox、不改 `isAlive`。

### D4 — HP 超 1024 复用伤害除数，符卡不做独立血池

**选择**：`MAX_HEALTH` 钳到 1024，超出部分以伤害除数实现（`有效HP = 实际HP × 除数`，`BalanceTestBossEntity.java:66-97` 已有先例）。**符卡只是一组"名称 + 血量阈值 + 轨道表"，不是独立 HP 池**；血条读 `LerpingBossEvent.getProgress()`，因为 `health/maxHealth` 随除数同步缩放，比例天然正确。

**理由**：傩神楽面按 T2/110s 需 18 600 有效 HP，若按"每符卡 ≤1024"分池则五张上限仅 5 120，装不下。伤害除数是既有且已验证的路径，符卡分段只解决"何时切阶段"与"叫什么"。

**代价**：符卡名无处显示（Non-Goal）。

### D5 — 移动：距离带 + 自由游走，非环绕

**选择**：默认策略每 tick 检查到主目标的距离——低于 `min` 后退、高于 `max` 前进、其间朝"当前游走目标点"平滑转向；游走目标点每 3~6 秒在环带球面上重选，排除墙内、离任一玩家过近、以及祭坛过近的点；选不出点则退化为即时横移。Y 分量独立向"垂直偏好"靠拢。

**覆写面**（每只 boss 可改）：`[min, max]` 距离带、移速、垂直偏好（等高/偏高/偏低）、游走点重选间隔、是否允许闪现重定位。

**理由**：需求是"保持距离、上下左右都会动"，不是绕圈。自由游走让**弹幕出发点每发都在变**——玩家无法背角度记死——这比任何增加弹量的手段都更有效地压制"站桩输出"。

**否决**：*固定角速度环绕*——一个可解的站位就废掉整场战斗。*`FlyingMoveControl`*——`FairyMoveControl` 文档已说明其在 `FlyingMob` 上失效。大妖精现挂的 `HoverAboveTargetGoal`（悬停头顶）要换掉。

### D6 — 只有瞄准型轨道随人数复制

**选择**：目标集合取距 boss 最近的 ≤5 名玩家，主目标为其中最近者。轨道节拍的"目标模式"分两类：

- `AIMED`（锁人）——**对每名目标各生成一份**，5 人 = 5 份
- `SELF_AXIS` / `ARENA`（自轴/场地）——**只生成一份**

boss bar 全体加入；闪现只对主目标；破盾按玩家各自结算（`TouhouCombatEvents` 已是 per-hit 事件，天然正确）。

**理由**：環/交差这类自轴弹幕若也按人复制，单个玩家会同时吃到 5 份环形压力——那不是"人越多越公平"，是**线性加难**。复制只对瞄准型成立，因为瞄准型的语义就是"有一发是给你的"。

**连带**：总弹量上限按 5 人峰值设（见 D7）。

### D7 — 弹幕实体硬上限 500，超限停止生成

**选择**：全局同时存在的弹幕实体数上限 500（进 config）。达上限时**停止生成新弹**，不删除既有弹。

**理由**：5 人 × 单人峰值约 80 发 = 400，留 100 余量。超限时删旧弹会造成画面突然"少了一大片"，读作 BOSS 放空了；停发则读作"这一轮到此为止"，可预期。

**R3 的口径**：6 格内的弹数按**每名玩家分别**判定，不按全场总数——否则 5 人时 R3 会自动放宽，可读性纪律失效。

### D8 — 数值：秒带取代倍带

**选择**：`monsterBudget` 段的 BOSS 生命由 `dps × [30, 50]` 改为 `dps × bossSeconds[tier]`，秒带覆盖 1~5 分钟（T1 60~90s / T2 110s / T3 180s / T4 240s / T5 300s）。单只 boss 在带内取自己的秒数与挨弹数，均进 config，并沿用 spawn ±25% roll（`MONSTER_SPAWN_ROLL`，此前已定义但无任何实体读取）。

**理由**：`[30, 50]` 与同项目 `TEST_BOSS_MIN_SECONDS=120 / MAX=180` 自相矛盾，且 30~50 秒装不下"1~5 分钟"的设计意图。秒带把"打多久"直接编码进配置，而倍带只编码了一个无量纲倍数。

**顺带修**：`referencePlayerEhp` 累加 `health_bonus` 时未应用 `ATTR_HEALTH_BONUS_CAP=200`，导致 T4（Σ270）高估 1.32×、T5（Σ810）高估 2.53×。当前无任何实体调用该预算，故修正零回归成本。

### D9 — 召唤挂钩：effect id 注册表

**选择**：新增 `effect` 字符串 id → 实体工厂的注册表，boss 侧声明 4 个 id。百鬼夜行配方引用这些 id。

**对接边界**：本变更交付**注册表与落地通路**。配方里 `effect` 字段的具体填写、以及把占位值 `hyakki:balance_test_boss` 替换掉，属 `add-hyakki-yagyo-summon-ritual` 的数据，不在本变更改。

**无门票/充能的语义沿用隔壁**（`spCost` 作容量、受灵汇速率 = 容量 ÷ 10），本变更不碰 `HyakkiYagyoBehavior` 任何一行。

### D10 — 血条白捡，但硬依赖隔壁接口

**选择**：四只 boss 实现隔壁已定义的 `entity.TouhouBoss` 空接口，即得咒符条。

**理由与风险**：`TouhouBoss` 是 common 侧空接口，boss 实体实现它即被 `TouhouBossBarRenderer` 识别（按 UUID 在 `entitiesForRendering()` 里查实体后 `instanceof` 判定）。**这是跨 change 的编译期依赖**：若隔壁改名或改语义，本变更的四处 `implements` 要跟着改。风险低但必须记在迁移顺序里（隔壁先合）。

### D11 — 残影的占位渲染走注册点，不硬编进实体

**选择**：残影的渲染器由一个注册点按实体 id 决定（占位形态为 billboard + 签名色盘），不写死在实体类里；大妖精沿用既有 GeckoLib（`lesser_fairy` geo + 自有贴图）。

**理由**：`project.md` §5.2「替换零成本原则」要求占位期保证未来替换时不改任何代码与引用。三只残影当前无模型是**占位而非终态**，硬编 billboard 会让后续换模型变成改代码。

**顺带**：签名色盘是"每轨一种独占视觉标识"的载体，与渲染实现解耦——弹幕颜色取自色盘，不取自渲染器。

### D12 — 四只 BOSS 的符卡与轨道构成

符卡 = 阶段，按血量阈值切分。**「缺哪一段」是对轨道构成的硬约束，不是比喻**。

```
  大妖精       3 符卡   教学。全大、全慢、全朝前，无 R1 违规
    一「散華」  1 轨  5 向扇，朝主目标，只覆盖前向 200°，全大慢球
    二「旋風」  1 轨  竖直环面向玩家、自转、留 60° 缺口
    三「落華」  1 轨  正上方垂直落下的慢球群，缓慢横漂

  鬼蛛「堅牢」3 符卡   缺「破」——轨道里没有主攻轨
    一「経糸」  2 轨  地滑帯（贴地外推后擦过地表）‖ 定幕（悬停弹定住成幕）
    二「結界」  2 轨  包囲（穹顶向内收拢再张开）‖ 潜溜（静止溜め散布在目标周围）
    三「硬化」  2 轨  交差（三正交面各转，交出移动空格）‖ 補発（自缺口方位补发的分裂弹）
    ⇒ 全程不瞄准玩家，弹只出现在"规则位置"，玩家必须主动破局

  狐火「無序」  3 符卡   缺「序」——无预备拍，起手即峰值
    一「乱焔」  2 轨  绕垂直轴曲射 ‖ 绕水平轴反向曲射
    二「泡」    2 轨  悬停泡缓慢逼近 ‖ 泡破裂时的分裂环
    三「散」    3 轨  乱序锥内随机（锁在缓慢旋转的锥里，非全向随机）
    ⇒ 预警窗口极短但 MUST NOT 违反 R1：读不出是因为没时间，不是因为看不见

  傩神楽面「無終」5 符卡  缺「結」——节拍无终止条件，到时不收束
    一「拍」    1 轨  固定节拍重复，无终止
    二「連拍」  2 轨  节拍重复，密度加倍
    三「乱拍」  2 轨  节拍重复但两轨交换位置
    四「急拍」  2 轨  节拍加速
    五「無終」  3 轨  三轨同时重复且互不同步——找不到共同节奏
    ⇒ 5 张全是"同一招的变奏"，正是"缺結"的定义
```

**难度阶梯的构成**：大妖精无缺陷（教学）→ 鬼蛛缺主攻（被迫主动）→ 狐火缺预警（被动挨打）→ 傩神楽面缺终止（时间压力）。**弹量与弹伤全程不增长**，变的是轨道构成、空间带（10~30 收到 6~22）与垂直偏好。

**数值分档**（`HP = 玩家DPS × 秒数`，`弹伤 = 玩家EHP ÷ 挨弹数`）：

```
  BOSS          阶   DPS      HP       EHP    弹伤   挨弹
  大妖精        T1   15.99     959     63.2   6.3     10
  鬼蛛          T1   15.99   1 199     63.2   7.9      8
  狐火          T1   15.99   1 439     63.2  10.5      6
  傩神楽面        T2  169.2   18 612    415.0  83.0      5
```

**难度旋钮是"中弹率分界线"而非"挨几发"**：玩家可带回复（T1 约 30 HP + 携带回复 ≈ 60 有效预算），故真正的判据是

```
  致命中弹率 p* = 有效预算 ÷ (单发实际掉血 × 全场危险弹数)
  T1 实测：p*=10% 稳过 / 25% 死 —— 全部难度都在这条约 15 个百分点的缝里
```

T1 参考玩家曲线（Σ1..1 grace base，无 roll）：`spirit_power=6`、`health_bonus=10`、`danmaku_reduce=1.0`、`graze=0.05`、`crit=0.11/0.60`、武器 Lv1 ×1.0、参考射速 2.5/s。

### D13 — 掉落

```
  四只均掉 碎符卡星（数量进 config）
  鬼蛛额外保底掉 隙间碎片 ×1
```

**不设单一用途锁死**：碎/整符卡星均可作非符卡用途，隙间碎片亦可有其他用途。本变更**只保证产出源与保底性**，不规定其消费方——消费设计不在范围内。

**保底而非概率**：隙间碎片是幻想乡的钥匙，锁在 RNG 上等于给终局门加随机失败。

## Risks / Trade-offs

- **[跨 change 编译期依赖]** → 四只 boss `implements TouhouBoss`，该接口属隔壁 change。**迁移顺序：隔壁先合。**
- **[新弹幕行为两端同规则失配]** → 该基类约定运动学纯由 `SynchedEntityData` 驱动、双端各自推进。四种新行为若任一端实现不同步，表现为"客户端看到弹悬停、服务端还在飞"或反之。**缓解**：四种行为各写一条双端一致性单测。
- **[5 人 × 并发轨道 → 实体数爆炸]** → 硬上限 500（D7）+ R3 按人分别判定。**待实机**：5 人真机跑一次峰值，观察是否常触顶；常触顶说明单人轨道密度给高了。
- **[随机游走把 BOSS 送进地形/卡死]** → 游走点排除墙内，飞行不受地形碰撞；选不出点时退化为横移而非停机。**待实机**。
- **[残影 billboard 会被视锥剔除]** → 与隔壁 D7 同类陷阱：`shouldRenderOffScreen()` 不豁免视锥，实体 bounding box 必须大于视觉尺寸。**缓解**：`makeBoundingBox()` 覆写按色盘半径放大。
- **[`star_silver` 移除削弱 T1 材料带价值]** → 符星铳原本靠一个 T2 材料当隐形门；移除后该门消失，`refined_cinnabar` / `spirit_iron` 的重要性上升。**这是意图**（T2 门只该由 BOSS 开），但需确认 T1 材料带不会因此显得多余。
- **[秒带改动波及未来调用方]** → 当前无任何实体读取 `MonsterStatBudget`，故 `referencePlayerEhp` 的 cap 修正零回归；但一旦寝宫 BOSS 接入，秒带即成为契约。**缓解**：把 1~5 分钟的秒带写进 spec 场景。
- **[五只占位 boss 与四只正式 boss 的血条并存]** → 咒符条按 `instanceof TouhouBoss` 判定，占位 boss 若不实现该接口则走原版条。**这是期望行为**（占位不该有正式血条），但需确认视觉上不突兀。

## Migration Plan

1. 弹幕基类四种行为 flag + 同步字段 + 双端一致性单测
2. 轨道/节拍模型与轨道器
3. BOSS 基类（符卡阶段、距离带移动、≤5 多目标、掉落钩子、伤害除数）
4. 三只残影实体（占位 billboard 渲染走注册点）
5. 大妖精实体重做（换掉 `HoverAboveTargetGoal`、接入符卡、接入多目标）
6. 数值：秒带 + `referencePlayerEhp` cap 修正 + 四只 BOSS 配置项
7. `zaohua_circle.json` 移除 `star_silver`
8. `effect` 注册表与 4 个 id 声明
9. 写测试：R1/R2/R3 静态校验、缺段约束校验、弹伤反推的挨弹数断言、`star_silver` 反死锁断言

**回滚**：无存档迁移。新增均为注册表对象，删除项仅配方中的一条材料引用。
