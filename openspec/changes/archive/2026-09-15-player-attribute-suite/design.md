# Design: player-attribute-suite

## Context

现状：玩家侧仅有 `spirit_power` 附件（current/max/temperLevel/regenBuffer/spiritDamage），恢复速率与最大灵力的成长已绑在 temperLevel 上但散落在 `ModAttachments.tickRegen` 硬编码；受弹结算只有 `DamageEventHandler` 对 mu_power / danmaku_protect 两个状态效果的乘算；增幅核词条（`RuneAffix`）直接改武器公式乘区，与玩家属性无统接口。玩法侧已定稿 14 项属性与"BOSS 只有血量、玩家靠减伤压同期伤害量级"的平衡模型（见 proposal）。

## Goals / Non-Goals

**Goals:**
- 一个开放的属性注册表 + 统一容器，新属性=注册键+接结算点，不改存储结构
- 结算管线（受弹/暴击/汲取/CDR/时长缩放）全部服务端权威
- 旧档零迁移成本，断链可回滚（新附件独立于 spirit_power）

**Non-Goals:**
- 不做属性面板 GUI（调试命令代替）；不定淬炼各阶成长曲线（后续淬炼内容步骤）；不扩增幅核词条池（先接框架）；不实现降神变身（只留白名单机制）

## Decisions

### D1 独立附件 + 键值容器（而非扩写 SpiritPowerData record）
新建 `player_attributes` 附件，内部 `Map<AttributeKey, Float>`（加区贡献，定点累计），另有**临时改写层**（transient，不持久化，供降神/变身用，到期整层丢弃即恢复原值）。`AttributeKey` 枚举注册表持有：显示名、结算域（加区/独立乘区）、默认基准值配置项、上限、可否被变身改写。
- 为什么不扩 record：SpiritPowerData 已 5 字段，再加 10+ 属性字段每次加属性都要动编解码与全部 with* 复制；且属性持久化与灵力当前值同步节奏不同绑，拆开各管各的。
- 为什么不直接用原版 Attribute（neoforge entity attribute）：原版属性系统只有生命/移速这类通用战斗数值值得桥接（见 D2）；弹幕系属性全是自定义伤害管线内的语义（减免先于抵抗、只对 danmaku 类型），塞进原版 Attribute 反而丢失结算顺序控制权。

### D2 分层公式：最终值 =（基准 + Σ加区平值）×（1 + Σ加区百分比）× Π(独立乘区)
基准值从配置读取（可按淬炼层级线性放大的键由配置基项声明），加区来源=附件持久层+临时层，乘区留给暴击这类"每键独立 roll/独立系数"。增幅核词条与未来所有装备词条只能映射到既有 AttributeKey 的加区，**禁止发明表外属性**——容器提供 `sourceId` 前缀的 modifier 分组，便于后续"洗练/卸下"整组移除。

### D3 原版属性桥：生命增幅与移动速度走 entity attribute modifier
生命增幅=额外生命语义：注册固定 modifier id 的 `minecraft:max_health` AddValue（值为套件最终值），数值刷新时整体重算而非累加（幂等）。原版规则天然处理"上限降低时血条钳制、提升时不自动回血"。移动速度同理 `minecraft:movement_speed`。这两项**不**进自定义受击管线。
- 否决备选：自管血条（双倍持久化复杂度，死亡/重生/传送全是坑）。

### D4 受弹管线：在 DamageEventHandler 内重构为固定顺序管道
仅当 受害者=玩家 且 伤害类型=`gensokyou:danmaku`：
1. **擦弹**：服务端 roll，命中则伤害=0，结束；
2. **减免%**：与 danmaku_protect 状态效果**乘算**：`(1-减免) × (9-盾级)/10`，合并后百分比减免全局封顶（配置，默认 90%）——属性自身永远达不到全免，全免保留给 10 级护盾这个"仪式手段"；
3. **抵抗**：再减固定值，允许减到 0（"前期数值打后期 BOSS 要么真无伤"是特性不是漏洞）。
mu_power 乘区顺序不变（先于本管线）。现有两个效果分支并入同一管道，行为回归测试。
- 为什么不把抵抗放减免前：固定值先扣会让百分比在缩小的基数上二次收益递减，MOBA 惯例（先%后定值）让两类词条量级可独立计算。

### D5 暴击：发射时 roll，系数写弹幕 NBT
`WeaponFiring` 生成弹时读 owner 套件 roll 暴击，命中结算按 NBT 系数进乘区。
- 否决"命中时 roll"：弹幕可存活跨玩家下线/换维度，命中时 owner 附件不可靠；发射时定值与既有"NBT 伤害持久化"模式同构。

### D6 灵力汲取：命中后结算，令牌桶限速
命中结算完成后：回复 = min(实际伤害×配置%, 剩余桶容量)，经 spirit_power 既有的扣减/回充接口入池（满池自然截断），桶每结算周期按配置上限回充（复用 ritual 侧 TickRateLedger 的周期账本思路，非同一实例）。实验件：配置总开关，设 0 即全链路自然失效、不留死代码。

### D7 CDR 与效果时长缩放的消费点
- CDR：`SkillStateData` 写冷却时用 `base × (1−CDR)`；HUD 显示的剩余秒数由服务端算好后本就正确，零客户端改动。封顶（默认 40%）在套件侧做，消费方不感知。
- 强效延长/韧性：在 `MobEffectInstance` 施加点统一折算（玩家获得/施加的正/负面效果时长 × (1+延长) / × (1−韧性缩减)），**惠及降神变身 T 秒**（已裁决）；比例型符卡效果（无想封印 min(最大生命/2,上限)）不吃符卡增幅，符卡增幅乘区只作用于"伤害数值项"，本步无现行消费者、为未来伤害卡预留。

### D8 同步策略：客户端只消费原版桥与既有通道
套件本体不同步全量到客户端（结算全在服务端）；客户端可见部分=原版属性同步（生命/移速）+ 现有 spirit/skill 同步载荷，不新增包（零新网络包原则延续阶段 A 决议）。

### D9 旧档与回滚
`player_attributes` 为新附件，旧档缺失即空容器=全属性取基准，无需迁移脚本；spirit_power 与 player-spirit-attributes 既有字段原样保留（灵力强度仍存旧字段、由套件读取合并，避免双写）。回滚=删附件注册，持久数据成惰性孤儿字段无害。

## Risks / Trade-offs

- [乘区叠爆（暴击×符卡增幅×武器等级×词条未来互乘）] → 每键独立上限入配置 + 设计评审新增乘区必须挂 AttributeKey 注册表，不允许公式内手写裸乘数
- [擦弹 RNG 手感（连续免伤或连续中招）] → 封顶 40–50%（配置）保留；试平不满意可整键停用（注册表开关），不伤管线结构
- [抵抗+减免导致旧内容零交互（数值上无伤=剧情体验流失）] → 接受：这是"养成校验"的设计意图，非漏洞
- [DamageEventHandler 重构回归风险（mu_power/protect 行为漂移）] → 既有 danmaku-combat 场景（III 级盾 100→60、XI 级→0）进本期任务测试用例
- [汲取高频武器循环回灵过强] → 桶上限+满池截断双闸；仍失衡则配置归零下线
