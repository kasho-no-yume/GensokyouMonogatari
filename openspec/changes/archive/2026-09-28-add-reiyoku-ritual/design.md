## Context

灵浴是仓库中**唯一一座结构已就绪、行为未实现**的仪式。现状与约束：

- `data/gensokyou/rituals/reiyoku_circle.json` 已存在并通过离线校验，四重展开后 1532 格，`toggleable: true`，`tiers`/`levels` 均为 1..5（结构阶与仪式石阶重合，故跨阶数值统一用 `match.level()`）。
- `RitualBehaviors` 中无灵浴条目 → `getCapacity()` 落进 `DEFAULT_CORE_CAPACITY = 10_000` 兜底分支。**该值恰好等于预期的 1 阶容量**，构成一个只会在 2~5 阶暴露的静默错误。
- pattern 无祭品台（无 `P` 键）、无配方、无战利品表 → 无 `RitualOfferings` / `RitualRecipeMatcher` 面。
- 玩家灵力池 `SpiritPowerData.current` 是 `float`，`temperLevel` 是唯一的超人类阶级事实来源。
- 渲染态通道 `RitualRenderState` 已有 8 个 kind，辅助字段按 kind 复用；客户端可经 `ClientRitualData` 取到已解析的 `RitualPattern`（含已展开方块表），但**不知道当前核心匹配到哪个 patternId**（`activeMatch` 只在服务端赋值）。

### 结构实测（1 阶，四重对称后剖面）

```
 y=+4            q  r                     ← 屋脊压顶
 y=+3         r  r  r  q                  ← 木屋顶，(0,3,0) 留 1 格烟孔
 y=+2                   K                 ← 墙 + 白羊毛窗（仅 4 轴）
 y=+1   ·  ·  ·  ·  ·  ·                  ← 柱廊层，4 轴全开
 y= 0   @  ·  1  ·  ·                    ← 核心 + 仪式石环（切比雪夫边界 = 2）
 y=-1   g  h  b  a  a  h  h  c  a        ← 实心台基，顶面 = y 0.0
```

- 地板 = `y = 核心Y-1` 层的**顶面**，故站立玩家脚底方块 Y = 核心Y，跳跃时 +1。
- 净空 `y ∈ [核心Y, 核心Y+2]` 三格；墙在半径 3~4。
- 可站点共 24 处：核心周围 3×3 空气袋 8 格（最大欧氏距离 1.41）+ 仪式石环顶面 16 格（最大欧氏距离 2.83）。
- `y = 核心Y-1` 层的格位数按阶为 137 / 137 / 233 / 433 / 433；这是外圈环 + 平台的实心地形，**水只铺其中被结构围出的部分**（见 D11），不是整层都铺。

## Goals / Non-Goals

**Goals:**

- 把灵浴完成为可游玩的启停型充灵仪式，并修掉 `getCapacity()` 兜底导致的 2~5 阶静默偏差。
- 充灵速率严格等于“结构阶对应玩家阶级标准池的 1%/s”，从 0 充满约 100 秒。
- 能量收支闭环：槽核 → 缓存 → 玩家，玩家充灵真实消耗缓存，缓存耗尽即停充且不改 `enabled`。
- 运行态表现（水面 + 灵气柱）以客户端网格为主载体，零逐 tick 网络包。

**Non-Goals:**

- 不做**会话型**（不绑定启动者、不走 `SeiiSession`）：任何走进浴亭的合格玩家都能用。
- 不做**产灵**：灵浴是纯消费者，不修改 `enabled` 之外的仪式状态机。
- 不改玩家灵力池的**上限**语义、不改回灵/汲取/汲取限速账本。
- 不改 pattern JSON（结构已定稿，本变更纯代码 + 配置 + 语言 + 指导书）。
- 不给凡人（T0）做任何注灵旁路——`max = 0` 时天然 no-op。

## Decisions

### D1 速率按**结构阶**取标准池，而非玩家自身阶级

`充灵速率(L) = 标准池(L) × 1%`，`标准池(L) = 1000 × 10^(L-1)`。

**为何**：用户明确选择“按结构对应阶级的玩家阶级”。这让“5 阶结构给 1 阶玩家充灵 = 秒满”成为**有意的阶级落差**——高阶设施对低阶玩家的降维服务。

**否决**：按玩家阶级取表。否决理由是它会让高阶结构对低阶玩家完全无意义（5 阶浴池给 1 阶玩家仍是 100 秒），结构等级沦为纯装饰。

**推论**：阶级门控 `玩家阶级 ≤ 结构等级` 的作用从“防刷”转为“防无意义”——否则 5 阶玩家站进 1 阶浴池会以 10/s 获得 10,000,000 灵力（11.5 天），体验上是“卡住了”而非“拒绝了”。门控把这种情形变成一句明确提示。

### D2 扣费走 `extract` 的返回值，比例折算，“停充”不需要显式判断

```
totalCachePerTick = 标准池(L) ÷ 200          // 满额供给时的理论值
perPlayerCache    = 均分后该玩家本 tick 的份额
taken             = core.extract(perPlayerCache)   // 返回实际取到的量；缓存空 → 0
gain              = taken ÷ 10.0f                  // 10 缓存 = 1 灵力
```

`extract` 返回实际取到的量，于是：

| 缓存余量 | taken | gain | 表现 |
|---|---|---|---|
| ≥ 份额 | 份额 | 满速 | 满速 |
| 3（份额 5） | 3 | 0.3 | 自动降速 |
| 0 | 0 | 0 | 停充，`enabled` 不变 |

**为何比例折算而非硬门控**：硬门控（`if (getStored() <= 0) return;`）会在缓存剩 1~9 点时卡住不动；比例折算把尾部也用掉，并让“没电”表现为优雅降速。缓存最终仍精确归零。

**扣费 MUST 走普通 `extract`，MUST NOT 走 `extractRouted`**：内部消耗若走路由通道会被自身 `inRate` 账本误截（`resonance-relay-routing` / `ritual-power-attributes`）。

### D3 默认配置下不需要进位，但把“不丢量”写成契约

| L | 标准池 | 缓存/tick | 灵力/tick | 整数？ |
|---|---|---|---|---|
| 1 | 1,000 | 5 | **0.5** | 缓存侧整；灵力侧半整数 |
| 2 | 10,000 | 50 | 5 | ✓ |
| 3 | 100,000 | 500 | 50 | ✓ |
| 4 | 1,000,000 | 5,000 | 500 | ✓ |
| 5 | 10,000,000 | 50,000 | 5,000 | ✓ |

- **缓存侧**：默认百分比下 `标准池/200` 恒整除 → 直接 `long` 抽取，不丢。
- **灵力侧**：只有 1 阶是 0.5/tick。玩家池是 `float`，量级 1000 处 ulp ≈ 6e-5，**0.5 精确可表示** → 直接 `withAddedCurrent(0.5f)`。

**但**：管理员把百分比调成使 `标准池/200` 非整除时，缓存侧会整除归零（skill 红线「整除截断丢量」）。故实现 MUST 带一个 `long` 进位累加器（先例：`RitualCoreBlockEntity.rateCarry` / `fillCarry`），使契约是“任何配置下都不丢量”而不是“默认数值恰好整除”。

**float 精度上界**：充灵速率恒为池的 1%/s，故每 tick 增量 = 池/2000；L5 池 10⁷ 时为 5,000/tick，而该量级 float ulp = 1.0 → 安全。任何“速率与池的比值”配置都不会让增量落到 ulp 以下（比值是配置项而非派生量），但实现 MUST NOT 改成“按当前池的百分比”式的动态口径（`superhuman-temper` 已有同款红线：回灵必须是定值）。

### D4 均分的分母只数“合格且未满”的玩家

**分母 N = 同时满足以下三条的玩家数**：

1. 位于浴区内；
2. `temperLevel ≤ match.level()`（阶级门控）；
3. `当前灵力 < 有效上限`（未满池）。

**为何要排除已满池者**：已满玩家泡在浴池里若计入分母，会做两件坏事——白吃缓存（`gain` 落到 `clamp` 后被丢弃）、并把速率分母撑大拖慢其他人。排除后“站满一圈人却没人充灵”的观感也消失了。

**分母为 0 时**（浴池空、或全员已满、或全员越阶）：本 tick 零抽取，缓存不动。

**均分的精度**：`per = (carry + total) / N; carry = (carry + total) - per * N`。经典 Bresenham 拆分，逐 tick 聚合后**总量精确等于** `total`，不因整除而系统性偏慢。`carry < N ≤ 玩家数`，量级可忽略，无需持久化（N 变化时残留 < 64，不影响正确性）。

### D5 tick 通道 = `serverTick`（核心方块实体侧），玩家扫描走 `level.players()`

**为何不挂玩家侧 `PlayerTickEvent.Post`**：玩家侧需要从“我在哪”反查“最近是哪个成型仪式”，要多一层反查与失效处理；而 BE 侧天然持有 `corePos` / `match` / `core`，扫 `level.players()`（维度内玩家数通常个位数）过滤半径即可。

**关于“每 tick 读-改-写附件会不会撞车”的澄清（此前的一次误判，勿再提出）**：`SpiritPowerData` 虽是不可变 record，但每个写手都在**自己执行时重新读一次** attachment 再写回，故顺序执行不产生丢更新。`GraceFlight.onPlayerTick` 与本变更同 tick 并存是安全的。**真正的代价只是带宽**——见 D6。

### D6 每 tick 写池并逐 tick 同步，但**只对正在被充灵的人**（第六轮反馈后修正）

`ModAttachments.set()` 每次都跟一个 `SpiritPowerSyncPayload`（`GraceFlight.syncGraceState`）。纯 per-tick 调用 = **20 包/秒/人**。

**原决策（已被推翻）**：新增一条不触发 `sync` 的写入路径（`setQuiet`），`serverTick` 用它逐 tick 写池，同步另行按固定周期（复用既有 1Hz 快照节奏）触发。

**为什么原决策是错的**：静默写入只保证**服务端**的池值逐 tick 涨；客户端拿到的最新值要等统一 1Hz 快照心跳，于是玩家亲眼看到的是「按秒补」——正是 D6 想避免的那个现象。写入路径与同步节奏必须一起决定，只降同步不降写入是自欺。**这条坑记在这里，别再犯第二次。**

**现决策**：
- 写入走 `setQuiet`（保持：不让 20 包/秒 的成本落到**所有**灵力写入路径上）；
- **充灵期间**按 `REIYOKU_CHARGE_SYNC_TICKS`（默认 **1** = 每 tick）补同步，离池即停。开销只落在「此刻正在被充灵的人」×cadence，1 阶场景即一名玩家 20 包/秒（约 7 字节/包）；
- 间隔做成配置项：调回 20 即退回 1Hz 行为，给在意包数的服主一个退路。

**未能再进一步的原因**：客户端 HUD 是**整点**语义（`GraceFlight.syncGraceState` 里 `Math.round(data.current())`，`SpiritPowerClientState.current` 为 `int`，供 0~5 槽位显示）。故 1 阶（0.5 点/tick）最快每 2 tick 跳 1 格，调小同步间隔低于 2 不会更平滑。要做亚点平滑就得把共享的 int 通道改成 float，那会波及全 mod 的回灵/飞行/超人类阶显示 —— 超出本变更范围，且收益不成比例。

**否决**（把充灵降到 20 tick 结算一次）：用户明确要求“每 tick 充灵不是每秒充灵”。且虽然累积后数学等价（1%/s 完全相同），但会让池读数滞后最多 1 秒，对以灵力为门限的符卡/武器结算有可感差异。

**否决**（缓冲累积 20 tick 后一次性 flush）：同上，且额外引入一个玩家侧待领取缓冲，收益仅是省 19 个包。

### D7 能量入口方向：覆写 `refillsCacheFromSocket()`，先补料后扣费

核心槽有两个**互斥**搬运方向：

```
产能仪式（迦具土/梦渡/赛尔）：  缓存 ──tickBatteryAutoFill()──────▶ 槽核
消费仪式（结界/丰穰/星移/百鬼）：  槽核 ──tickBatteryToCacheFill()──▶ 缓存
```

灵浴是纯消费者，故 MUST 覆写 `refillsCacheFromSocket() → true` 并每 tick 先 `tickBatteryToCacheFill()` 再扣费。

**顺序有讲究**：同一 tick 内先扣后补会让净值短暂为负一档（`BarrierBreakBehavior` 已有同款注释）。灵浴的扣费是逐 tick 的，所以补料必须在扣费之前。

**若不覆写的后果**：槽核退化成“只进不出”的黑洞——玩家插满灵核，缓存恒为 0，浴池永不工作。而由于 `DEFAULT_CORE_CAPACITY` 兜底恰好等于 1 阶目标值，**1 阶实机测试完全看不出问题**，2 阶才暴露。

### D8 浴区判据（写死为欧氏 + 闭区间）

```
水平： hypot(player.x - core.x, player.z - core.z) ≤ BATH_RADIUS
垂直： coreY ≤ player.blockPosition().y ≤ coreY + BATH_HEIGHT
```

- **欧氏而非切比雪夫**：仪式石环四角在欧氏 2.83、半径 3 恰好全含；切比雪夫会把半径 3~4 的墙体外的站位也纳入。欧氏更贴合“站在池子里”的直觉。
- **闭区间 `coreY ≤ y ≤ coreY+H` 而非 `|Δy| ≤ H`**：后者会把挖穿 `y = 核心Y-1` 台基、站在 `y = 核心Y-2` 的玩家也纳入。
- 取**脚底方块** `blockPosition().y`（即 `BlockPos` 语义，非 AABB），与“玩家站在哪一格地板上”一致。
- 观察者（spectator）无灵力池，天然 no-op；创造玩家有池，允许充灵（`GraceFlight` 排除创造玩家是因为**耗灵**，语义不同）。

**半径与高度进配置**（skill 红线：可调数值不得硬编码），默认 `3` / `2`。

### D9 阶级门控提示走 `InfoLine.tipped`，可见行只放 4 汉字

信息盒右缘 x=112、文本起点 x=8，默认字体 1 汉字 ≈ 9px → **纯文本行预算 11 汉字**。目标句子「错误：“玩家名”的等级高于仪式阶级」约 17 汉字，**必然超框**（超框虽会自动换行不丢内容，但会撑高行、挤掉后续行，`ritual-gui-info-lines` 明确要求换行只作兜底）。

**决策**：
- 可见行：短标签（如「无法注灵」，4 汉字），红色 `0xFFB22222`（同 `kagutsuchi.stalled`）。
- tooltip：完整句子，含玩家名 / 玩家阶级 / 仪式阶级三个参数。

**为什么是指南按查看者的 `uiInfo(viewer)` 重载**：提示的受众是“当前打开这个仪式的那个玩家”，而一个浴池可能同时服务多个不同阶级的玩家。走 viewer 重载后，快照本就按玩家点对点组装，无需广播。

**该行只在“查看者本人在浴区内且越阶”时出现**——否则每个打开界面的人都会看到与自己无关的告警。

**lang 键必须显式列举**：句子含玩家名等动态内容，MUST 走带占位符的 lang 键（`textArgs` / `tipArgs`），MUST NOT 拼接键前缀（`lang_audit.py` 会把拼接前缀当字面量误报）。

### D10 新增渲染态 kind `KIND_REIYOKU = 9`，占地由客户端本地推导

`RitualRenderState` 的辅助字段按 kind 复用，位宽 `long` 上限 64 条。本 kind 的字段分配：

| 字段 | 语义 |
|---|---|
| `enabled` | 唯一门控（停机即无特效） |
| `tier` | 结构等级（`match.level()`），客户端据此取该阶 pattern 切片 |
| `minY` | 结构最低点 Y 偏移（= −1） |
| `maxY` | 结构最高点 Y 偏移（L1 = +4 … L5 = +16）。**仅供调试对照**：灵气顶面改取世界建筑上限（D12） |
| `linkPos` / `inCount` / `movingMask` | **不使用**（无逐台通道） |

**占地推导**：客户端不知道 patternId（`activeMatch` 只在服务端赋值，`buildRenderState` 在 `isClientSide` 时直接返回）。故采用 `KIND_REIYOKU → gensokyou:reiyoku_circle` 的**单向硬绑**，再经 `ClientRitualData.pattern(id)` 取该阶切片，按 D11 的两条规则算出主池与院子。这**不是第二套几何语义**——读的是同一份 pattern 数据，客户端不硬编码任何坐标。

**代价与替代**：直接下发 328 个坐标需要 328 个 `long`（远超 64 通道上限）；`RitualFxLayout` 的纯函数布局 + 服务端下发锚点（`WUJINZANG` / `BAFANG` 走的路）需要新增 kind 字段。硬绑 kind 是唯一既不扩 payload 又不引第二套语义的方案。

**渲染包围盒**：`getRenderBoundingBox()` 现有分支给非 `RELAY`/`WUJINZANG`/`KANAYAMAHIKO`/`SUMMON` 的水平半径只有 16 格，而 L4/L5 水面达 ±11、且 `shouldRenderOffScreen=true` **不豁免视锥**（方法 javadoc 明确：NeoForge 走 `frustum.isVisible(renderer.getRenderBoundingBox(be))`）。故 MUST 为本 kind 单独开一支，水平半径取 `max(16, 水面半径 + 2, 灵气派生横截半径 × (1 + 张开) + 2)`，**顶面 MUST 到世界建筑上限**（D12）。

### D11 水面几何：0.8 格高，只铺**主池 + 外圈院子**，走道不铺水

结构里 `y = 核心Y-1` 层是实心台基。若把 0.8 格高的水体按“底面在 y = 核心Y-1”放置，它会**完全埋在实心方块内、渲染上不可见**。唯一自洽的读法是：

- 基准面 = `y = 核心Y-1` 层的顶面（世界坐标 `核心Y`）；
- 水体自该面向**上**占据 0.8 格，即占 `y = 核心Y` 这一格的 0.8；
- 站立玩家的脚正好没入 0.8 深的浅水 → “浴”的语义成立。

**占地 = 两块，都是同一份 pattern 的纯函数（零魔数）**：

| 区域 | 定义 | 实测 |
|---|---|---|
| **主池** | `y = 核心Y` 层**未被 pattern 声明**、且**格坐标距** ≤ `REIYOKU_BATH_RADIUS`（默认 3）的格位 | 各阶恒 12 格 |
| **院子** | `y = 核心Y-1`（最低层）中未被声明、且**被已声明格位包围**的空连通块（4 邻域 flood fill 自图外起） | L1–L3 = 0 块；L4/L5 = 4 块 × 79 格 |

合计 **12 / 12 / 12 / 328 / 328** 格，水平半径 3 / 3 / 3 / 11 / 11。

四条必须写死的设计约束：

1. **包围判定 MUST 在最低层做**。灵浴外圈石砖环只在 `y = 核心Y-1` 是实心的；上一层的环有缺口，在那里 flood fill 只会得到 3 个 8~9 格的小口袋，4 个院子全丢。这也是“4 阶起才有窝”的实现方式 —— 低阶外圈没有实心环，自然 0 块，**MUST NOT 按阶硬编码特判**。
2. **主池 MUST 取“未声明”而非“最低层全部格位”**。最低层含核心基座与仪式石环（它们占 `y = 核心Y` 那一格），水画进去会被埋在方块内不可见；而只有未声明处才有空气。得到的集合恰好等于“玩家能站进去泡水”的全部格位 —— 水面即“浴区”本身，这个不变量值得保持。
3. **院子格位在 pattern 中未声明**（不受结构约束、亦无地板），故 MUST NOT 用“pattern 声明了什么”定位；靠“被声明格位包围”反推，边界来源仍是同一份 pattern。
4. **两块底面 MUST 相差一格**：主池坐在最低层顶面（`minY + 1`），院子低一格（`minY`）—— 院子处最低层未声明、无地板，地面在更低一层。`WaterCell` 因此 MUST 携带 `y`，渲染端只做「逐格底面 + 统一抬升」，**MUST NOT 再叠加整体基准 Y**（`cell.y()` 已是完整局部偏移，叠加会重复计数把水面顶到结构上方去）。

**走廊/外圈 MUST NOT 铺水**：轴向通道是未声明且**与图外连通**的，包围法天然排除它；外圈石砖环已声明，也天然排除。这条由 `ReiyokuBathSurfaceTest.axialWalkwaysAreNotWatered` / `outerRingIsNotWatered` 钉死（判据用“网格坐标恰为 0”而非“靠近中轴 ≤1 格”——院子实测跨到 `z = ±1`，用 ≤1 会把院子内角误判成走廊）。

**主池 MUST 四向对称**：半径 MUST 按**格坐标距**（`hypot(x, z)`）算，MUST NOT 按格心算成 `hypot(x + 0.5, z + 0.5)`。后者把 `|−3|` 记成 2.5、`|+3|` 记成 3.5，于是 r = 3 时多出的 8 格**全落在 −x/−z 一个象限**，主池读作明显偏心。此错**只在整数半径下暴露**（r = 3.5 恰好对称），故回归 MUST 用默认 3.0；已由 `poolIsFourFoldSymmetric` 做 4 重旋转不变性断言钉死。

**规模可接受**：328 quad/帧，低于既有煅炉火星场（`FX_FORGE_EMBER_COUNT_BASE` 180 + 70×L，每点 3 面片）的现役开销。仍加距离 LOD 降级。

### D12 灵气：堆叠 camera-facing billboard，一路升到**世界建筑上限**（实机三轮反馈后改写）

第二轮反馈：「光柱要一直到建筑高度上限。不然不如做成更淡的灵气的感觉」。

**先确认一条硬事实**：`DanmakuRenderTypes.additiveGlow` 的注释写明「深度测试仍开启，因此发光不会穿透墙体」。灵浴屋顶在 `核心Y+3`、屋脊 `+4`，只留中心 1×1 烟孔；半径 3 的硬光柱在屋外必被屋顶**整片**遮住，只余烟孔一线。所以「让光柱看起来到顶」在物理上做不到 —— 除非把屋顶拆了。

**第二轮改法**：保留「到建筑高度上限」，把表现从「光柱」改为「灵气」（单层软雾、无亮芯）。

**第三轮反馈**：「复用的灵气柱像个八角」+「可以换 billboard + 世界顶」。

**八角的成因**：`emitCrossPlanes` 让 3 个**固定朝向**的面片相交成柱。面片是硬的、棱是硬的，相机斜看时三个面各自成面 —— 读出来是八棱柱而非雾气。

**故改为 N 片 camera-facing billboard 沿高度堆叠**（`FxGeometry.emitBillboard`）：每片都正对相机，任意视角都只有一个软边轮廓，叠加后自然读作“一柱上升的雾”。这消除了棱，也不需要更多面片去凑圆度。

| | 第二轮（单层米字面片） | 第三轮（堆叠 billboard） | 第四轮（修「完全没了」） | 第五轮（修「一股一股」） |
|---|---|---|---|---|
| 几何 | 3 片固定朝向面片相交 | 10 片 camera-facing billboard | 片数按柱高 ÷ 绝对间距推导（约 64 片） | **95 片**；间距 = 雾团高 × **0.25**（约 4 片重叠） |
| 横截半径 | 绝对值 3.0 | 绝对值 1.0 | 绝对值 1.0 | **绑到 `REIYOKU_BATH_RADIUS × 1.0`**（3.0） |
| 雾团形状 | — | 正方形 | 正方形 | **竖向拉伸 1.8**（只拉高不拉宽） |
| 八棱 | 斜视时可见 | 消除 | 消除 | 消除 |
| 高度顶面 | 结构最高点 | `getMaxBuildHeight()` | 同左 | 同左 |
| 高度分布 | 均匀 | 指数 0.7（方向反了） | 指数 1.0 | 指数 1.0 |
| 摆动 | 无 | 按片序号取相 | 按片序号取相 | **按高度 `u` 取相**（整柱同相位） |
| 底/顶 alpha | 0.5 / 0.25 | 0.32 / 0.25 | 0.15 / 0.25 | 0.14 / 0.25 |
| 相机朝向 | 不适用 | `camRot` 取自另两处内部 | 提到 `render()` 分发前 | 同左 |

**第五轮「一股一股、像烟囱」的双重成因**：

1. **片间距远大于雾团尺寸**。半宽 1（2 格高）配 4 格**绝对**间距 —— 横向只有 2 格、垂直却隔 4 格，相邻两片**根本不相接**，叠起来就是一串独立烟团。绝对间距与雾团尺寸脱钩，改宽或改高都不会自动跟随。
2. **柱身本身就是根细管**。绝对半径 1.0 = 2 格宽，塞在 6 格净空的浴亭里，读作亭中一根烟囱管子。

**解法（三条，各自独立）**：

- **间距 MUST 是雾团自身高度的比例**，不是绝对格数。`间距 = 雾团高 × FX_REIYOKU_QI_SPACING_RATIO`（默认 0.25）—— 雾团变大则间距同比变大，**光滑度与尺寸解耦**。
- **横截半径 MUST 绑到充灵半径**：`REIYOKU_BATH_RADIUS × FX_REIYOKU_QI_WIDTH_RATIO`（默认 1.0）。用户明确要求「灵气范围与充灵范围一样大」；两个独立旋钮迟早漂移，漂移后柱身与浴区不同宽又变回烟囱。
- **竖向拉伸把「光滑度」与「横截面积」解耦**：雾团只拉高不拉宽（`FX_REIYOKU_QI_TALL`，默认 1.8），垂直重叠因此显著变密，而横截面仍严格等于充灵半径。否则要更光滑只能加宽，那会破坏用户要求的横截面积 —— 这是三条里唯一能同时满足两条需求的关键。

**摆动 MUST 沿高度连续**。片数上百时若按片序号取相，相邻两片反向摆动，读作杂乱喷溅而非一根连贯的柱；按 `u`（0..1 的高度比例）取相则整柱同相位移动，像一股上升的气。`FX_REIYOKU_QI_MAX_SPRITES` 封顶会拉大实际间距（重叠变少、又变回"一股一股"），故默认参数刻意让 256 格柱只算出 95 片、不触发封顶。

其余三条必须写死的约束：

1. **顶面 MUST 取自 client level**（`getMaxBuildHeight()`）而非写死 320 —— 超高于 320 的世界会在柱顶截断。
2. **渲染包围盒 MUST 一并开到世界顶**。渲染态的 `maxY` 只是结构最高点（偏移 ≤16），只按它收盒子的话柱顶远在盒外，视锥剔除会把**整个 BER 连同整柱灵气**一起剔掉 —— 现象与“灵气完全不显示”无法区分。与 `KIND_SUMMON` 的高柱同源，两处都踩过。
3. **回绕处 MUST 两端淡入淡出**。否则高 alpha 的片从顶端跳回柱底会读作“闪一下”。

**片数 MUST 按柱高推导，MUST NOT 是固定值。** 这是第四轮「灵气效果完全没了」的根因：顶面取世界上限后，核心在 y≈64 时柱高约 **256 格**，固定 10 片 + 指数 0.7 算下来最靠下的一片落在 **y≈33**（亭顶才 +4），其余 9 片相隔 30 余格挂在天上 —— 亭内空空如也、天上零星几点，任一视角都读不出「一柱」。

**指数方向极易搞反**：`y = 底 + 柱高 × u^k` 中 **`k > 1`** 才是「低处密、高处疏」（k=2.5、u=0.05 → 柱高×0.0004，贴底）；`k < 1` 反过来把采样点**往上推**。我曾用 0.7 想要「低密高疏」，实际得到「全在高处」，是上面那个 bug 的第二重成因。默认已改回 1.0（均匀）。

**`camRot` MUST 每帧统一设**。它此前只在 `renderOrb` / `renderSummon` **内部**赋值，于是本 kind 拿到的是上一帧残留值或单位四元数 —— billboard 恒朝 +Z，斜看时同样读作「特效没了」，且现象随 BER 渲染顺序变化，极难定位。现已提到 `render()` 里分发之前，两处内部赋值删除（单一数据源）。

**为何这个方向成立**：玩家泡在池中时**身处亭内** —— 视线里就是「脚下 0.8 格浅灵水 + 四周充满的绿雾 + 头顶木梁」，这正是「灵浴」。屋外不可见不再是缺陷而是「秘所」的性质。`FX_REIYOKU_PILLAR_CORE_RATIO` 早已随亮芯下线（死旋钮比没有旋钮更糟）；`FX_REIYOKU_PILLAR_PLANES` 随面片方案下线，`PILLAR_*` 整组更名为 `QI_*`（语义已从“光柱”变成“灵气雾团”，名字该跟上）。

**已确认接受**：屋外仍被屋顶遮住。实现 MUST NOT 为此加开口或额外绘制。

## Risks / Trade-offs

- **加法混合穿透发光** → 水面占地 MUST 取**未声明**格位而非包围盒（D11）；并用实心方块做天然遮挡。
- **视锥剔除把整段特效剔掉** → MUST 为 `KIND_REIYOKU` 单独开 `getRenderBoundingBox()` 分支，且**顶面到世界建筑上限**（D10/D12）。
- **1 阶“碰巧正确”掩盖回归** → `DEFAULT_CORE_CAPACITY = 10_000` 与 1 阶目标值相同。回归验证 MUST 覆盖 2~5 阶的 `getCapacity()`，否则本变更即使整体回滚也测不出来。
- **不覆写 `refillsCacheFromSocket()` 导致槽核黑洞**，且 1 阶不可见（D7）。任务清单 MUST 把该覆写与容量分派列为独立验收项，且验收用例 MUST 用 2 阶。
- **均分分母整除丢量** → Bresenham 进位（D4）。
- **配置的百分比使每 tick 增量非整数** → `long` 进位累加器（D3）。
- **每 tick 写附件 = 20 包/秒/人** → 写入走 `setQuiet`（不落到所有灵力写入路径），但**充灵期间按 cadence 补同步**（D6）。只降同步不降写入会让玩家看到"按秒补"，是已犯过的错。
- **教程条目被自动生成器捎带** → `tools/gen_ritual_book_entries.py` 会自动捡起这个已能成型的仪式；本变更 MUST 一并补 `RitualTierComponent` 的阶级参数页分支，否则阶级页缺参数。灵浴无配方无掉落 → `--no-recipes`、不建 `loot_page`。
- **lang 审计误报** → 门控提示的句子含玩家名，MUST 用带占位符的独立 lang 键，MUST NOT 拼前缀（D9）。
- **既存观察**：仪式信息区已有滚动与自动对齐机制（`ritual-gui-info-lines`），灵浴行数（状态行 + 门控行 + 5 行由来诗）远低于视口，无需额外处理。

## Migration Plan

无存档格式变更。`ReiyokuBehavior` 无跨 tick 持久态（`carry` 累加器量级 < 64，N 变化时丢弃不影响正确性），故 `onStructureLost` 无需清理动作。回滚 = 移除行为注册，`getCapacity()` 回落兜底（回到本变更前的静默错误状态）。
