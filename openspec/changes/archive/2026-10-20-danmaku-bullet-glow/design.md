# Design: danmaku-bullet-glow

## Context

### 代码级现状

```
DanmakuRenderProbe.ALWAYS_LOD = true          // 硬编码
        ↓
updateDense() → dense = ALWAYS_LOD = true     // 恒为 true
        ↓
effectiveGlow() = glowEnabled && !dense ≡ false
effectiveCore() = coreEnabled && !dense ≡ false
        ↓
SphereDanmakuRenderer.renderGlow() / 亮核层  ── 早退，永不执行
```

- 实体路径 `SphereDanmakuRenderer`：1 个 quad / 1 次 draw，贴图 `sphere_danmaku_lod.png`，
  混合 `translucentDepth`（alpha 混合 + **写深度** + `sortOnUpload=true`）。
- 程序路径 `ProgramDanmakuRenderer`：同样 1 个 quad / 1 次 draw，
  **自己 hardcode** 了 `SPHERE` 常量与 `bodyType`，与实体路径各写各的。
- 激光 `LaserDanmakuRenderer`：**豁免密度 LOD**，四层（亮核 / 主体 / 外发光 1.9× / 端盖）
  今天全开——这就是"激光效果还好"的原因，也是本变更**不动**它的原因。
- `Profile.glowScale=1.35` / `glowAlpha=110` 两个字段仍活着，但驱动的图层已被永久短路。

### 贴图级现状（逐像素实测）

| | `sphere_danmaku_lod.png`（现役） | `sphere_danmaku.png`（旧球） |
|---|---|---|
| 尺寸 | 64×64 | 64×64 |
| 实心区 | 半径 d≤0.4375 → **宽度 43.75%**、面积 15% | 半径 d≤0.62 → 宽度 62%、面积 33.7% |
| 核与外圈之间 | **全透明环缝**（d 0.4375~0.625） | 无缝，smoothstep 连续 |
| 外缘 | **三档硬边台阶** alpha 70/140/25 | 连续衰减到 0 |
| 可见面积占比 | **48.7%** | 77% |

⇒ 现役球弹**读作一个环（甜甜圈），不是一颗球**。"单调"的一半来自这里，与辉光无关。

### 当年砍三层的账（`2026-10-07-danmaku-dense-render-lod/design.md`）

> 800×3 层 = 9600 verts / 2400 getBuffer，body-only ≡ 三层时间中的 1/3
> Double additive 未排序（sortOnUpload=false）后单体负载仍不可控，**只能靠减遍数**
> 不做 GPU instancing：INSTANCED_QUADS 能省 CPU 提交，但 **fragment/过绘的主因仍在**

⇒ 三层方案的成本 = **填率 ×3 量级**，不是 draw call 数量问题。结论"减遍数"是对的，
但代价是**把本体和辉光一起扔了**——本变更要在**单通**前提下把它们拿回来。

### 关键的空间事实

quad 的世界边长 = 实体 `size`（碰撞箱同源），**不可动**。
而贴图里当前只有 **48.7%** 面积可见 ⇒ **辉光可以住进同一张贴图的空白区，
quad 面积不变 ⇒ 填充率不涨**。当年之所以另起一层，不是"没地方画"，
而是 **alpha 混合画不出真辉光**（见 D5/D6）。

### 采样状态（实测 `TextureStateShard` 字节码）

`TextureStateShard` 的构造 lambda 会调用 `AbstractTexture.setFilter(blur, mipmap)`。
现役 `DanmakuRenderTypes` 一律 `new TextureStateShard(loc, false, false)`
⇒ **最近邻采样 + 无 mipmap**。这对硬边环勉强能看，对**软晕**是灾难：
弹在 10 格外时 quad 仅约 27 px 而贴图 64~128 px ⇒ 2~5 倍缩小 ⇒ 无 mipmap 的
最近邻会持续闪烁，且辉光会碎成块。**新贴图 MUST 走线性过滤 + mipmap。**

## Goals / Non-Goals

**Goals**

1. 球弹在**单 quad / 单 pass / 单 draw**前提下同时拥有**实心本体**与**外辉光**。
2. 辉光半径随弹体尺寸等比缩放。
3. 新旧观感可在**同一构建**内热切换，以便做严格的对照压测。
4. 把"弹幕能扛多少弹"从"2000 弹不掉帧、但不知道上限在哪"变成**有数据的事实**。
5. 实体路径与程序路径共用同一张贴图与同一组常量，不再分叉。

**Non-Goals**

- 不复活三层结构；不加任何额外 pass；不做 instancing；不用粒子做辉光。
- 不改模型类几何（五角星柱）、不改灵符、不改激光的渲染结构。
- 不动 `BalanceNumbers.DANMAKU_ENTITY_CAP`（平衡常量）。
- 不改服务端判定、同步、协议、存档。
- 不改 `danmaku-sphere` 之外的玩法语义。

## Decisions

### D1：单通路线（不复活三层）

**选**：球弹恒为 1 个 quad / 1 次 draw / 1 个 RenderType。

**理由**：当年的账已经算清——三层 = 填率 ×3，且 "Double additive 仍不可控"。
辉光必须**寄生在同一张贴图里**，而不是多画一遍。

**备选**：
- *两层（本体 + 加法辉光）*：填率 ×~1.8~2（辉光 quad 还大 1.35×），
  且历史上已实测"不可控"。**否决**。
- *预乘 alpha 单 pass（自定义 blend state + 自定义着色器）*：
  混合公式 `out = src + dst·(1-a)`，本体区 a=1 完全覆盖背景、光晕区 a=0 纯加法，
  **仍是 1 quad / 1 draw**，能同时拿到真加法辉光与白热核。
  技术上已核实可行（`TransparencyStateShard` 构造器 public、
  `RenderSystem.blendFuncSeparate(ONE, ONE_MINUS_SRC_ALPHA, …)` 存在、
  本仓已有 4 个自定义核心着色器可抄）。
  **本变更不做**——用户明确要求"改贴图实现，而不是再叠其他东西"，
  且自定义着色器 + 自定义混合状态的风险面显著大于换一张贴图。
  留作**后续独立变更**（见 Open Questions）。

### D2：新贴图用新文件名，不改旧图

**选**：新增 `textures/entity/sphere_danmaku_glow.png`；
`sphere_danmaku_lod.png` 原样保留（既是对照臂，也是回滚点）。

**理由**：新旧两张图的 **alpha 通道语义不同**（旧图 alpha = 覆盖度且带硬边台阶，
新图 alpha = 覆盖度但语义扩展到辉光区）。资源包若替换了旧图，
MUST NOT 被静默改造成新语义；反之资源包替换新图时也不该被旧语义约束。

**备选**：直接覆盖 `sphere_danmaku_lod.png` ⇒ 资源包生态被静默改写，**否决**。

### D3：新贴图规格

- **尺寸 128×128**（辉光带需要连续衰减；64×64 的辉光带只有 ~26 px 宽，
  在缩小时极易被 mipmap 抹平或走样）。RGBA，PNG。
- **RGB 通道恒为白**（`255,255,255`）：全部色相由顶点色给出，
  资源包替换不得带色（沿用 `danmaku-sphere`「Sphere texture asset」的既有约定）。
- **A 通道 = 覆盖度**（0 = 完全透明，255 = 不透明）。
- **径向剖面**（`d` = 归一化半径，0 = 中心，1 = 贴图半宽）——**「实心核 + 分离环 + 收窄外晕」**：

  | 区间 | A | 意图 |
  |---|---|---|
  | `d ≤ 0.50` | 255 | **实心核**，宽度 50%（旧 LOD 43.75% 且是硬边，读作甜甜圈） |
  | `0.50 < d ≤ 0.56` | 255 → 0（smoothstep） | 核的柔边 |
  | `0.56 ~ 0.58` | 0 | 窄缝：让环与核分开 |
  | `0.58 < d ≤ 0.66` | 0 → 215（smoothstep） | 环的内缘 |
  | `0.66 < d ≤ 0.72` | 215 → 0（smoothstep） | 环的外缘 |
  | `0.72 < d ≤ 0.80` | 0 → 48 | 外晕内缘 |
  | `0.80 < d ≤ 0.86` | 48 → 0 | 外晕外缘 |

  - **为什么是「核 + 环」而不是一坨渐变**：顶点色只能乘不能加（D5），
    贴图里做不出**比本体更亮**的环；而**分离的环**是单层里唯一能做出
    「球旁边有一圈」的手段。核给足 50% ⇒ 读作"一颗有环的球"，
    而不是旧 LOD 那种"小核 + 硬边粗环"的甜甜圈。
  - **外晕必须收窄**：可见外缘止于 `d ≈ 0.83`（原设计是 0.93）——
    辉光铺满整个 quad 时，弹读作"一团纯色球"，环完全看不见。
  - **辉光外缘靠原版着色器的 `discard`（`a < 0.1`）自然收口**：
    `a = 0.1` 处约在 `d ≈ 0.83` ⇒ 辉光既不无限扩散，
    **深度写入的边界也停在这条等值线上**（见 D7）。
- **生成方式**：复用 `tools/gen_danmaku_textures.py` 的**超采样程序化管道**
  （`make_sphere()` 已在此产出旧球），新增 `make_sphere_glow()`。
  **不新增逐像素脚本文件**，也不用 `tools/gen_tex.py` 的 ASCII + 调色板管道
  ——ASCII 调色板表达不了连续 alpha 衰减（`gen-textures` 技能的限制是针对**像素画**，
  而软晕是连续渐变，与 `make_sphere` 同族）。

### D4：辉光随 size 等比 —— 天然满足

贴图映射到 `size × size` 的 quad ⇒ 辉光半径 = `size × 0.41`（可见外缘 0.83×半宽）。
**与弹体尺寸严格成比例，无需任何额外参数或额外绘制。**

**代价（必须写进 spec）**：实心核宽度固定为 quad 的 50% ⇒
**判定箱（= size）与可见球（= 0.5×size）的比值不变**
（与旧球的 62%、旧 LOD 的 43.75% 相比更居中），
MUST NOT 因为"辉光吃掉了空间"而让球看起来比判定箱小。
若日后要调这个比值，走档案的 `visualScale` / `hitboxScale` 两个字段，**MUST NOT**
通过改贴图里的实心区比例来偷偷调判定。

### D5：纯贴图路线的硬限制 —— **没有白热核**

原版 `rendertype_entity_translucent.fsh` 的合成是
`out = tex.rgb × tint × light`，即 **顶点色只能"乘"、不能"加"**。
⇒ 同一张 quad 上**不可能**同时出现"纯白核 + 染色辉光"：
白核要求 rgb 独立于 tint，而乘法做不到。

**结论**：本变更的"发光"由 **不透明本体 + 软晕**构成（暗背景下读作发光的球），
**MUST NOT 在验收里要求白热核**。若日后必须要，只有两条路：
自定义着色器单 pass（D1 的备选），或第二层 pass（**已否决**）。

### D6：亮背景下的已知限制（alpha 混合的物理边界）

alpha 混合的合成是 `out = src·a + dst·(1-a)` ⇒ 半透明光晕**必然压暗背景**。
本仓球弹的顶点色是**饱和色**（弹幕随机取色），故亮地面上的光晕读作"染色污渍"而非光。

- **本变更接受该限制**：弹幕战斗主要发生在暗场景/夜晚/幻想乡维度；
  程序路径的 `billboards` 本身就是加法混合，天然无此问题。
- **验收口径**：暗背景下 MUST 读作"发光的球"；亮背景下 MUST NOT 出现
  "方块状硬边"或"比背景更暗的洞"，但**允许**读作染色晕。
- **未来出路**：D1 的预乘单 pass 路线（`a=0` 的辉光区是真加法），
  或把球弹本体改成加法混合（代价：密集弹墙会叠成白，隐藏态压暗失效）。

### D7：写深度 —— 保留现状，代价已算清

**现状就是写深度**（`translucentDepth` = alpha 混合 + `COLOR_DEPTH_WRITE`）。
用户要求"要写"，本变更**维持**。

- **新增的不是"写深度"，而是"辉光区也开始写深度"**：
  现役贴图的可见区（核 + 环）写深度，透明环缝被 `discard` ⇒ 不写。
  新贴图的辉光区 `a ≥ 0.1` ⇒ **会写深度**。
- **几何后果**：弹后的水/云被弹的**软圆轮廓**挖掉一块（不是方洞——
  深度写入的边界就是 `a = 0.1` 的等值线，形状是软圆）。
  这与激光的做法一致（激光的外发光层同样写深度，
  理由见 `LaserDanmakuRenderer` 的类注释："否则其光晕仍会被后画的水/云覆盖"）。
- **性能代价**：
  - 深度写本身：每多一个非 discard 片元多写一次深度缓冲，
    约等于一次 4 字节写，**远低于**帧缓冲的读改写（RMW）成本。
  - **真正的成本变化是 RMW 次数**，而它由贴图里「alpha ≥ 0.1 的片元占比」决定：
    旧 LOD 贴图约 **36%**（外缘那档 alpha 25 恰好被 `discard` 掉）、
    「整张实心 + 宽辉光」版约 **97%**、本设计的「核 + 环 + 窄辉光」版约 **43%**。
    ⇒ 相对**现役 LOD** 约 +19% 的混合片元，相对「宽辉光」版则是 **-2.3 倍**。
  - 片元总数**不变**（quad 面积不变），着色器调用数不变，draw call 与顶点数不变。
  - 辉光区写深度 ⇒ 弹后的水/云被挖掉的是**软圆轮廓**，
    其半径 = `alpha ≥ 0.1` 的等值线（`d ≈ 0.83`）⇒ 比「整张实心」版小得多。

### D8：压测夹具 —— 为什么 `/danmaku wall` 不够

`/danmaku wall N` 的几何：`side = ceil(√N)`，间距 1.2，网格在**眼睛高度的水平面**上，
位于 `look × 10` 处。

按 MC 默认 FOV 70（**垂直** FOV，16:9 下水平半角 51.2° ⇒ 可见宽 `2.49d`）估算：

| N | 网格半宽 | 深度范围 d | **视锥内弹数（估）** |
|---|---|---|---|
| 2000 | 27 格 | 0 ~ 37 | **≈ 970**（约 48%） |
| 6000 | 46.8 格 | 0 ~ 56.8 | **≈ 2560**（约 43%） |

两个问题：
1. **弹数 ≠ 屏上弹数**：N 涨 3 倍，屏上只涨 ~2.6 倍，且远弹只占几像素
   ⇒ 该夹具主要压 **CPU（每实体一次渲染调用）**，压不到**填充率**。
2. **墙是瞬态的**：弹以 0.1 格/tick 推进，100 tick 后撞到玩家即销毁，
   寿命仅 `period×20 = 800` tick（40 s），**撑不住 30 s 暖机 + 180 s 采样**。

**决策**：
- `/danmaku wall` 的**数量上限 2000 → 6000**（用户明确要求；供肉眼巡检与 CPU 压测）。
  它走 `addFreshEntity` 直连、**不经** `DanmakuEmitter` ⇒ **不受**
  `DANMAKU_ENTITY_CAP` 节流，**平衡常量不动**。
- **新增 `/danmaku screen <数量> [距离] [间距]`**：静止、无害（damage 0）、
  正对玩家的**竖直平面**弹墙，寿命覆盖采样窗口（≥ 6000 tick）。
  - 网格在垂直于视线的平面上 ⇒ **屏上弹数 = 可直接算出的量**：
    可见格数 = `(2.49d / spacing) × (1.40d / spacing)`。
  - `距离` 控制单弹屏幕尺寸（填充率主因），
    `间距` 控制重叠度（间距 < 弹径 ⇒ 大量重叠 ⇒ 最坏填充）。
  - 典型填充档：`screen 6000 6 0.35` ⇒ 单弹 ~45 px，
    6000 弹 ⇒ 约 12 M 像素/帧 ≈ **6 屏过绘**。

### D9：对照压测的形状 —— 同一构建热切换

**决策**：新增 `/danmaku texture lod|glow`（客户端命令，权限 2），
在**同一个二进制**内热切换球弹贴图。

- 换构建会把"贴图差异"和"代码差异"混在一起；热切换让两臂**只有贴图不同**。
- 两臂各自跑 30 s 暖机 + 180 s 采样，产出 `frames.csv` / `server.jsonl` /
  `proxy.jsonl` / `window.json` / `metadata.json`，
  **复用现成工具链**：`tools/baseline_window.py`（采样）、
  `tools/program_benchmark_run.py`（编排）、`tools/program_ab_report.py`（汇总）。
- **门槛**：新贴图臂的**帧时间 p95 相对旧贴图臂的劣化 ≤ 5%**；
  同时记录 p50 / p99 与 `DanmakuRenderProbe` 的 draw / 顶点 / getBuffer 计数。
- **必须同时记 2000 档**（用户诉求：原 2000 弹不掉帧，但不知上限在哪）⇒
  档位取 {2000, 4000, 6000}，两臂各跑一遍。
- **样本要求沿用 `program_ab_report.py` 的既有判据**：
  `warmupSeconds ≥ 30` 且 `sampleSeconds ≥ 180`，缺数据**不填 0**。

### D10：降级阶梯（若压测不达标）

按"观感损失从小到大"依次收：

1. **收窄辉光**（辉光带从 `d 0.72~1.00` 收到 `0.72~0.90`）⇒ RMW 面积减少。
2. **降辉光峰值 alpha**（92 → 64）。
3. **把本体实心区从 60% 收到 52%** ⇒ 不透明片元减少。
4. **降贴图到 64×64**（RMW 面积不变，省的是显存与采样带宽）。
5. **退回旧贴图**（`/danmaku texture lod` 即时回滚，无需重编）。

> 注意：1~3 改的都是**贴图内容**，**不改变 quad 面积** ⇒ 不改变 draw call 与顶点开销。
> 真正的性能杠杆只有 RMW 面积，而它由贴图里"非透明像素占比"决定。

### D11：渲染剖针修复

`/danmaku layers` 与 `/gs_boss danmaku` 里的 `glow` / `core` 计数**恒为 0**
（层被 `ALWAYS_LOD` 永久短路），诊断手段已失效。

**决策**：
- 剖针的 `body` / `glow` / `core` 三档**语义改为"实际绘制的层数"**，
  并新增一档 `pass`（每弹实际提交的 quad 数）——球弹恒为 1。
- `ALWAYS_LOD` 常量**保留**（它现在是"球弹恒单通"的事实来源），
  但 MUST NOT 再被读成"密度降级开关"；`effectiveGlow()` 的语义
  改为"是否绘制附加层"，球弹路径**恒不绘制** ⇒ 计数恒 0 是**正确的**，
  文档与命令输出 MUST 说清"球弹单层是设计，不是降级"。

### D12：两条路径共用贴图与常量

`ProgramDanmakuRenderer` 目前自己 hardcode `SPHERE` 与 `bodyType`；
`SphereDanmakuRenderer` 又有自己的一套。

**决策**：新贴图的 `ResourceLocation` 与 RenderType 选择**收敛到一处**
（`DanmakuRenderTypes` 或一个 `DanmakuBulletTextures` 常量持有者），
两条路径引用同一处。**MUST NOT** 出现"实体路径换了、程序路径没换"的分叉。

### D13：程序路径的 `bodyType` 与 `additiveSolid` 混用

程序路径的 `billboards`（装饰/贴片）走 `additiveSolid`，`members`（真正的弹）走
`bodyType`（alpha 混合）。**本变更只动 `members` 的贴图**，
`billboards` 的加法混合**不动**（它们不是弹）。

**注意**：加法混合的 `billboards` 与 alpha 混合的 `members` 若共用一张新图，
新图的辉光区在加法路径上会**额外叠加**一层光 ⇒ 观感与实体路径不同。
⇒ **新贴图只给 alpha 混合的弹用**；程序路径的 `billboards` 若引用同一张图，
MUST 换回旧图或接受差异（本变更的实现取"换回旧图"）。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| **帧缓冲 RMW 翻倍**（不透明片元 48.7% → ~95%）导致填充率劣化 | D9 的 p95 ≤ 5% 门槛 + D10 的降级阶梯；必要时收窄辉光/收小实心区 |
| **无 mipmap/最近邻采样**让软晕碎成块并持续闪烁 | 新贴图走**线性过滤 + mipmap**（需给 `DanmakuRenderTypes` 加一个带过滤的 `translucentDepth` 变体；混合/深度/剔除状态完全复用，只换 `TextureStateShard(loc, true, true)`） |
| **辉光区写深度**在水/云上挖出软圆洞 | 与激光的既有做法一致；洞的形状是软圆不是方块；验收项 4 盯这条 |
| **"白热核"无法实现**（D5） | 已在 spec 与验收里写死：本体+软晕即"发光的球"；白热核留作后续自定义着色器变更 |
| **亮背景下光晕读作污渍**（D6） | 已列为已知限制；战斗主场景为暗背景；程序路径 billboards 本就是加法混合 |
| **压测夹具与真实战斗负载不一致**（screen 是静止平面墙，真实弹幕在动） | 两臂同夹具同机位，**差值**只反映贴图；另用 `/danmaku wall` 跑动态档交叉验证 |
| **6000 弹的网络突发**（6000 个生成包）污染帧时间读数 | 30 s 暖机覆盖突发；两臂同量，差值抵消；`proxy.jsonl` 记录线速 |
| **压测本身依赖真实客户端 + RCON + 中继** | 复用现成工具链（`program_benchmark_run.py` 等），不新造轮子；缺数据不填 0 |

## Migration Plan

1. **新增**新贴图与生成脚本函数；`/danmaku texture` 默认为 **`glow`**（新观感）。
2. 实体路径与程序路径切到新贴图（共用常量，D12）。
3. `/danmaku wall` 上限提到 6000；新增 `/danmaku screen`。
4. 剖针改语义（D11）。
5. 跑对照压测（D9），按 D10 阶梯调参直至达标或回落到 `lod`。

**回滚**：`/danmaku texture lod` 即时回滚（旧图与旧路径都还在）；
最坏情况把默认值改回 `lod` 重编即可，无存档/协议/服务端影响。

## 对照压测结论（2026-10-20，用户实机）

**结论：6000 弹规模下不掉帧。** 压测由用户在本机实机执行（新旧贴图对照），
**原始 p50/p95/p99 数值未随本变更入库**——需要做长期基线对比时应当回填。

> 记录口径说明：本节只写实际发生的事。下面的"理论增量"是设计期的估算，
> 压测结论是实机观察；两者不是同一回事，故分列。

### 理论增量（设计期估算，供后人对照）

本变更改的是**贴图内容**，而贴图内容唯一影响的是**帧缓冲读改写（RMW）次数**：

| | 参与混合的片元占比（alpha ≥ 26） | 相对现役 |
|---|---|---|
| 旧 LOD（`sphere_danmaku_lod.png`） | 36.1% | 基准 |
| 新贴图（核+环+窄晕） | 43.1% | **+19%** |
| （第一版"整张实心+宽辉光"，已废弃） | 97% | +169% |

其余成本项**逐位不变**：quad 面积（= `size`）、draw call 数、顶点数、
批次数、排序开销、着色器调用数。

⇒ 理论增量有界（混合片元 +19%），实机观察与之一致（不掉帧）。

### 复现步骤（留档）

1. 起服 + 起客户端 + 计费中继（`tools/program_benchmark_run.py` 依赖这三件已在跑）。
2. 客户端内建弹墙：`/danmaku screen <数量> <距离> <间距>`
   —— 推荐 `6000 6 0.35`（单弹 ~45 px ⇒ 约 6 屏过绘，最坏填充）。
   弹是静止、无害、寿命 6000 tick ⇒ 撑得住 30 s 暖机 + 180 s 采样。
3. 采样：`tools/baseline_window.py`（产出 `frames.csv` / `server.jsonl` /
   `window.json` / `proxy.jsonl` / `metadata.json`）。
4. 汇总：`tools/program_ab_report.py`（p50 / p95 / p99）。
5. 档位 {2000, 4000, 6000} × 两臂：
   - 旧臂：客户端命令 `/gs_bullet texture lod`
   - 新臂：客户端命令 `/gs_bullet texture glow`
   （两臂**采样设置相同**、只有贴图内容不同 ⇒ 差值就是纯贴图成本。）
6. `/gs_boss danmaku` 的 `renderProbe[body=… glow=0 core=0 quads=… verts=… getBuffer=…]`
   可核对「球弹恒单层」这一读数口径。

### 门槛与降级（若日后复测超标）

**新臂 p95 相对旧臂劣化 MUST ≤ 5%**。超标则按 tasks 4.4 的降级阶梯处理
（收窄辉光 → 降辉光 alpha → 收小实心核 → 贴图降 64×64 → 回滚 `lod`），
**降级只改贴图内容，不改 quad 面积与 draw call 数**。

## Open Questions

1. **是否接受"没有白热核"**（D5）？若不接受，本变更应改为走自定义着色器单 pass，
   范围与风险都要重估。
2. **辉光峰值 alpha 92 是否偏高**？6000 弹同屏叠加时可能把局部推白；
   需在压测档位上目视确认。
3. **要不要顺带把 `visualScale` / `hitboxScale` 的比例调一下**（可见球 0.6×size
   vs 判定箱 1.0×size）？属判定手感问题，**建议另立变更**，MUST NOT 混进本变更。
4. **`/danmaku screen` 的默认距离/间距**取多少？需与真实弹幕的典型屏幕尺寸对齐
   （真实弹幕 0.28~0.8 格，10~30 格外）。
5. **压测机位与客户端参数**（分辨率、视距、压缩）需要固化到 `metadata.json`，
   沿用 `program_ab_report.py` 的字段清单即可。
