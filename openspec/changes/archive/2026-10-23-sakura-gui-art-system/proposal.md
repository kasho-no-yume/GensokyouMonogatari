# 樱符 GUI 美术系统

## Why

三条理由，全部来自实测：

**1. 现有占位美术与题材严重脱节。**
九个 GUI 面板里，只有**仪式核心**有背景贴图，而那张图是 1px 紫色描边 + 近黑底；
其余七个面板——无尽藏（306×264）、仪式构建器（264×196）、仪式编辑器（268×208）、
无尽藏晶（184×250）、造景（176×150）、灵弹（176×152）、对话——**全部靠
`graphics.fill()` 画纯色矩形**。项目本体是东方和风题材，这套是纯程序员美术。

**2. 产线已经跑通，但没有落成规格。**
「AI 出材质与装饰 → 程序定结构」这条产线，经过 6 次实测生图 + 3 版实装验证已经成立
（材质件 t2i、布局锁定 multi_edit、粗简大形 prompt 纪律、整数比降采样收口、
结构层重铺）。但它**全部活在 `build/guiart/` 的临时脚本里**：没有规格、没有可复用的
调用方法、没有 prompt 纪律的成文约定、没有成本模型。下一个人接手只能重读一遍对话。

**3. 逐面板各自烘焙会风格漂移，除非共用同一套素材与规范。**
九个面板尺寸从 176×150 到 306×264 各不相同。若各画各的，跨面板的纸色、花瓣分布、
边框粗细**不可能对齐**；改一个色调要重出九张。一致性 MUST 由「共用素材件 + 共用
prompt 纪律 + 共用收口脚本 + 共用调色板」保证。

## 九宫格：这个反问的实测答案

**「背景完全可以是九宫格的吧？」—— 能，但九宫格本身不是最优解，而且「拆零件复用」
这条路对烘焙整图也不成立。**

做了两轮**零 API 成本**的装配实验（`build/guiart/kit_experiment*.py`）：把已烘焙的 A 版拆成
「平铺纸底 + 程序化外框 + 抠出来的装饰 sprite」，重新装配成 176×234，与烘焙整图版并排。

### v1（朴素平铺）暴露的四个缺陷

| 缺陷 | 实测现象 | 根因 |
|---|---|---|
| **纸底平铺露接缝** | 顶栏能明显看到 tile 边界造成的色差带 | 纸底有渐变 + 花瓣分布不规律，缩到 128² 后平铺必然重复 |
| **装饰件抠图带底** | 樱枝与樱印周围出现**矩形色块** | 从烘焙整图裁 sprite 会连原纸底一起裁进来 |
| **卡片底色丢失** | 卡片内部变成纯白 | 卡片的柔和底色是 AI 烘焙的，零件化后无处可寻 |
| **软装饰丢失** | 金角括号消失 | 角括号是 AI 画进卡框的，不是独立零件 |

### v2（去渐变平铺 + 色键抠 alpha）仍追不平

补上「去大尺度渐变只留纸纹高频」与「色键算 alpha」之后，装饰件确实抠出来了，
花瓣也能独立布点，但**仍有两处结构性缺陷**：

1. **装饰 sprite 必然带原纸底残留** —— 色键是「按与纸底的距离算 alpha」，纸底附近的像素
   永远带着半透明纸色，贴到别处就是一圈矩形浅晕。这是色键的固有代价，
   **从烘焙图拆就修不掉**。
2. **「半结构半装饰」的成分无处可归** —— 卡片柔和底色、金角括号、外框金线，
   它们既不是纯结构也不是纯装饰，烘焙时是一起画的，拆开后必然丢失或需要重做。

⇒ **结论：九宫格/零件复用这条路对「烘焙整图」不成立。**
九宫格要求边条可拉伸无失真，而烘焙边框含枝/印破坏了该前提；中心块平铺则纸纹渐变与
不规律花瓣分布必然重复；拆零件则装饰永远带着原纸的残影。

### 主线：逐面板烘焙整图，靠「共用素材」保证一致性

跨面板一致性 MUST 由以下**共用**保证，而不是由共用零件保证：

| 共用件 | 作用 |
|---|---|
| 同一张材质件（`image_2`） | 纸色、花瓣质感、光晕倾向一致 |
| 同一套 prompt 纪律 | 风格倾向一致 |
| 同一个收口脚本 + 同一套调色板 | 量化、光照、结构层完全一致 |
| 同一份布局规范 | 卡片等高、无通栏硬线、控件不越框 |

⇒ **每个需要氛围的面板各烘焙一张整图（1 次 API 调用）**，代价 $0.02~0.03，可忽略；
换来的是**与 A 版同等的品质**。9 个面板全做完，总成本 < $0.3。

### 零件套件：只给小面板 / 降级路径

若某面板**不需要自然氛围**（造景 176×150、灵弹 176×152、对话），或某次没有生图预算，
则 MAY 用「程序化边框 + 平铺纸底」的无氛围版本，**0 次 API 调用**。
此时装饰 MUST 为**专门生成的带 alpha sprite**（MUST NOT 从烘焙图抠 —— 实测证明那会带残影），
或直接不要装饰。

## What Changes

1. **规格**：分辨率宪法（1 texel = 1 逻辑像素）、三层分工、樱色系调色板单一色源。
2. **规格**：AI 生图的完整调用方法 —— 端点、模型、工作流、参数、三类调用形态、
   prompt 纪律、降采样收口流程、成本模型。
3. **规格**：适用场景判定表 —— 同一件美术该走 AI、ASCII、程序化哪条路。
4. **规格**：跨面板一致性的保证方式（共用素材件 + 共用规范），以及九宫格/零件复用的
   否决理由与适用边界。
5. **实现**：仪式核心界面 v2 布局（已完成，见 tasks）。
6. **任务**：九个面板的改造顺序与统一验收。

## Non-Goals

- **不改任何玩法语义**。本变更只动像素与布局坐标，不动配方、槽位索引、存档格式。
  槽位**索引**不变、只改像素坐标，故存档兼容。
- **不做 HD 资源包**。全部资产按 1:1 逻辑像素产出，不引入 2×/4× 落盘（见下）。
- **不追求 AI 出成品像素图**。AI 只出材质与装饰的大形，最终像素栅格 MUST 由程序收口。
- **不改原版 Button 外观**。按钮仍走原版 widgets 图集，只是位置随新布局调整。
- **不做「一套零件通吃所有面板」**。实测证明那条路品质下降，本变更以「品质与 A 版持平」
  为首要目标，一致性靠共用素材与规范达成。

## 验收

- 每个被改造的面板 MUST 有一张人工眼检通过的成品图存档在仓库外（`build/guiart/versions/`），
  且 MUST 在实机 1080p（guiScale=4）下确认过文字可读、无糊字。
- 规格 MUST 写明「API 调用方法」与「适用场景」，使下一个面板的改造 MUST NOT 依赖本次对话记录。
- 后续面板的成品 MUST 与仪式核心 A 版**并排目检无明显风格落差**。
