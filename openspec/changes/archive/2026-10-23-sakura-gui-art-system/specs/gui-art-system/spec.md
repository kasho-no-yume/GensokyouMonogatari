## ADDED Requirements

### Requirement: GUI 贴图 SHALL 遵守 1 逻辑像素 = 1 texel 的分辨率宪法

所有 GUI 贴图 MUST 按 **1 texel = 1 逻辑像素** 产出并按 1:1 绘制，
即贴图尺寸 MUST 等于它在面板坐标系里占据的尺寸。

MUST NOT 产出 2×/4× 落盘后按比例降尺寸 blit 的贴图：MC 的 GUI 纹理是 NEAREST 过滤，
2:1 最近邻降采样会丢掉一半像素、锯齿并糊掉边缘。

**唯一例外：BOSS 咒符条血条。** 它 MUST 按 **1080p 物理像素**产出
（182×36 逻辑 × guiScale 4 = **728×144 texel**），见下方「BOSS 血条」那条 requirement。
理由：血条是 HUD 上最大的单件美术，而 182×24 只有 4368 texel、端头柱仅 22×20 逻辑像素，
扩散模型无处落笔；按物理像素产出后，默认 1080p 下仍是 **1 texel = 1 物理像素、零缩放**。
代价是玩家把 guiScale 调到 4 以下时会被降采样 —— 已知并明确接受。
其余所有面板 / 按钮 / HUD 贴图 MUST 继续遵守本宪法。

**理由（实测）**：1080p 下 MC 的 auto GUI scale = 4（`windowHeight/240` 取满足 320×240
的最大倍率）。182 逻辑像素的血条在屏上占 728 物理像素。按 1:1 逻辑像素绘制时，
每个 texel 放大成干净的 4×4 物理像素块；这既是原版 GUI 在任何 guiScale 下都锐利的原因，
也意味着**贴图的 texel 数直接等于设计信息量**。

#### Scenario: 面板底图按面板尺寸 1:1 产出
- **WHEN** 改造一个 176×234 的面板
- **THEN** 其背景贴图 MUST 是 176×234，MUST NOT 是 352×468

#### Scenario: 换低 GUI 缩放不糊
- **WHEN** 玩家把界面尺寸调成 1 或 2
- **THEN** GUI MUST 仍为锐利的像素块放大，MUST NOT 出现降采样锯齿

### Requirement: 美术 SHALL 分为材质装饰层与结构层两层且分工 MUST NOT 混淆

美术 MUST 分为两层，且每一层的产出手段 MUST 固定：

**材质装饰层**（有机质感：纸纹、花瓣、枝、印、光晕）—— 由 AI 扩散模型生成，
或由 ASCII 数据生成，产出的是**大形与明暗层级**，MUST NOT 追求微观纹理。

**结构层**（坐标锁死的一切：卡框、分隔线、槽格、电池槽框、面板外框）—— MUST 由
程序或 ASCII 数据绘制，MUST NOT 由 AI 生成。

理由（实测）：AI 出的「唐草卷云纹」在 14 texel 宽的边框里经 5× 降采样后糊成一坨
红褐色，完全读不出是云纹；而同一张图里的**和纸底**在同样倍率下依然干净可读。
**微观纹样的信息量随栅格缩小而崩塌，宏观大形不会。**

#### Scenario: 小尺寸边框不靠 AI 出纹样
- **WHEN** 需要一个 46×24 的端头装饰
- **THEN** 其 MUST 是单一大形（一枚印 / 一个符号），MUST NOT 是卷草/缠枝一类细纹样

#### Scenario: 结构元素由代码绘制
- **WHEN** 面板上有槽格网格、卡框、分隔线
- **THEN** 它们 MUST 由程序按硬编码坐标绘制，MUST 与贴图内容解耦

### Requirement: 樱色系调色板 SHALL 有单一色源

樱符主题的调色 MUST 由**一组代码常量**定义（Java 侧），所有面板的绘制 MUST 取自该组常量，
MUST NOT 在贴图里硬编码色相。

至少覆盖：纸底、卡面底、槽内凹底、樱粉主线、樱粉暗调、樱深红强调、金色点缀。
槽位与状态色（✓/✗/进度条）另走一套，不得混入装饰色。

理由：本项目已有 `TierPalette` 作为品阶色单一色源的先例（见 `openspec/project.md` §5.4）。

**Java 侧与 Python 侧 MUST 逐值一致。**
Python 侧 `tools/textures/gui_sakura.py` 的 `PAL` 是烘焙侧的色源，Java 侧对应
`SakuraPalette` 常量组；两者 MUST 由**测试**逐值比对（改了任一侧而忘了另一侧 MUST 让测试变红）。
理由：樱粉一度同时存在 0xC77A92 / 0xC87A92 / 0xCB7A92 三个值，
跨面板对不上颜色时无从查起（实测）。

#### Scenario: 槽框描边色随主题走
- **WHEN** 主题从朱红改为樱粉
- **THEN** 槽框描边色 MUST 由该常量组决定，MUST NOT 仍留在旧主题的亮紫

#### Scenario: Java 与 Python 调色板一致
- **WHEN** 改动 Python 侧 `PAL` 的任一色值
- **THEN** 未同步改 `SakuraPalette` 时一致性测试 MUST 失败

### Requirement: 搜索框 SHALL 保留原版编辑能力而由程序绘制外观

搜索框 MUST 继承原版 `EditBox`（不重写光标 / 选区 / 剪贴板 / 中文 IME），
但 MUST 由程序绘制全部外观。

三条硬约束：

1. **凹槽是结构层，MUST 由程序绘制**，MUST NOT 烘焙进面板贴图
   （面板贴图里那圈凹槽位只负责把该区域**抹平**，避免 AI 在那儿画东西）。
   理由：聚焦态要随焦点实时变化，烘焙做不到；且结构层本就归程序。
2. **`setBordered(false)` 之后文字 MUST 重新定位。**
   原版 `EditBox#renderWidget` 里 `k = bordered ? getY() + (h - 8) / 2 : getY()` ——
   去掉边框后文字会贴到控件左上角。故控件 MUST 摆在<b>正文位置</b>
   （凹槽内缩 4px / 3px，尺寸 (宽−8, 8)），8 = 字形实占高度。
3. **命中区 MUST 覆盖整条凹槽**：控件本体只有 8px 高，
   凹槽上下各 3px 点不到 → MUST 覆写命中判定。
4. **正文 MUST 关闭投影（`dropShadow = false`）。**
   原版 `EditBox#renderWidget` 用的 5 参 `drawString` 默认带投影，投影色是
   `(color & 0xFCFCFC) >> 2`：墨色 `#4A1A2C` 的投影约 `#12060B`，在浅粉凹底上
   等于每个字右下角多一块近黑实心像素；guiScale=4 下那是 4×4 物理像素鬼影，
   中文笔画密，实机读作「字发糊、双份」。
   `EditBox` 的投影写死在 `renderWidget` 内、没有可覆写的开关 → MUST 整段接管绘制
   （正文 / 光标 / 选区都自绘），并镜像父类的 `displayPos` / `highlightPos`
   （两者只经 public 的 `setCursorPosition` / `setHighlightPos` 写入）以保持滚动与选区一致。
   「追加态」光标（顶到长度上限时画竖线）MUST 用墨色，MUST NOT 沿用原版的浅灰
   `0xFFD0D0D0` —— 浅灰在浅粉凹底上看不见。

#### Scenario: 搜索框外观是樱符的
- **WHEN** 打开带搜索框的面板
- **THEN** 输入区 MUST 是和纸凹槽 + 樱粉描边，MUST NOT 是原版灰盒

#### Scenario: 聚焦有可见反馈
- **WHEN** 搜索框获得焦点
- **THEN** 描边 MUST 由樱粉转金，MUST NOT 无任何变化

#### Scenario: 凹槽任意位置都能点到
- **WHEN** 点击凹槽上下边缘（不在 8px 正文行内）
- **THEN** 搜索框 MUST 获得焦点

#### Scenario: 浅底深字不带投影
- **WHEN** 搜索框内有输入内容
- **THEN** 字形 MUST 不画 1px 投影，MUST NOT 出现与正文同色的偏移重影

### Requirement: HUD SHALL 用樱符控件且 MUST 避开原版占位

HUD（灵力条 + 技能槽）MUST 使用樱符主题控件，
且 MUST NOT 与原版底部中央的固定元素重叠。

原版底部占位（1080p / guiScale=4 → 逻辑 480×270）：

| 元素 | y |
|---|---|
| 选中物品名浮字 | H-59 |
| 状态行（心 / 饥饿 / 护甲） | H-39 |
| 经验条 | H-29 |
| 快捷栏 | H-22 |

四条硬约束：

1. **灵力条 MUST 竖排贴左缘**，高约屏高的 1/3。
   理由：底部中央那条带子已被原版占满，且**别的 mod 也常在那儿放东西**；
   左侧中部相对干净。聊天框会盖住竖条下沿 —— 这是**有意接受**的取舍。
2. **灵力条 MUST 只显示比例，MUST NOT 显示具体数值。**
   5 阶上限 1000 万，写成 `10000000 / 10000000` 要 116px，早就出了屏幕。
   比例靠填充长度 + 25/50/75% 刻度表达。
3. **填充色 MUST 取自品阶色单一色源**（`TierPalette`），
   而 MUST NOT 用装饰色（樱粉）—— 灵力值与「多少」有关，与主题无关。
   ⚠️ 刻度 MUST 画在<b>框侧的樱粉带</b>上，MUST NOT 画进槽里：
   3 阶是金（0xFFC107），金色刻度落进金色填充会消失。
4. **技能槽 MUST 为 24×24 符印格；键位标签 MUST 画在槽下方**，
   MUST NOT 压在图标上（旧版把 `G+N` 画在图标左上角、冷却秒数画在图标正中，
   图标被两层信息盖住）。冷却时 MUST **压暗整格**让秒数跳出来。

**z-order 硬约束（实测踩过）**：HUD 层渲染时**深度测试是开着的**
（`Gui#render` → `enableDepthTest()` → 渲染全部 GUI 层 → `disableDepthTest()`），
且 GUI 里 **z 越大越靠前**，物品固定画在 `z=150`。
故任何要盖在物品上的东西（压暗遮罩、冷却秒数）MUST 用 `z > 150`
（本作取 200），MUST NOT 用默认的 z=0 —— 否则会被物品**挡在后面**，
表现为「符卡图标压在冷却数字上面」。

#### Scenario: 灵力条不与原版浮字叠字
- **WHEN** 切换快捷栏物品（原版在 H-59 浮出物品名）
- **THEN** 屏幕 MUST NOT 出现数字与物品名叠在一起（旧版把数值画在 H-59，必然叠字）

#### Scenario: 冷却秒数盖在图标之上
- **WHEN** 技能槽处于冷却
- **THEN** 冷却秒数与压暗遮罩 MUST 以 z > 物品 z 绘制，MUST NOT 被图标遮挡

#### Scenario: 高阶时数值不出屏
- **WHEN** 灵力上限为 1000 万
- **THEN** HUD MUST NOT 渲染 19 字符的数值，MUST 只显示比例

#### Scenario: 技能图标不被信息盖住
- **WHEN** 某个槽处于冷却
- **THEN** 键位标签 MUST 在槽外，图标区 MUST 只剩压暗后的图标与秒数

### Requirement: BOSS 血条收口 MUST 保留自然轮廓并对齐实际槽口

BOSS 边框收口 MUST 在缩放前去除白底与白色混边，并使用预乘 alpha 缩放。
MUST NOT 为统一外形而补出贯穿画布的矩形纸底，MUST NOT 强制自然边缘全部不透明。
血槽 MUST 映射到 texel `[88,640) × [80,112)`，装饰与框体 MUST 共用横向映射。
窗口坐标 MUST 以用户框选为准；MUST 保留伸入槽内的装饰，血量先绘制、外框及装饰后绘制。
MUST NOT 将整块窗口清空或人工补直线内唇；窗口中心读数区 MUST 保持通透。
槽内与外侧散布装饰 MUST 使用强于和纸框的去白策略，剔除浅色底雾并保留有色纹样；
MUST NOT 为保留装饰而连带保留大片浅白背景。
含金光、裂痕的窗口若检测不可靠 MUST 使用人工审定坐标；坐标 MUST 绑定原图版本。

#### Scenario: 自定义宽度的填充与开槽一致
- **WHEN** 五阶贴图按 120/160/182/240/300/400 逻辑宽度渲染
- **THEN** 装饰 MUST 随框体映射并覆盖在血量之上，中心读数区 MUST 保持通透

### Requirement: AI 生图 MUST 按三类调用形态使用且 MUST 有 prompt 纪律

AI 扩散生图 MUST 只用于材质装饰层，且 MUST 区分三类调用形态：

| 形态 | 目的 | 参考图 | 典型输出尺寸 |
|---|---|---|---|
| **材质 t2i** | 纸底、花瓣、光晕等可平铺/可复用的素材 | 无 | 1024×1024 |
| **布局锁定 multi_edit** | 把已有占位图重绘成成品面板 | `image_1` = 结构草稿，`image_2..N` = 材质件 | 目标尺寸 × 整数倍 |
| **装饰件 t2i/multi_edit** | 独立 sprite（枝、印、单瓣） | 可选 | 512×512 前后 |

**prompt 纪律（实测得出，MUST 遵守）：**

1. **要「粗」，不要「精细」。** 提示词 MUST 明确要求 `bold simple shapes`、
   `NO fine filigree`、并写明「缩到 N 像素宽后仍可读」。只说「精致」会让模型加细节，
   而细节在降采样后必然消失。
2. **降采样比 MUST 是整数倍。** 目标尺寸 MUST 取目标 × 整数 k（如 176×234 → k=5 得
   880×1170 ≈ 1MP，恰在模型甜区）。非整数比会产生不等宽的像素格。
3. **布局靠参考图锁，不由文字描述锁。** MUST 传结构草稿当 `image_1`（编辑目标），
   让模型自己读图；文字里 MUST NOT 试图描述坐标。
4. **MUST NOT 要求模型出文字。** 模型的图内文字渲染虽强，但 GUI 上会出现不可控的字形。
5. **negative prompt 在 cfg=1.0 下无效**（官方路径 cfg 固定 1.0），MUST 靠正向描述规避。

#### Scenario: 布局由参考图锁住
- **WHEN** 用 multi_edit 重绘面板
- **THEN** 外框、卡片、槽格阵 MUST 与 `image_1` 的位置逐像素一致

#### Scenario: 提示词写粗不写细
- **WHEN** 提示词要求边框
- **THEN** 它 MUST 要求粗/大形/低细节，MUST NOT 要求精细纹样

### Requirement: AI 出图 MUST 经收口流程量化成项目像素画

AI 产出的高分辨率原图 MUST NOT 直接进游戏，MUST 经过程序化收口：

1. 目标尺寸 × 整数倍生成 → **预乘 alpha** 的 LANCZOS 缩放到 1:1
2. **alpha 二值化**（在量化之前，否则羽化边会变成脏边）
3. **量化到固定调色板** —— **默认关闭**。实测：22 色固定量化会把樱枝洗白、纸面渐变压平，
   并把贴图里的 1px 金线打成黄虚线，品质反而下降；已认可的仪式核心 A 版就是**未量化**的。
   仅当原图过于「绘画感」时才手动量化，且 MUST 用**固定调色板**（MUST NOT 用自适应
   MEDIANCUT —— 那会让每个面板各调出一套色，跨面板立刻漂移）
4. **结构区擦除**：AI 在结构坐标附近画错的线 MUST 被擦掉，改为纯底色。
   擦除 MUST 只覆盖**边缘窄带**，MUST NOT 整片擦卡片 —— 卡片内部有 AI 画的柔和底色与装饰，
   整片擦会把手绘质感抹平成一块死色
5. **ASCII 零件叠加**：道具格等重复件 MUST 由 ASCII 数据生成后平铺，
   MUST NOT 手绘成一片（N 个格子 = 1 个 18×18 sprite + 程序复制）
6. **光照统一**：左上高光 / 右下暗部

#### Scenario: 降采样后仍是干净像素画
- **WHEN** 一张 1024² 原图被收口到 176×234
- **THEN** 结果 MUST 是硬边像素块，MUST NOT 有半透明羽化边或彩色噪点

#### Scenario: 重复件用 sprite 平铺
- **WHEN** 面板有 27 个物品格 + 9 个快捷栏格
- **THEN** 它们 MUST 由同一个 18×18 ASCII sprite 复制而成，MUST NOT 逐格手绘

### Requirement: 跨面板一致性 MUST 由共用素材与规范保证而 MUST NOT 靠共用零件

需要氛围的面板，MUST 各自烘焙一张整图；跨面板的一致性 MUST 由下列**共用件**保证：

| 共用件 | 保证的一致性 |
|---|---|
| 同一张材质件（作为 multi_edit 的 `image_2`） | 纸色、花瓣质感、光晕倾向 |
| 同一套 prompt 纪律（见「AI 生图」那条 requirement） | 风格倾向、细节密度 |
| 同一个收口脚本 + 同一套调色板常量 | 量化结果、光照方向、结构层像素 |
| 同一份布局规范（见「面板布局」那条 requirement） | 卡片等高、无通栏硬线、控件不越框 |

底图 MUST NOT 采用九宫格方案，MUST NOT 采用「把烘焙整图拆成零件再平铺/复用」的方案。

**实测否决理由（两轮零成本装配实验）**：
① 九宫格要求边条可拉伸无失真，而烘焙边框含枝/印破坏该前提；中心块平铺则纸纹渐变与
不规律花瓣分布必然重复，实测可见明显接缝带。
② 从烘焙整图抠装饰件必然带原纸底残留 —— 色键按「与纸底的距离」算 alpha，纸底附近的
像素永远带半透明纸色，贴到别处就是一圈矩形浅晕。
③ 卡片柔和底色、金角括号、外框金线这类「半结构半装饰」的成分，烘焙时是一起画的，
拆开后无处可归，必然丢失。

#### Scenario: 新面板走烘焙路线
- **WHEN** 改造一个需要氛围的新面板
- **THEN** 它 MUST 用同一张材质件 + 同一套 prompt 纪律 + 同一个收口脚本烘焙一张整图

#### Scenario: 后续面板与 A 版无风格落差
- **WHEN** 新面板的成品与仪式核心 A 版并排目检
- **THEN** 纸色、花瓣质感、边框粗细 MUST 无明显落差

#### Scenario: 不从烘焙图拆装饰件
- **WHEN** 需要一个独立的樱枝 sprite
- **THEN** 它 MUST 由 AI 专门生成并自带 alpha，MUST NOT 从烘焙整图裁剪

#### Scenario: 无氛围小面板允许零调用
- **WHEN** 改造一个不需要自然氛围的小面板（造景 / 灵弹）
- **THEN** 它 MAY 用「程序化边框 + 平铺纸底」实现，MUST NOT 产生 API 调用，
      且 MUST NOT 出现装饰 sprite 的矩形残影

### Requirement: 按钮 SHALL 用九宫格贴图且 MUST 满足可拉伸约束

按钮边框 MUST 走九宫格：按钮**宽度随文字长度变**（中文 2 字与英文 12 字符差 5 倍），
九宫格正是这类控件的标准解法；这与「面板底图 MUST NOT 用九宫格」并不矛盾 ——
两者的差别在**边条是否可拉伸**。

九宫格贴图 MUST 满足三条可拉伸约束：

1. **斜面只做上下**。左右边条被纵向拉伸，竖向斜面会让它竖向不均匀 -> 拉伸出横向条纹。
   顶高光放上边条、底阴影放下边条（两者横向拉伸，每行水平均匀 -> 仍是 1px 厚）。
2. **左/右边条每列竖向同色**。
3. **中心为纯色**（中心块被双向拉伸，非纯色会被抹花）。

cap 的选择 MUST 使「中心高度」能整除本项目的全部目标按钮高度，
使纵向缩放不产生半像素（本项目：20/16/14/12，cap=6 -> 中心 8/4/2/0，全部整除）。

MUST 提供 normal / hover / disabled 三态。

**按钮体内的纹理 MUST 程序化逐像素绘制，MUST NOT 烘焙进贴图。**
九宫格的中心区是双向拉伸的，烘焙进去的散点在按钮变宽时会被拉成横条。
程序化逐像素画则永远是 1px 点，形状不变；位置按按钮坐标取种子 -> 逐帧稳定不闪烁。

**主体色 MUST 取自项目调色板**（与面板里的强调色同源），
MUST NOT 用近黑色系 —— 近黑在浅粉面板上读作「一块黑」，与主题完全脱节。

**MUST 有本地目检手段。** {@code GuiGraphics.blit} 的两个重载参数顺序不同
（9 参是 1:1 裁切 {@code (atlas,x,y,uOffset,vOffset,width,height,texW,texH)}，
11 参是拉伸 {@code (atlas,x,y,width,height,uOffset,vOffset,uWidth,vHeight,texW,texH)}），
**写错不报错，只是画错**（实机表现为「0 尺寸的块 + 采错源区域」，画面直接崩坏）。
故 MUST 提供一个用**与 Java 完全相同的逻辑**在本地渲染全部目标尺寸的预览脚本，
改完九宫格逻辑 MUST 先过本地目检再进游戏。

⚠️ 预览脚本本身 MUST **真的模拟拉伸**（源区域 resize 到目标尺寸）。
用 1:1 粘贴的预览会「看起来通过」而实机是坏的 —— 本轮就踩过。

- **WHEN** 按钮文字从 2 个汉字变成 12 个英文字符
- **THEN** 按钮边框 MUST 仍然四边等宽、无拉伸失真

- **WHEN** 改动按钮的九宫格切分逻辑
- **THEN** MUST 先用本地预览脚本渲染出全部目标尺寸的图并目检，MUST NOT 直接进实机

### Requirement: 每件美术 MUST 有明确的适用场景判定

选择产出手段时 MUST 按下表判定，MUST NOT 凭偏好：

| 目标 | 手段 | 理由 |
|---|---|---|
| 和纸/纸纹/光晕/散布花瓣 | AI 材质 t2i | ASCII 画不出有机质感 |
| 单个大形装饰（印/符号/单瓣） | AI 装饰件 t2i | 需自然轮廓与明暗 |

| 按钮边框 | **九宫格贴图**（ASCII 画） | 宽度随文字变、边条规整可拉伸 |
| 面板外框、卡片底 | 程序化绘制 | 简单且必须精确 |
| 面板整体底图（需自然分布的装饰） | AI 布局锁定 multi_edit，每面板一次 | 平铺无法替代不规律分布 |

### Requirement: 樱符滑块 SHALL 把标签放在轨槽之外的独立行

滑块控件 MUST 分为两条互不重叠的横向带：

```
┌────────────────────────────┐
│ 长（X）：8 格               │ ← 文字带：标签独占
│ ▓▓▓▓▓▓▓▓▓▓●▓▓▓▓▓▓▓▓▓▓▓▓▓▓ │ ← 轨槽带：轨槽 + 滑钮
└────────────────────────────┘
```

三条硬约束：

1. **轨槽高 MUST > 字形实占高度。**
   MC 的 unifont 字形是 `pixelHeight = 16`、`oversample = 2`，**实占 8 行**
   （`SheetGlyphInfo.getBottom() = 16 / 2 = 8`；原版 bitmap 字体同为 8）。
   轨槽若也只有 8px，文字就被轨槽上下两条描边齐平地夹住，底边描边直接切在字脚上，
   实机读作「字显示不全」。
   ⚠️ MUST NOT 用 `Font.lineHeight`（= 9）当字形高度 —— 那是行高，不是字形高。
2. **滑钮 MUST 与轨槽同高，MUST NOT 贯穿控件高度。**
   贯穿式滑钮（8px 宽 × 整控件高）会横切文字带：滑钮的竖向描边把汉字劈开。
   实测默认值 25% 时滑钮正好压在标签中段。
3. **标签 MUST 落在自己的文字带内**，MUST NOT 与轨槽/滑钮有纵向重叠。

滑钮**横向**位置 MUST 与原版一致（`x + (int)(value * (width - 8))`，宽 8px），
否则拖动时手柄与实际值错位。原版取值映射是 `(mouseX - (getX() + 4)) / (width - 8)`。

**MUST 有本地目检手段。**「字显示不全」这类问题**只有把字真的画出来才看得见**，
而实机验证要开游戏、摆方块、右键、截图，一轮几分钟。
故 MUST 提供一个本地预览脚本，用**与 Java 完全相同的几何 + MC 自己的字形**渲染面板。

⚠️ 预览的字形 MUST 取自 MC 真实资源（客户端 jar 的 `textures/font/ascii.png` +
unifont 的 16×16 位图按 2:1 降采样），MUST NOT 用方块代替 —— 方块看不出「字被切掉」。
⚠️ 字形高 MUST 按 **8 行**算（`pixelHeight=16 / oversample=2`），
MUST NOT 用 `Font.lineHeight`（=9，行高不是字形高）。

#### Scenario: 轨槽比字形高
- **WHEN** 滑块控件的轨槽与标签并存
- **THEN** 轨槽高度 MUST 大于字形实占高度（8 行），标签 MUST NOT 被轨槽描边切到上下两行

#### Scenario: 滑钮不横切标签
- **WHEN** 滑块处于任意进度（含 0% 与 100%）
- **THEN** 滑钮的纵向范围 MUST 与轨槽一致，MUST NOT 进入标签所在的文字带

#### Scenario: 手柄与实际值不错位
- **WHEN** 玩家拖动滑块
- **THEN** 滑钮绘制位置 MUST 与原版取值映射一致

#### Scenario: 改完先本地目检
- **WHEN** 改动滑块几何或标签排版
- **THEN** MUST 先用本地预览脚本渲染出面板并目检，MUST NOT 直接进实机

### Requirement: 深底覆盖窗 SHALL 自绘浅色标题而 MUST NOT 继承原版深灰标题

深色底板（覆盖窗、深色面板）上的标题 MUST 由界面**自绘**，
MUST NOT 走 `AbstractContainerScreen.renderLabels` 的默认绘制。

原版默认把标题画成 `4210752 = 0x404040`（深灰）。压在深紫粉覆盖窗（`0xC03A2630`）上，

同一方法还会把「物品栏」标签画到面板外的世界上（同样是深灰），

- **THEN** MUST NOT 在面板外绘制「物品栏」标签

### Requirement: BOSS 血条 SHALL 按 1080p 物理像素产出、细纸框悬空窗 + 品阶色主题 + 灵力液面

咒符条血条的边框贴图 MUST 是 **728 × 144 texel**，即逻辑尺寸 **182 × (24 + 12)**
（默认 config 宽度 × 血条本体高度 + 上方 12 行装饰带）在 **1920×1080 / guiScale=4**
下的物理像素数。屏上血条本体逻辑尺寸仍是 182×24，装饰向上生长；
默认分辨率下 **1 texel = 1 物理像素、零缩放**。

MUST NOT 退回 182×24 的 1 texel = 1 逻辑像素方案：那只有 4368 texel，
端头装饰柱仅 22×20 逻辑像素，扩散模型画不出可读细节，屏上表现为「大色块」。

**符纸 MUST 是细边框，MUST NOT 是实心纸卡片。** 纸只占逻辑 **16..31** 行
（上沿 2 + 内唇 2 + 血槽 8 + 内唇 2 + 下沿 2），上下各留 **2 行透明缝**（14..15 / 32..33），
使纸框读作「悬空的一圈框」而不是「一张纸片」。血槽窗 MUST 保持开放，
装饰 MUST NOT 画进窗口内。

每一阶 MUST 有独立的装饰意象，主题色与 `TierPalette` 同色相：

| 阶 | 主题色 | 装饰意象 |
|---|---|---|
| 1 | 绿 `#4CAF50` | 竹节 / 草叶 / 风痕，稀疏 |
| 2 | 蓝 `#2196F3` | 水纹 / 雨脚 / 流动水线 |
| 3 | 金 `#FFC107` | 金箔碎光 / 金色流光 / 细雷纹，**不要铜钱** |
| 4 | 红 `#F44336` | 彼岸花（红花石蒜）+ 赤色花丝（保留） |
| 5 | 紫 `#9C27B0` | 境界裂痕 / 蝶影 / 星点，最繁密 |

装饰密度 MUST 随阶递增（1 阶最素、5 阶最满）。边框颜色 **画死在每张图像素里**，
MUST NOT 运行期染色（色相来源仍是 `TierPalette`；改色时五张图与色板一起改）。

九宫格 MUST 保留（config 宽度仍可调 120~400），但 MUST 满足：**默认宽度下中段源宽 ==
目标宽**（`728 − 2×240 texel` == 62 逻辑像素 × 4），即默认宽度下**不产生任何拉伸**。
目标侧端头 MUST 是 60 逻辑像素（240 texel），源区域按 texel 切分；目标尺寸与源尺寸的
倍率差 MUST NOT 混用（混用不报错，只会裁切错位）。

血槽条身区 MUST 由程序**挖成透明**（血条自己填色），MUST NOT 让 AI 画的纸面盖住填充。
**血槽边线 MUST NOT 由收口程序重绘**（保留 AI 原画）；收口只做两件事：
把框线一圈的 alpha 钉成不透明（防缩放脏边）、按坐标挖槽。
若 AI 的窗口位置与草稿有比例偏差，收口 MUST 以**血槽奶油带为锚**做**3×3 网格重映射**：
横向拆成「左端 / 窗口 / 右端」，纵向拆成「上框 / 窗口 / 下框」，把 AI 的窗口精确拉到
`x 88..639`、`y 80..111`，端头按剩余宽度/高度贴满。只做纵向映射会让填充条比纸框窗口
短一截（AI 画的窗口宽度不是固定 138 逻辑），MUST NOT 只做纵向。

**装饰层 MUST 全白抠除**（含被花枝围住、不与画布边缘连通的白缝），
MUST NOT 留下白色底板。**纸框 MUST 是固定矩形**：窗口以外补纸色、alpha 固定，
保证五阶的框宽/框高完全一致；MUST NOT 沿用 AI 高度不一的外轮廓
（实机读作「有的阶短一截」）。装饰可以越出纸框，但纸框本体不参与撕边。

**血量条本体 MUST 读作「凹槽里的灵力」，MUST NOT 是纯色进度条**：

1. 凹轨、残影、灵力填充共用 `segment.png`（64×32 灰度纵向剖面：上缘内阴影 →
   上三分之一亮芯 → 下缘压暗），运行期分别乘轨道色 / 残影色 / 品阶色。
2. 灵力前端 MUST 叠 `segment_edge.png`（8×32 近白月牙），乘**提亮后的品阶色**，
   使液面比条身亮一档；乘法染色只能压暗，故条身剖面最大亮度 MUST < 1.0。
3. 前缘宽度 MUST 不超过当前填充宽度（低血量时至少 1px），MUST NOT 越过条身两端。
4. **凹轨色 MUST = 深墨 + 约 25% 品阶色**（绿→暗橄榄 / 蓝→暗蓝灰 / 金→暗金褐 /
   红→暗红 / 紫→暗紫），MUST NOT 用纯黑 `#2A1A1C` 直接铺满空槽。

- **THEN** 边框贴图的每一列 MUST 1:1 落在屏幕物理像素上，MUST NOT 出现横向放大

- **THEN** 每一阶 MUST 呈现对应品阶色的装饰意象，且 5 阶装饰密度 MUST 明显高于 1 阶

- **WHEN** 自动检测的窗口与 AI 实际画的纸框窗口对不上（每阶框长/框高不同）

- **WHEN** 装饰层（竹/水纹/金箔/彼岸花/裂痕）压在纯白背景上
- **THEN** 所有近白/浅灰背景 MUST 变透明（含被装饰围住、不与画布边缘连通的白缝），
       MUST NOT 留下白色底板或白色描边
