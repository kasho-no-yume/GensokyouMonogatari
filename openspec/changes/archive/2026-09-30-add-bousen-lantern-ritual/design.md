# 忘川灯坛（`bousen_circle`）设计文档

## 0. 既成事实（本文档的一切推导都以此为前提）

pattern 已落盘并通过四重展开验证。蜡烛键为 palette 的 `D` = `minecraft:candle`（**纯 block id，无状态后缀**），祭品台键为 `P` = `#gensokyou:ritual_pedestals`，二者严格一一对应（同 `x,z`，烛在台上方一格）：

| 等级 | 新增蜡烛（规范形） | 累计蜡烛 = 累计祭品台 | 该级新增格数 |
|---|---|---|---|
| 1 | 4 | **16** | 74 |
| 2 | 4 | **32** | 88 |
| 3 | 8 | **64** | 148 |

三条由此推出的关键性质：

1. **熄灭的蜡烛仍然匹配得上结构。** predicate 是纯 block id，`LIT=false` 不改变方块身份，故 `RitualMatcher` 不会因熄灭而判定结构失效。反之，打掉蜡烛（变成空气）会让该格失配 → **结构不成型**。这两种"蜡烛没了"必须严格区分，代码里不可合并处理。
2. **64 根蜡烛 = 正好一个 `long` 字长。** 这不是巧合，是下文位掩码方案的支点。
3. **64 个祭品台 = 核心对外暴露 64 格代理箱。** 玩家可逐台手动取回，灌多少都随玩家。**本期不动 pattern。**

另：蜡烛总数恰为 16/32/64 ⇒ 1 阶 4 位、2 阶 5 位、3 阶 6 位皆可被单个 `long` 无损表示；`MAX_CHANNELS = 64` 恰好顶满，**故不用 `linkPos` 承载坐标**（见 §7）。

## 1. 熄灭模型：为什么"只模拟根数"与逐根模拟同分布

### 1.1 朴素实现（不采用）

```
每根蜡烛 → 一个 10 秒倒计时 → 到点掷 1% 的骰子 → 输了 setBlock(LIT=false)
```

代价：需要 64 份独立 tick 状态；且"是否全亮"这个产灵判据要在每 tick 重新回答 ⇒ 逐 tick 扫 64 个方块。

### 1.2 聚合实现（采用）

设当前有 `n` 根点亮。下一个 10 秒结算帧内，每根**独立地**以概率 `p` 熄灭。则熄灭根数 `k ~ Binomial(n, p)`，且**给定 `k` 时，熄灭的那 `k` 根在 `n` 根点亮蜡烛中是均匀随机的子集**。

理由（这是整个方案成立的全部依据，不是近似）：

> 朴素过程对集合 `S`（本次熄灭的蜡烛集合）的概率是
> `P(S) = p^|S| · (1-p)^(n-|S|)`，**只依赖 `|S|`**。
> 因此在 `|S| = k` 的条件下，`S` 服从所有 `C(n,k)` 个子集上的**均匀分布**。

于是"先抽 `k ~ Binomial(n,p)`、再从点亮集合中均匀抽 `k` 个"与"逐根独立掷币"给出**完全相同的联合分布**——不只是根数分布相同，连**是哪几根**的边缘分布也相同。两条路径在任意时间跨度 `T` 上逐点同分布。

> 附注（易错点）："均匀随机 k 子集"只在**条件于 k** 时与伯努利乘积律相同。若直接均匀抽 k 而不先抽 `k` 的分布，就是错的。本方案的正确性依赖"先抽 k 再抽子集"这两步的顺序，MUST NOT 简化为其中一步。

推论：**"还剩几根亮着"是整个过程的充分统计量。** 不需要记住 64 根各自的下一次掷骰时间，不需要任何逐烛状态。

### 1.3 采样实现的复杂度

需要 O(k) 期望工作量，而不是 O(n)：

- **抽 `k`**：不用"翻 n 次硬币"（O(n)），用**几何跳跃法**——`k` 的期望只有 `n·p`（1 阶 0.16、3 阶 0.64），故实际循环圈数约等于 `E[k]`，即 O(E[k])。1 阶最坏也只是"绝大多数时候 0 次循环"。
- **抽熄灭对象**：对 `long` 掩码用**拒绝采样** `pick = rng.nextLong() & mask`，`pick == 0` 则重试；首个非零 `pick` 在所有置位 bit 上**均匀分布**。命中后 `idx = Long.numberOfTrailingZeros(pick)`，清位。一次期望尝试 < 2 次（点亮占比高时更接近 1 次）。

整帧稳态工作量：**1 次采样调用 + 期望 0.16~0.64 次 `setBlock`。**

### 1.3a ⚠️ 游标与熄灭计数 MUST 分开维护（实机踩到，两轮才发现）

**症状**：不到一分钟内"一次性熄灭十几根"（第一次是全灭 64 根，改了一轮后变成 ~12 根）。
`n·p = 0.16` 的分布下，`k = 12` 的概率约等于 0，所以这是采样器本身错了，不是参数错了。

**根因**：`sampleBinomial` 的几何跳跃把**游标**和**熄灭计数**用成了同一个变量：

```java
// 错的
int extinguished = 0;
while (extinguished < n) {
    int survivors = geometricSkip(p);
    if (survivors >= n - extinguished) break;
    extinguished += survivors + 1;     // ← 游标该走 g+1，计数只该 +1
}
return extinguished;
```

顺序伯努利的正确读法是"**g 根存活 + 1 根熄灭 = 消耗 g+1 根**"：游标前进 `g+1`，而熄灭计数只 **+1**。
混用之后返回值是"已消耗根数"而非"已熄灭根数"，它会冲过 `n`。

**离线验证**（把该函数原样抽出来跑 200 万次，与理论 pmf 对表）：

| | 修复前 | 修复后（理论值） |
|---|---|---|
| n=64, p=0.0025 `E[k]` | **4.92** | **0.160**（0.160） |
| n=64, p=0.0025 `P(k=0)` | 0.852 ✓ | 0.852（0.852） |
| n=64, p=0.0025 `P(k=1)` | **0.0021** | **0.1367**（0.1367） |
| max over 200 万次 | **64**（全灭） | 5 |

注意修复前 `P(k=0)` 一直是**对的**（= `(1-p)^n`，因为首抽就 break 的那条路径不经过累加），
只有 `k>0` 全错。**单看 `P(k=0)` 或单看均值都会漏掉它**，必须整张分布对表。

> 这类错误在游戏内极难定位：表现是"概率不对"，而 `p` / `n` / RNG 全都看起来正常。
> 结论是——**任何带随机采样的仪式逻辑，采样器必须是可离线跑的纯函数，并且自带分布对表断言**。
> 本项目的 `selftest` 正是为此存在（见 §1.3b）。

### 1.3a-2 ⚠️ 「拒绝采样 `nextLong() & mask` + `numberOfTrailingZeros`」MUST NOT 当作"在置位上均匀抽样"

**症状**：每次熄灭的都是**同一个位置**（最小下标那根），清掉后次小那根又接着中选。
而根数分布此时是**完全正确**的——所以 §1.3a 的均值检查抓不到它。

**根因**：`nextLong() & mask` 在 2^k 个取值上均匀，但"最低置位是第 j 位"的取值有 `2^(k-1-j)` 个，故

```
P(选中第 j 位) = 2^(k-1-j) / 2^k = 2^(-j-1)
```

**指数衰减，不是 1/k。** 最小下标以 1/2 中选、次小 1/4、次次小 1/8……

**离线验证（20 万次）**：

| 场景 | 旧法 | 正解 | 均匀值 |
|---|---|---|---|
| 2 位掩码（bit3 + bit60），k=1 | **0.667 / 0.333** | 0.4989 / 0.5011 | 0.5 / 0.5 |
| 3 位掩码，k=2 的三个子集 | **0.571 / 0.286 / 0.143** | 0.3333 / 0.3346 / 0.3322 | 1/3 each |

**正解**：

```java
int r = rng.nextInt(remaining);      // 均匀选"第 r 个置位"（0-based）
long probe = work;
for (int s = 0; s < r; s++) probe &= probe - 1L;   // 清最低置位，跳过前 r 个
int idx = Long.numberOfTrailingZeros(probe);
work &= ~(1L << idx);                 // 抽中即移出候选 → k 次抽取构成均匀随机 k-子集
```

开销 `O(r)` ≈ `O(remaining/2)` 次位运算，且只在真正要熄灯时付。

> 这条是 §1.2 等价性论证的**第二半**（"给定根数时熄灭的那 k 根在点亮集合中均匀随机"）。
> 第一半（根数分布）由 §1.3a 修好，第二半（本节）此前一直是**错的**——论证写对了，
> 实现没对上。**写对了的推导不等于实现了的语义**，两半都要单独断言。

### 1.3b 掷骰 MUST NOT 用 `Level#getRandom()`

顺带确认的一条独立规则（**不是**上面那个 bug 的原因，但同样该守）：

```java
public final RandomSource random = RandomSource.create();            // ← getRandom() 返回这个
private final RandomSource threadSafeRandom = RandomSource.createThreadSafe();  // 真正的流，没人用
```

`Level.random` 是**固定种子 0、且被天气/雷声/随机刻/熔炉共享**的遗留流。熄灭结算是固定 200 tick
节拍去取值的。正确取法是 `ServerLevel#getRandomSequence(ResourceLocation)`（`RandomSequences` 是
`SavedData` 支撑、逐维度持久化、每个名字一条独立且正常推进的 `XoroshiroRandomSource`）。
本仪式用 `gensokyou:bousen_extinguish`。

**防御纵深**：`selftest` 的第 0 项是 RNG 健康度检查（连续 9 次 `nextDouble()` 必须互不相同）；
第 3 项是采样均值检查；**第 6 项是抽样均匀性检查**（2 位掩码下 bit3 占比 MUST ∈ [0.48, 0.52]，
旧实现给 0.667）。`/gs_debug bousen selftest` 自带的 RNG 也 MUST 现场播种——
用被查对象去查自己等于没查。

**这三个 bug 里，均值检查本该当场抓住第一个，均匀性检查本该抓住第二个；两次都因为
"没在游戏里跑 selftest"而漏到实机才发现。** 下次改动请先跑 `/gs_debug bousen selftest`。

> 同类先例：`RitualFxLayout.fireBed` 早就用 `RandomSource.create(seedBase)` 而非
> `level.getRandom()`。这条经验应当推广到所有按固定节拍掷骰的仪式逻辑。

### 1.4 产灵铺光的高度 MUST 由结构推导

坛面的行走面是 **y-1 层的顶面**，而内圈祭品台（y0）、各环缘石都坐在它上面。把加法铺光贴死在
行走面高度，会被这些方块逐面遮掉——现象是"金光在地底下"（加法外壳是深度测试但不写深度，被
遮的部分就是纯看不见）。

正解：高度取**最内圈蜡烛的方块中点**（`lowestCandleMidY`，三阶同为 1.5，因为后二阶只向外加环、
内圈一直在），语义即"灯火本身的光"，再用 `fxGoldLift` 供玩家微调。**MUST NOT 硬编码 y 值**，
否则改结构就得同步改魔数。

## 2. 为什么重扫蜡烛不贵：与既有固定开销的量级对照

仪式核心的 `serverTick` 已经在每秒做这些事（`RitualCoreBlockEntity.java:2188`）：

| 既有工作 | 每秒次数 | 每次方块访问数 |
|---|---|---|
| `RitualMatcher.matchAt` 全量重扫 | 1 | ≈ 1240（310 规范格 × 4 旋转） |
| `writePedestalTiers` 逐台同步品阶 | 1 | 64 |
| `syncRenderState` | 20 | 1 |
| GUI 快照（仅观看者） | 20 | — |

**本变更新增的部分：**

| 新增工作 | 每秒次数 | 每次方块访问数 |
|---|---|---|
| 蜡烛点亮态重扫 | 1 | 64 |
| 二项采样 | 0.16 | 0 |
| `setBlock` 熄灭 | 0.16 | 1 |

**结论：新增蜡烛开销约为既有重扫的 5%，且不随 tick 率放大。** 这是"1 Hz 重扫"而非"逐 tick 扫描"的全部理由——两者相差 20 倍，而 1 Hz 已完全够用（产灵本身也只精确到秒）。

需要**明确避开**的四种写法（它们才是真正的性能大户）：

| 反模式 | 后果 |
|---|---|
| 每 tick 扫 64 根蜡烛 | ×20 = 1120 次/秒/座；20 座灯坛 = 22400 次/秒 |
| 给每根蜡烛挂 `BlockEntity` | 64 个 tick 中的方块实体；本项目 `onFormed` 正是"未来大 tileblock 扩展点"，极易被误用成此 |
| 把逐烛状态每 tick 推给客户端 | 稳态持续包，直接违反 `ritual-runtime-fx` 的零稳态包不变量 |
| 在 `uiInfo` 里现算点亮数 | 每观看者每 Hz 64 次读，多人同时看则线性放大 |

## 3. 状态机与 tick 编排

### 3.1 两条通道的分工

```
serverPassiveTick（成型即跑，无 enabled 门控）
  └─ 每 candleScanPeriodTicks（默认 20）= 1 Hz
       ├─ 全量重扫 64 根蜡烛 → litMask / litCount（瞬态，不持久化）
       └─ 供 GUI 信息行与渲染态读取（故停机态数据依然新鲜）

serverTick（仅 enabled 时跑）
  ├─ 每 20 tick（1 秒）：if (allLit) deposit(rate[level])
  └─ 每 200 tick（10 秒）：if (allLit) rollExtinguish()
```

**为什么重扫放 `serverPassiveTick` 而非 `serverTick`**：GUI 信息行要在**停机态**也显示"灯火 63/64"（玩家需要知道该去补哪一根），渲染态的淡红标记也要在停机时可见。放 `serverPassiveTick` 保证数据任何时候都是世界真值。代价是停机灯坛仍付 64 次/秒的读——与 §2 同量级，可忽略；而放 `serverTick` 会让停机态的 GUI 展示过期数据，是明确的体验退化。

### 3.2 熄灭的自我冻结

```
              每 10 秒结算帧
                    │
              allLit == true？
              ├── 否 ──► 不产灵、不掷骰（本帧空转）
              │          ▲
              │          │ 玩家用火石点亮缺失的蜡烛，下一个 1 Hz 重扫恢复 allLit
              是
              ▼
        ① 产灵 deposit(rate[level])
        ② k ~ Binomial(litCount, p[level])
        ③ 均匀抽 k 根 → setBlock(LIT=false, flags=2)
        ④ 若此后不再全亮 ──► 冻结，直到 ③ 之后玩家补点
```

**"冻结"是本仪式的核心手感**：它不是"蜡烛会逐渐耗尽直到全灭"的衰减曲线，而是一个**二元状态机**——全亮则产灵并继续面临下一次随机熄灭；一旦有灯灭，立刻停产并停止一切随机性，把控制权完整交还玩家。玩家永远不会面对"灯越点越少、越点越难"的滑坡。

### 3.3 `setBlock` 的 flags

**MUST 用 `flags = 2`（`UPDATE_CLIENTS`，不触发邻居更新），MUST NOT 用 3。**

理由：蜡烛的 `LIT` 是状态属性、不改变碰撞盒与光照几何，`UPDATE_NEIGHBORS` 是纯浪费。而 3 会惊动结构内 64 个祭品台与约 1240 格匹配区域的方块更新检查，与 §2 的成本表直接冲突。

### 3.4 瞬态状态

`litMask` / `litCount` **MUST NOT 持久化**。它们是"每 1 Hz 由行为侧按同一判据从世界重算"的派生态，存进 NBT 只会写下一份早已过期的快照（与 `RitualCoreBlockEntity.reiyokuBatherCount` 同一处置）。区块卸载后重新加载时，1 Hz 重扫自然收敛。

## 4. 分阶熄灭概率的均衡推导

原始设想的"每根 1% / 10 秒"若对三阶一视同仁，总熄灭率会随蜡烛数线性放大，把高阶变成不可能维持的值：

| 阶 | n | p | n·p / 10s | 首次熄灭期望间隔 |
|---|---|---|---|---|
| 1 | 16 | 1% | 0.16 | 62.5 s |
| 2 | 32 | 1% | 0.32 | 31.3 s |
| 3 | 64 | 1% | 0.64 | 15.6 s |

**采用"总熄灭率恒定"梯度**：`p[level]` 取 `[0.01, 0.005, 0.0025]`，与蜡烛数的 2 倍增长反比。三档 `n·p` 完全相等：

| 阶 | n | p | n·p / 10s | 首次熄灭期望间隔 |
|---|---|---|---|---|
| 1 | 16 | 0.0100 | 0.16 | 62.5 s |
| 2 | 32 | 0.0050 | 0.16 | 62.5 s |
| 3 | 64 | 0.0025 | 0.16 | 62.5 s |

派生体感曲线（三档共用同一条）：

| 距上次补齐 | 仍全亮概率 | 期间期望熄灭次数 |
|---|---|---|
| 30 s | 62% | 0.5 |
| 60 s | 38% | 1.0 |
| 120 s | 15% | 2.0 |
| 300 s | 0.8% | 4.8 |
| 600 s | 0.006% | 9.6 |

即"一分钟"在体感上实际是 **43 秒的"全亮"半衰期 + 约每分钟补一根**。三阶在数值上不比一阶更烦；它的额外压力来自**空间**（要在 20×20 坛面找到那一根淡红再走过去），而非频率。叙事上也自洽：灯越多，单盏越耐烧（3 阶单根 400 秒 ≈ 6.7 分钟才轮到一次），"灯火渐高"与"愈多愈稳"是同一件事。

**配置形态：显式列表，不是"每阶减半"的公式。** 一是玩家在 config 文件里能直接读到三档真实值，二是将来蜡烛数不是 2 倍增长时不会静默算错。三张灵力表（产灵 / 缓存 / 供灵）同样不是 `base × 4^L` 几何序列，故本仪式**不使用**既有的 `kagutsuchiCapacity` 式公式，改用分阶列表。

## 5. 灵力三件套与端点

| 项 | 1 阶 | 2 阶 | 3 阶 | 形态 |
|---|---|---|---|---|
| 产灵 | 100/s | 500/s | 3000/s | 分阶表 |
| 缓存上限 | 50000 | 1000000 | 10000000 | 分阶表 |
| 供灵端点 | 1000/s | 5000/s | 20000/s | 分阶表（静态） |
| 受灵端点 | 0 | 0 | 0 | 不声明（不可作受灵汇） |

**产灵分流口径**（与 `daycycle-generator-ritual` 一致，MUST NOT 走 `extractRouted`/`receiveRouted`，否则被自身 inRate=0 误截）：

```
槽内灵力核心（不限速直注）→ 溢出进仪式缓存（截到上限，余量作废）
```

**缓存 → 槽核回流** SHALL 走 `serverPassiveTick`（不受启停门控），复用 `core.tickBatteryAutoFill()`。**停机时回流继续**（缓存是已挣到的钱），但**停机时不产灵**。

**供灵速率 MUST 为静态值**：路由按结算周期 memo 端点速率并以 `> 0` 筛源，动态速率会致源在蜡烛明灭时闪断、或夜间消失。

**关于"out 恒高于产灵"的取舍**（已知并接受）：三档 `out ÷ 产灵` 分别为 10× / 10× / 6.7×，意味着供灵端点速率从不构成瓶颈，缓存是个只涨不落的池子（3 阶填满需 3333 秒，而路由满速抽干只需 500 秒）。这符合"长期蓄能库"的定位，缓存容量数字因此是主要的经济刻度而非缓冲带刻度。**本期不改口径**，如将来要改，是把 `outRatePerSecond` 调到产灵量级，属独立变更。

## 6. 熄灭的自我冻结与产灵门控（重复强调，因其为本仪式的语义核心）

- 产灵判据 = `enabled == true` **且** `litCount == 该阶蜡烛总数`。二者缺一不产。
- "灭 1 根"与"灭 64 根"**完全同义**：都是"不产灵"。不设部分产灵、不按点亮比例缩放、不做停机惩罚。
- 熄灭时**不清缓存、不扣缓存、不落物、不报错**。缓存是已挣到的钱，停产只是停产。
- 熄灭**不触发** `setEnabled(false)`。仪式在 GUI 上仍是"运行中"，只是"灯火不全、暂停产灵"——这样玩家补完灯后**自动恢复产灵**，无需再次点启动。

## 7. 渲染态与客户端特效

### 7.1 通道选型

新增 `RitualRenderState.KIND_BOUSEN = 10`：

| 字段 | 语义 |
|---|---|
| `enabled` | 仪式启停态 |
| `tier` | 结构等级（客户端据此取该阶 pattern 切片） |
| `movingMask` | **蜡烛点亮位掩码**，bit i = 规范序第 i 根蜡烛点亮 |
| `minY`/`maxY`/`period`/`inCount` | 不使用 |
| `linkPos` | **不使用**（见下） |

**为什么不用 `linkPos` 承载 64 个坐标**：`MAX_CHANNELS = 64`，64 根恰好顶满、零余量；而 `forgeBurnMask` 之类已占用 bit0 作标志位（只余 63 位），且将来若增第 65 根蜡烛就静默截断。**坐标一律由客户端本地推导**，遵循 `ritual-runtime-fx` 既定规则（`KIND_REIYOKU` 的 433 格占地即因此才改走推导路径）。

**"全亮"不需要额外标志位**：客户端由 `litMask == 满掩码` 自行判定。

```java
// 满掩码：注意 Java 的 (1L << 64) == 1（移位数按 64 取模），
// 直接写 (1L << n) - 1 在 n == 64 时得 0 而非 -1，必须特判。
static long fullMask(int candleCount) {
    return candleCount >= 64 ? -1L : (1L << candleCount) - 1L;
}
```

### 7.2 ★ 跨端位序一致性（关键不变量）

`movingMask` 的 bit i 在服务端与客户端 MUST 指向**同一根蜡烛**。为此：

- 新增 `ritual/BousenLanterns.java`，与 `RitualPedestals` **同构**：服务端 `positions(match)` 与客户端 `offsets(pattern, tier)` **共用同一段筛选代码与同一个 `(y, z, x)` 规范排序**。
- 排序 MUST 为 `(y, z, x)`——与服务端 `match.positionsOf('D')` 经 `RitualPedestals.collect` 的排序口径一致。
- 服务端用绝对坐标排、客户端用相对偏移排，但锚点是同一常量，排序结果因此逐项相同（`RitualPedestals.offsets` 的 javadoc 已论证此点）。
- pattern 已四重对称展开，`RitualMatcher#orient` 只做置换与符号翻转，故位序与仪式朝向无关。

**任何一侧重排或改排序键都会让掩码指向错误的蜡烛**（表现为"客户端高亮的位置和服务端熄灭的位置不符"）。这是本变更最易被后续修改踩坏的一处，MUST 以注释固化。

### 7.3 网络与渲染成本

```
网络
  渲染态：仅在 litMask 翻转时推送（syncRenderState 已内建"值变才发"）→ 8 字节
  方块更新：每次熄灭 1 个 ClientboundBlockUpdatePacket
  稳态（全亮、无明灭）：零包

渲染（每帧、每座可见灯坛）
  遍 1  一张白色柔光贴图 + 顶点色 tint
        ├ 64 个淡蓝 quad（点亮）
        └ 64 个淡红 quad（熄灭）—— 同一 consumer！
        ─────────────────────────────────► 1 个 draw call，128 quad
  遍 2  熄灭态冲天细光柱（每根熄灭蜡烛一道，高 4 格）  ≤64 draw call，期望 0~1
  遍 3  产灵时坛面淡金铺光                          1 draw call
  ─────────────────────────────────────────────────────
  典型：2~3 个 draw call
```

**为什么 64 个 billboard 只需 1 个 draw call**：`DanmakuRenderTypes` 是 `Map<ResourceLocation, RenderType>` 缓存，同一贴图返回**同一 RenderType 实例**，`MultiBufferSource.getBuffer` 按 RenderType 分桶 ⇒ 亮/暗两批写进同一 consumer。且 `additiveGlow` 走加法混合、无深度写 ⇒ **顺序无关**，可安全混写。**只此一贴即可，MUST NOT 为亮/暗各做一张贴图**（那会变成两个 RenderType，MUST 分趟提交）。

**新贴图**：`textures/fx/lantern_halo.png`，白色径向柔光（居中不透明、边缘全透），走 `tools/gen_tex.py` 的 ASCII 像素图 + 调色板管道生成。淡蓝/淡红/淡金三色全部由顶点色给出。

**渲染包围盒无需改动**：坛面半径 9，蜡烛最远角点 `√(9²+9²) ≈ 12.7 < 16`（默认 `r`）；蜡烛最高 y=+3、坛基 y=-2，落在默认 `[y-16, y+48]` 内。熄灭光柱高 4 格亦在盒内。⇒ `getRenderBoundingBox` 无需为 `KIND_BOUSEN` 开分支。

### 7.4 熄灭态的"找得到"设计

需求是"方便玩家快速找熄灭的蜡烛"，而 3 阶要在 20×20 坛面上找。采用**双通道提示**：

| 手段 | 作用距离 | 实现 | 成本 |
|---|---|---|---|
| 淡红 billboard 放大（0.5 → 0.9 格宽） | 近 | 顶点缩放 | 0（在遍 1 内） |
| 淡红 billboard 呼吸脉动（alpha + 缩放，周期 ~0.8s） | 近 | 顶点 alpha/缩放随 `now` | 0 |
| **冲天细光柱**（高 4 格，向上） | **远（50 格外可辨）** | 独立 draw call | 期望 0~1 个/座 |

光柱只在存在熄灭蜡烛时出现。由于熄灭后系统即冻结、不会连锁恶化，同时熄灭的根数期望 < 1，即使偶发 3 根也只读作"这几根坏了"，不会退化成信号弹。

## 9. 决策记录

| 议题 | 决定 | 理由 |
|---|---|---|
| 逐烛倒计时 vs 聚合采样 | **聚合** | §1.2 分布等价；§2 成本差 20 倍 |
| 采样方式 | 先抽 `k ~ Binomial(n,p)`，再均匀抽 `k` 个 | 仅"条件于 k 的均匀子集"才与逐根掷币同分布（§1.2 附注） |
| 掩码载体 | `movingMask`（`long`），坐标客户端推导 | `linkPos` 顶满 64 零余量；`KIND_REIYOKU` 已定此先例 |
| 熄灭概率形态 | 显式分阶列表，非"每阶减半"公式 | 可读 + 蜡烛数变化时不会静默算错 |
| 产灵门控 | 严格全亮 | 需求原文；且"停机 ≠ 熄灭"避免了第二种停机态 |
| 熄灭是否停机 | **不停机**，只停产 | 玩家补完灯即自动恢复，无需再点启动 |
| 熄灭是否清缓存 | **不清** | 缓存是已挣到的钱 |
| 批量点灯 / 停机吹熄 | **不做** | 需求方明确："启停都不需要去改，就该让玩家去自己点" |
| 蜡烛缺失是否豁免结构判定 | **不豁免** | 需求方明确："蜡烛算在仪式结构里的，蜡烛打掉仪式不成型" |
| 熄灭音效 / 迸射粒子 | **本期不做** | 需求方明确归入统一 FX 批次 |
| 熄灭瞬时反馈 vs 熄灭态常驻表现 | 常驻表现（billboard + 光柱）**本期做** | 前者是"一次性事件"，后者是玩家赖以定位灭灯的**持续可读性**，缺了则机制不可玩 |
| 祭品台 64 格是否改造 | **不动 pattern** | 需求方确认玩家可逐台手动取回，灌多少随玩家 |
