## Context

`danmaku-motion` 与 `danmaku-behaviour-decoupling` 刚落定，弹幕运动学被重写为「弹位 = 位置的解析纯函数」，双端各自推进、位置包降级为安全网。这套设计成立的前提写在 `danmaku-lag-smoothing/proposal.md:30`：

> 弹幕运动是 `tickCount` 的**纯函数** …… ⇒ 客户端自 spawn 起**已知道整条未来轨迹**

这个前提有两个隐含成分：**纯函数成立**（已验证成立），以及**自变量的取值双端相同**（在读档后不成立）。

自变量即年龄。本项目用的是原版 `Entity.tickCount`，而从 NeoForge 21.1.248 反编译源码可确认：

```
Entity.java:195          public int tickCount;
Entity.java (全文)        仅 3 处 tickCount 引用，全是水晶音效；读写存档的两处方法不含它
Entity.java:3562         recreateFromPacket(...) —— 不设 tickCount
ServerLevel:772          p_entity.setOldPosAndRot(); p_entity.tickCount++; p_entity.tick();
ClientLevel:298          p_entity.setOldPosAndRot(); p_entity.tickCount++; p_entity.tick();
```

⇒ 读档后服务端实体自 0 重数（但位置被 NBT 还原到「年龄 T」的坐标），客户端实体自 0 重数（位置由生成包给出）。**位置存了，年龄没存**，两端自变量从此不等，且此后以恒定速率发散。

**「读档」只是触发条件之一，且不是最高频的那个。** 客户端实体的年龄归零，触发条件是客户端丢掉该实体、之后又重新拿到：

```
  ① 世界读档
  ② 走出 clientTrackingRange 再走回来          ← 多人正常游玩中每分每秒发生
  ③ 客户端卸载区块而服务端仍加载
  ④ 末影箱 / 跨维度 / 传送 / 重生
  ⑤ 弹所在区块卸载后重新加载（BOSS 战跨区块边界）
```

② 与 ③ 是**常态**而非边界情况。服务端在这五条路径下的状态完全一致：那份实体一直未被销毁、一直在 tick。**故服务端侧根本区分不出「读档」与「后撤回来」——这把「读档即销毁」这个廉价修法彻底排除掉了**（详见决策 1 的替代方案）。

同时暴露出的第二层事实：`tickCount` 的自增在 **Level** 而非 `Entity` 中，位于 `entity.tick()` **之前**。`AbstractDanmakuProjectile:769-779` 关于「`super.tick()` 还没把 `tickCount` 加一」的注释据此不成立，编队帧的 tick 编号整体超前 1。

**约束**：
- 不改 `FormationFrame` / `DanmakuSpeedProfile` 的数学——它们已经是对的，问题在喂给它们的自变量
- 不改 `lerpTo` 的纠偏策略、不改渲染路径——那是 `danmaku-lag-smoothing` 的地盘，且本缺陷修好之后该提案的准入判据需要重新取数
- 每 tick 每弹的同步量必须保持为零（`danmaku-motion`「编队的参数带宽不随队形规模增长」）

## Goals / Non-Goals

**Goals:**

- 读档后双端在**同一年龄**上推进，读档前已在飞的弹不再抽搐
- 修法只增一个同步 int（且只在生成包与存档中出现，不逐 tick 发送）
- 正常发射路径**逐位不变**——新代码对未存档的弹给出与今日相同的结果
- 读档后弹的寿命 / 分裂 / 相位隐藏 / 悬停 / 越过发射点销毁按真实年龄继续扣减
- 修正编队帧的 1 tick 编号偏差与编队方向轴的存档缺失
- 在动手前先把「年龄失步」变成**可判定**的数据，而不是靠现象推断

**Non-Goals:**

- 不做位置纠偏策略的任何改动（`lerpTo` 阈值、模拟/渲染分离、相位推前）
- 不改 `updateInterval`、`clientTrackingRange`
- 不引入任何逐 tick 的年龄同步
- 不为旧存档做迁移（见「迁移」一节的理由）

## Decisions

### 决策 1：年龄 = 同步的「基准」 + 本地 tick 计数

```
age()  =  entityData.get(DATA_AGE_BASIS)  +  this.tickCount
```

**为什么不是「把 `tickCount` 整体同步」**：那需要每 tick 发包，或引入一个会与服务端 tick 漂移的估算器。基准 + 本地计数是唯一在两端都**逐 tick 相等**又**零持续带宽**的写法。

**为什么不是「只靠服务端位置包反推年龄」**：位置包只带位置不带年龄，反推需要额外协议，且在弹静止（悬停 / 溜め）时无解。

**为什么基准 MUST 走 `SynchedEntityData`**：客户端实体完全由生成包构造，**从不加载 NBT**。普通字段在客户端恒为默认值。`trackedDataValues` 随生成包在同一个 `ClientboundBundlePacket` 里下发（`ServerEntity.sendPairingData`），故没有「位置已到、年龄未到」的单帧竞态。

**为什么这样能跨存档**：

```
                 基准            本地 tickCount        age()
正常发射   server      0                0..n          0..n
          client      0                0..n-L        0..n-L
          ⇒ age 恒等，与今日无差别 ✓

读档后   server      T                0..m          T..T+m
          client      T（生成包）       0..m-L        T..T+m-L
          ⇒ 常数差 L = 网络管线延迟，与今日同量级 ✓
```

关键在于：**常数偏移 L 一直存在、且很小**（今天也是这么平滑的），而现状是**读档后凭空多出 T 的常数差**。本决策把 T 从「凭空出现」变成「随生成包下发」。

**替代方案（否决）**：
- *重新获取时销毁该弹*（`readAdditionalSaveData` 里 `discard()`，或客户端侧不移除）——**已否决（2026-09-29，用户）**。单机读档时消失可接受，但路径 ②（后撤 8 格再回来）会走同一条 NBT 往返，discard 会让玩家每次后撤再贴脸就永久失去那一片弹幕。症状从「弹在抖」变成「弹没了」，触发频率从「读档一次」升到「每场战斗数十次」。
  **根因不是「discard 太狠」，而是服务端无法区分两种丢失原因**——它看到的都是「客户端实体没了，服务端那份还在 tick」。任何以丢失原因为分支的修法都是错的。
- *用世界时间当自变量*——世界时间也不随生成包下发，且会引入「同一个世界时间下两枚弹年龄相同」的错误耦合。

### 决策 2：基准一旦写入便不再变更

`DATA_AGE_BASIS` 在**生成时**与**读档时**各写一次，此后永不 `set`。理由：它是常量，任何后续 `set` 都会把 `age()` 猛地跳一下，等于把读档缺陷搬到了运行中途。

代价：分实体类型的 `EntityDataAccessor` 只能定义在基类上（`SynchedEntityData.defineId` 绑定到具体的 `Class`），这与既有全部字段的做法一致。

### 决策 3：`splitFired` / `targetLost` 维持普通字段，但判据被改写

这两个是**一次性触发守卫**，注释声称「两端 tick 次数相同，故由 `tickCount` 派生的守卫值天然一致」。这条声称在读档后不成立，但**结论仍成立**——因为 age 连续之后，两端在同一年龄上的触发时机确实相同。

⇒ 决定的处理是：**不把这两个字段改成同步字段**（那是纯开销），而是把 `danmaku-pipeline-capacity` 的准入判据里「tick 次数相同」的表述改掉，让判据的表述与真实前提一致。判据写错比字段写错更贵——字段写错会编译失败或行为异常，判据写错会持续产出新字段沿用错误前提。

### 决策 4：编队帧 tick 编号直接用 `age()`，去掉 `+1`

`framePositionThisTick()` 当前的 `framePositionAt(this.tickCount + 1)` 在 1.21.1 之下等价于「年龄 0 时取 `framePositionAt(1)`」。改为 `framePositionAt(age())` 后，出生当 tick 取 `t=0`。

**这会改变所有既有编队符卡的观感一整 tick**——花心的第一帧从「已经张开 1 tick」变成「出生即收拢」。这正是 `FormationFrame.scaleAt` 注释里写的预期（「出生即收拢」不需要额外参数），故方向上是回正而非改动。但**观感无法自动验证**，故 tasks 把它单列为一个可单独回滚的步骤。

同一处还有一个量纲问题：`advance = unscale(FrameAdv) * tick`（`tick` 现为 `age()`）随年龄**无界增长**。本变更**不修**它——修它要引入「总行程上限」或把推进项并入速率曲线，是另一个设计问题。记录在此以免后续误读为遗漏。

### 决策 5：方向轴的存档写入条件放宽到「挂帧或挂曲线」

现状 `if (this.hasSpeedProfile())` 包住了 `SpAxis*` 的写入，而 `bindToFrame` 也写同一组 `DATA_AXIS_*`。于是「挂帧、不挂曲线」的弹读档后方向轴回落 `(0,0,1)`。

**为什么不在两条路径各写一份**：同一个 NBT 键写两次会让「键存在」与「键的语义」脱钩。正确形态是**单一写入点，条件为「挂帧 OR 挂曲线」**，读入同理。

### 决策 6：诊断先行的形状

`DanmakuBudget` 现有 `HARD_CORRECT`（按弹速分档）与 `LAG_BUCKETS`（0-1/1-2/2-4/4-8/8-16/16+）两个直方图。新增的年龄偏移**不复用**这两者，理由：它们的分母含未对齐的弹，修复前读数本就被污染；再往里加维度只会让「哪些数字可信」更难分辨。

新的维度需要**按来源分类**（会话内新发射 / 存档还原），且分档要能分辨 0~4 与 4+ ——即本缺陷的实际量级。测量点放在 `lerpTo` 里：那里同时握有权威位置、客户端自推位置、以及弹的年龄基准与年龄。

**为什么必须在第 0 步就加**：本缺陷与「网络滞后严重」在既有诊断上表现相似（都是硬纠正暴涨、滞后分布右移）。没有分类统计就会把修法投到错的方向上——而错方向的修法（相位推前）会把硬失败变成静默错渲，比不修更难查。

## Risks / Trade-offs

**[年龄基准的 int 溢出]** → 理论上界 `Integer.MAX_VALUE`。实际不可达（`MAX_LIFETIME_TICKS = 1200` 使任何弹在年龄 1200 时已销毁）。仍在 `age()` 内加钳位，且钳位值取一个远超寿命的值以免影响正常弹。

**[修复前的诊断读数被污染]** → 正是第 0 步必须先做的理由。第 0 步本身**不依赖**任何修复即可实施：它只读现有的 `DATA_*` 与 `tickCount`，在两侧都能跑。

**[编队 1 tick 回正改变观感]** → 单列为可独立回滚的一步。若实机判定「回正后反而不好」，可只回滚该步而保留年龄同步——两者无耦合。

**[基准字段用 int 而非更宽的类型]** → `EntityDataSerializers` 提供 `LONG`，用 LONG 可彻底消除溢出面，代价是生成包多 4 字节。选 int 是因为 1200 的寿命使溢出不可达；若将来寿命上限上调，此项需重新评估。

**[专用服务器上偏移 K 可达数千 tick]** → 修复后这不再是问题（客户端拿到的基准就是 T）。但它意味着**修复前**的诊断在专服上会看到远超 `LAG_EDGES` 上界的读数——分桶上界须在实施前按实测重定。

**[只改服务端不同步是不够的]** → 这是本设计最容易踩空的一点：客户端实体从不加载 NBT。**任何**只加 `addAdditionalSaveData` 而不加 `SynchedEntityData` 的修法都会让客户端继续按年龄 0 推演，缺陷原样保留。因此 spec 把「年龄 MUST 经 SynchedEntityData」写成硬性约束而非实现建议。

## Migration Plan

- **存档格式**：新增 NBT 键（年龄基准、编队方向轴）。**不做迁移**，且这是更安全的默认——旧存档缺键时按缺省值读入，读档得到的飞行中弹退化为今日的行为，**不比迁移前更差**。迁移反而要求为「一个已知错误的年龄」去推断正确值，而正确值不可知（`tickCount` 根本没被存过）。
- **回滚**：本变更不含协议变更、不含存档格式的破坏性变更。回滚代码后旧存档里的新键会被忽略，双端回到今日行为。
- **上线顺序**：第 0 步（诊断）可独立上线并观测；第 1 步（修复）待第 0 步数据确认后实施。**不得跳过第 0 步**——理由见「决策 6」。

## Open Questions

1. ~~读档后飞行中的弹幕是否应当存活？~~ → **已决**：年龄同步方案（决策 1），「重新获取即销毁」已否决。
2. **`danmaku-lag-smoothing` 归档还是改写？** 本缺陷修好后，`lag` / `hardCorrect` 两项读数才第一次具备准入意义。建议在其 proposal 里加一条判据：「双端年龄未对齐时，其准入表不可读」。是否直接归档关闭由用户定。
3. **`advance` 无界增长**（决策 4 已记录但未修）是否另开一个变更？它与年龄无关，是推进项的量纲问题。
4. **`/gs_boss danmaku` 的呈现形态**：年龄偏移是与既有 `lag` 并列一行，还是单独子命令（更易做前后对比）？
5. **弹在视野外时的行为**是否需要一并审视？服务端不因客户端看不见就停止 tick，弹会继续飞到寿命结束——这是既有行为，与本变更无关，但在路径 ② 的语境下它变得可感知（玩家后撤时弹幕会离开视野，回来时它已经飞远了，但**年龄必须是对的**）。若希望「看不见就停」是玩法需求，那是另一个变更。
