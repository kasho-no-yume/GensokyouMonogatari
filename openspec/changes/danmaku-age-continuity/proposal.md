## Why

**读档后，客户端与服务端的弹幕「年龄」不再相等，位置纠偏包于是每 2 tick 把弹硬拽一次。**

现象：正常游戏弹幕平滑无延迟；**一旦存档退出再进入，原本正在飞的弹幕立刻开始抽搐、不断被拽向服务端位置**。单人已可见，专用服务器上偏移量更大。

**根因：`Entity.tickCount` 既不进存档，也不同步给客户端。**

从 NeoForge 21.1.248 反编译源码逐条核实（`net/minecraft/world/entity/Entity.java:195`）：

| 事实 | 证据 |
|---|---|
| `tickCount` 从不写入 / 读出 NBT | `Entity` 全文仅 3 处 `tickCount` 引用，全是水晶音效；`addAdditionalSaveData` / `readAdditionalSaveData` 不含它。整个 MC 只有 `AreaEffectCloud` 自己存 `"Age"` |
| 生成包不带年龄，客户端重建时也不设 | `Entity.recreateFromPacket`（`:3562`）只做 `syncPacketPositionCodec` / `moveTo` / `setXRot` / `setYRot` / `setId` / `setUUID`，**无 `tickCount`** |
| 两端每 tick 各加 1，节奏一致 | `ServerLevel.tickNonPassenger` 与 `ClientLevel.tickNonPassenger` 均为 `setOldPosAndRot(); tickCount++; entity.tick();` |

于是：

```
发射时   server tickCount = 0 ──┐
         client tickCount = 0 ─┘ (同 tick 配对)      ⇒ 相位相同 ⇒ 平滑 ✓

读档后   server tickCount = 0 起步，但 NBT 把【位置】还原到「年龄 T」的坐标
         client tickCount = 0（生成包给的）
         ⇒ 服务端已在跑第 T tick，客户端以为自己在跑第 0 tick
```

**位置被保存了，年龄没被保存。** 而本项目的运动学恰恰是「`tickCount` 的纯函数」——位置与状态之间缺了那个自变量。

### 触发条件不止「读档」：每一次「失去跟踪 → 重新跟踪」

客户端实体的年龄归零，其触发条件是**「客户端丢掉这个实体、之后又重新拿到」**。读档只是其中最显眼的一个实例：

```
┌─ 会让客户端实体消失、并在新实体上从 0 重数的所有路径 ─────────┐
│                                                             │
│  ① 世界读档（本变更最初观察到的）                              │
│  ② 玩家走出 clientTrackingRange（球/刀/符 = 8 格）再走回来       │
│  ③ 客户端区块卸载但服务端仍加载（模拟距离 < 追踪距离时必然发生）  │
│  ④ 末影箱 / 跨维度 / 传送 / 重生                                │
│  ⑤ BOSS 战横跨区块边界，弹所在区块被卸载后重新加载                │
│                                                             │
└─────────────────────────────────────────────────────────────┘
        ↓ 无论走哪条：服务端那份一直在 tick，客户端那份从 0 重数
        ↓ ⇒ 双端年龄差 = 服务端已跑过的 tick 数
```

**② 与 ③ 在多人正常游玩中每分每秒都在发生**：玩家后撤拉开距离再贴脸回来，一枚编队弹的客户端年龄就被重置一次。**单机看不出来，是因为单人世界里客户端与服务端几乎从不脱钩，且观察者多半在盯相位无关的直线弹。**

**这条同时否掉「读档即销毁」这条廉价修法**：一旦 discard，玩家后撤 8 格再回来弹幕就永久消失——那比抽搐更糟。**唯一正确的解是让年龄本身跨「重新获取」连续。**

**为什么表现为「抽搐 + 被拉回」**（球/刀/符的 `updateInterval(2)`，见 `ModEntityTypes`）：

```
服务端 age=T ──每 2 tick──► 位置包 p_server = f(T) ──► lerpTo
客户端 age≈0 ──本地推演──► p_client = f(2)
                            err² = |f(T) − f(2)|² ≫ 1.0
                            ⇒ setPos(p_server)      硬纠正
客户端下一 tick 本地又回到 f(3)          ⇒ 回到自己的解析轨迹
再下一个位置包又被拽回 f(T+2)            ⇒ 抽搐 / 反复被拽
```

`lerpTo` 的硬纠正只 `setPos`、不 `setOldPosAndRot`，而 `xOld` 仅由 Level 的 `setOldPosAndRot()` 设置，于是渲染器在那一帧跨着 1 格以上的横距做插值——肉眼即顿挫。

**受影响的形态**（取决于运动学是否 `tickCount`-依赖）：

| 运动形态 | 弹位是年龄的纯函数？ | 读档后 |
|---|---|---|
| 匀速直线（无 profile/curve/frame） | 否（位置与年龄无关） | ✅ 正常 |
| **编队帧** `FormationFrame` | **是** | 💥 客户端从花心重放、服务端在半圈外，误差几十格 |
| **速率曲线** `DanmakuSpeedProfile` | **是** | 💥 减速型弹客户端用 `v0` 猛冲、服务端已近乎停住 ⇒ **服务端位置在后面，真的往回拽** |
| 曲射 `CURVE` | 否（对当前速度做增量旋转） | ✅ 正常 |
| 悬停 / 分裂 | 是（阈值 tick） | ⚠️ 客户端提前 `discard()`，与服务端不同步消失 |
| 相位隐藏 | 是 | ⚠️ 闪烁相位错位 |
| 寿命 / `diesAtOrigin` | 是 | ⚠️ 读档后多活 `MAX_LIFETIME_TICKS` |

**为什么专用服务器「不敢想」**：偏移量 K = 服务端实体已跑过的 tick 数，且**在多人下它由玩家行为决定，不由世界状态决定**——后撤几秒再回来就是几十 tick，走远一趟再回来就是几百上千 tick。误差上百格时每 2 tick 被拽飞一次，弹幕会在两个相距上百格的位置之间反复瞬移。单机 K 近似为 0（客户端与服务器几乎不脱钩），故单人仅在读档那一刻可见。

### 对「读档即销毁」这条廉价修法的否决

若读档后飞行中的弹幕直接 `discard()`，单机确实可接受（弹幕本就活不过几秒）。**多人服务器不可接受**：路径 ②（走出 `clientTrackingRange` 再回来）与 ③（客户端卸载区块、服务端仍在）走的是同一条 NBT 往返路径，discard 会让玩家每次后撤再贴脸就永久失去那一片弹幕。**症状从「弹在抖」变成「弹没了」，且触发频率从「读档一次」升到「每场战斗数十次」。**

⇒ 读档时的存续与后撤时的存续**必须是同一个判据**，而该判据只能是「年龄跨重新获取连续」。

### 与 `danmaku-lag-smoothing` 的关系：该提案**不能**解决，且会掩盖

`danmaku-lag-smoothing/proposal.md:30` 的前提是「客户端自 spawn 起**已知道整条未来轨迹**，预测早已免费获得」。**读档后这句话不成立**——客户端知道公式，但自变量错了。逐个候选看：

| 候选 | 对本缺陷的作用 |
|---|---|
| A 速度相对阈值（`v × 4 tick`） | **放大接受窗口**，几十格误差更容易被吞 ⇒ 更难发现 |
| B 模拟 / 渲染分离 | 抖动消失，巨大相位差照旧 |
| C 相位推前 `f(t + L̂)` | `L̂` 估出 30（单机）/ 3000（专服），被钳到 10 ⇒ 弹被**平滑地画在错误的位置** |

该提案 `:115` 自己写下了这个风险：「`L̂` 吸收真 bug——把同步 bug 从硬失败静默转成错渲」。方向恰好相反：现在是**硬失败**（一格一格抽搐），装上 `L̂` 会变成**静默错渲**。

而它的准入判据表（硬纠正计数 / 滞后 p95）**已被本缺陷污染**：读档后两项都会爆表，会被误读成「网络抖动严重，需要上相位推前」。**闸门确实开了，但闸门后面站着的是另一个问题。**

### 顺带确认的两处既存偏差

**(1) 编队帧整体超前 1 tick。** `AbstractDanmakuProjectile:769-779` 注释称「本方法在 `super.tick()` 之前调用，而 `super.tick()` 还没把 `tickCount` 加一」。**在 1.21.1 这句话是错的**：`Entity.tick()` → `baseTick()` 根本不碰 `tickCount`，是 `Level.tickNonPassenger` 在调 `entity.tick()` **之前**就自增了。故 `framePositionThisTick()` 算的是 `framePositionAt(tickCount + 1)`，实际**超前整一 tick**，`framePositionAt(0)` 永远用不上。两端一致故非同步 bug，但整份编队编排相对设计意图偏了一 tick。

**(2) 编队弹的方向轴在「有帧、无速率曲线」时不入存档。** `bindToFrame`（`:737-740`）会写 `DATA_AXIS_*`，但 `addAdditionalSaveData`（`:1009-1025`）只在 `if (this.hasSpeedProfile())` 分支里存它。读档后该弹的 `axis()` 回落默认值 `(0, 0, 1)`，沿弹道推进项指向世界 +Z。

## What Changes

### 第 0 步：诊断先行（准入闸门，无条件先做）

本变更 MUST NOT 在实测数据到手前实施任何修法。先补齐测量能力：

- `DanmakuBudget` 新增**年龄偏移**维度：记录「本弹自 spawn / 自读档起已被推进的 tick 数」与「其解析自变量的权威值」之差，按档给出直方图
- 区分**刚发射**与**读档还原**两类弹——这是本缺陷唯一的判别特征，正常游戏里前者恒为 0
- `/gs_boss danmaku` 输出年龄偏移的 min / 中位数 / p95

**准入判据**（实施前由用户依实测填写）：

| 实测结果 | 结论 |
|---|---|
| 读档后「读档还原」类弹的年龄偏移 p95 显著非零（≳4 tick），且刚发射类恒为 0 | 假设成立，继续第 1 步 |
| 刚发射类弹的年龄偏移也非零 | 另有根因，MUST 重新调查，MUST NOT 实施本变更的修法 |

### 第 1 步：让「年龄」成为显式同步量

新增一个 `SynchedEntityData` 字段承载**出生 / 读档时的年龄基准**，并纳入存档；`age()` 由「基准 + `tickCount`」得出。基类内全部 `this.tickCount` 换成 `age()`。

```
生成时   基准 = 0                        ⇒ 与今日行为逐位一致
读档后   server 基准 = T, tickCount 从 0 数 ⇒ age = T, T+1, …
         client 基准 = T（生成包自带）    ⇒ age = T, T+1, …   ✅ 逐 tick 相等
```

同时修正：(1) 编队帧的 tick 编号 off-by-one；(2) 编队弹方向轴的存档缺失。

### 硬性约束

- 年龄基准 MUST 走 `SynchedEntityData`（生成包已随 `trackedDataValues` 同 bundle 下发，无单帧竞态）MUST NOT 走普通字段
- 正常发射路径的行为 MUST NOT 改变（基准为 0 ⇒ `age() === tickCount`）
- **本变更接管「弹体年龄」**。`danmaku-lag-smoothing` 在其被重新评估前 MUST NOT 实施——理由见上节

## Capabilities

### New Capabilities

- `danmaku-age-continuity`: 弹体年龄在存档 / 读档后双端连续；年龄偏移的可判定测量；编队帧解析求值的 tick 编号正确性；编队弹方向轴的存档完整性

### Modified Capabilities

- `danmaku-motion`: 「双端一致」这条 Scenario 此前**隐含假设**双端 `tickCount` 恒等，该假设不成立，须改为「双端在任意**年龄**上逐位相同」
- `danmaku-pipeline-capacity`: 「弹体状态的同步准入判据」把「双端 tick 次数相同」写成了判据的前提，须改为「双端**年龄**相同」并补上年龄本身的同步义务

## Impact

- **改动面**：`AbstractDanmakuProjectile`（新增年龄字段 + `age()` + 10 处 `tickCount` 替换 + 帧 tick 编号 + 方向轴存档）、`DanmakuBudget`（新计数维度）、`DanmakuTestCommands` / `/gs_boss danmaku`（诊断输出）
- **依赖**：测量能力挂在 `DanmakuBudget` 上，与 `danmaku-budget-and-sync-correctness` 已落地的 tick 计时维度同处一个类，建议同一次改动内完成
- **不改动**：`lerpTo` 的纠偏策略、渲染路径、`FormationFrame` / `DanmakuSpeedProfile` 的数学
- **行为变化**（刻意压到最小）：
  - 读档后编队弹 / 速率曲线弹 / 悬停弹 / 相位隐藏弹不再抽搐
  - 读档后弹的剩余寿命按真实年龄扣减，MUST NOT 平白多活 `MAX_LIFETIME_TICKS`
  - 编队编排相对设计意图回正 1 tick（`framePositionAt(0)` 开始被使用）——**这是观感变化，需实机确认**
  - 「有帧、无曲线」的弹读档后推进方向不再回落到世界 +Z
- **风险**：
  - **第 0 步的诊断本身有观测偏差**：`DanmakuBudget` 的 `recordLag` 分母含未对齐的弹，读数在修复前本就不可信——这正是必须先做第 0 步的理由
  - **年龄基准是 int，理论上限 `Integer.MAX_VALUE`**。`MAX_LIFETIME_TICKS = 1200` 故实际不会溢出，但 MUST NOT 依赖这一点而不加钳位
  - **观感无法自动验证**：「抽搐消没了吗」「编队正回来了吗」只能实机判断
- **兼容**：存档格式新增若干 NBT 键（年龄基准、编队方向轴）。旧存档缺这些键时按缺省值读入，读档出的飞行中弹幕仍会退化为今日的错位行为——**不需要迁移，且不迁移是更安全的默认**

## Open Questions

1. ~~读档后飞行中的弹幕**是否应当存活**？~~ → **已决（2026-09-29，用户）**：单人读档消失可接受，但**多人服务器不可接受**（后撤再贴脸会永久失去弹幕）。**故否决「读档即销毁」，采用年龄同步方案。** 该决断的完整理由见「对『读档即销毁』这条廉价修法的否决」一节
2. `danmaku-lag-smoothing` 是**改写**（加一条「年龄未对齐前禁止实施」的判据）还是**归档关闭**（其问题域被本变更覆盖大半）？
3. 编队帧的 1 tick 回正会改变所有既有编队符卡的观感。MUST 在实机确认后再决定是本变更内一并改，还是拆成独立变更
4. **客户端跟踪丢失是否需要与「丢失原因」区分？** ②（走出 8 格）与 ①（读档）在服务端侧是同一种状态（客户端实体消失、服务端那份继续 tick），但玩家的**可感知后果**不同：① 一次，② 一次后撤一次。前者可以只靠「重新进入时年龄正确」解决，后者还牵涉「弹在视野外时是否继续飞」这一玩法问题（默认：继续飞，因为服务端不因为看不见就停止 tick）
